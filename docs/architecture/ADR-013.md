# ADR-013 — Correction Semantics, Historical Dependencies, Projection Effects, and Exception Workflow

## Status

Accepted

## Context and authority

The Slice 10 readiness gate identified missing correction semantics after Slice 9 closed. D6 requires a reversing entry plus a correct entry, both referencing what they correct and carrying a stated reason. The original history must remain intact. The existing correction-reference seams do not alone define administrative reversal, repeat admission, effective history, receipt consequences or Exception workflow.

This decision supplies those bounded semantics. It is a document-only governance artifact; it does not implement or open Slice 10. A separately authorized implementation gate must provide the migration, production behavior, invariant proofs and prior regressions.

The starting checkpoint is main at f6e60f1e4cd58ae1aba276ce7d1f8c57c2c56c1c, matching origin/main after fetch. Migration head is 0010_receiving. The accepted software baseline remains 1,906 tests passed on PostgreSQL 16.15. No new software test result is claimed by this authoring gate.

## Scope

| Class or workflow | Slice 10 disposition |
| --- | --- |
| Ordinary lifecycle transitions, movements, ownership, custody and assignment events | Admitted corrections, subject to effective-head/global-version eligibility and existing replacement-domain rules. |
| Receipt lines | Admitted typed correction overlays on completed receipts, with atomic receiving/Exception consequences and preserved creation identity. |
| Issued procurement line record mistakes | Admitted typed correction history within the unreferenced-comparator boundary; genuine expectation amendments still use supersession. |
| Immutable Exception observations | Workflow status events and correction-derived consequences; no direct observation-edit operation. |
| Configuration correction | Deferred; existing append/order behavior remains unchanged. |
| Receipt-header correction | Excluded from this bounded surface. |

| Evidence storage, offline correction, materials, conversion and RMA/logistics | Remain deferred. |

The following decisions are normative for a separately opened Slice 10 implementation. Exact table/column/route names may follow repository conventions; that freedom does not permit changing root, generation, time, version, projection or admission semantics.

## Decision 1 — Administrative correction preserves physical truth

A correction repairs the recorded interpretation of an earlier fact. Its REVERSAL is an administrative reversal of recorded authority under D6, not an assertion that an inverse physical or business action occurred. The CORRECTED entry establishes the replacement recorded fact. Both are immutable history with their own correcting Actor and administrative times.

Correcting a recorded A -> B movement to the actual A -> C must not assert a physical B -> A return. Correcting an owner or custodian must not invent a later transfer; correcting an assignment must not invent an unassignment. An actual subsequent compensating action remains an ordinary domain operation with its actual event-time claim. The correction role distinguishes these meanings in storage, history responses, and effective interpretation.

## Decision 2 — Every admitted correction has one complete pair

Each admitted correction creates exactly two correction entries in its affected authoritative history: one REVERSAL and one CORRECTED. The ordinary original remains byte-identical. The first generation therefore adds two rows to the original, preserving the handoff's original/reversal/corrected pattern.

Asset-history pairs belong to their typed Asset history class. Receipt-line and procurement pairs belong to their respective typed correction histories alongside the unchanged ordinary records. Pair metadata, typed consequence links, new Exceptions and workflow events are not additional correction entries or Asset-version producers. Neither half can commit alone.

## Decision 3 — Correction role is explicit

Every ordinary or correction-produced history row has an explicit typed role equivalent to NONE, REVERSAL or CORRECTED. Ordinary originals have role NONE. Every correction pair has exactly one of each correction role. A nullable corrects_* reference alone is not sufficient to determine role.

Role, references and pair shape must agree durably. Existing ordinary histories remain ordinary and are not reclassified as corrections. No externally supplied role permits bypassing the typed correction operation. Exact column names and the structural representation of existing ordinary rows belong to implementation.

## Decision 4 — Root original is stable

ROOT ORIGINAL means the ordinary, non-correction record whose recorded authority is being corrected. Every generation for that fact references this same root. A REVERSAL or CORRECTED row is never an independently addressable correction root, and no pair targets another pair.

For procurement, the correction root can be an ordinary issued PO-line amendment version; it need not be the first version of the procurement supersession lineage. Procurement lineage and correction generations are distinct relationships. Root organization, entity and history class never change.

## Decision 5 — Pair identity and typed linkage

Each operation has an immutable pair identity. Both rows carry the same root reference, pair identity, correction generation, normalized reason, credential-derived correcting Actor and administrative correction occurrence-time claim. Each row has its own identity and server recording time.

Existing corrects_transition_id, corrects_movement_id, corrects_custody_change_id, corrects_ownership_change_id and corrects_assignment_event_id seams retain same-class, same-Asset, same-organization root semantics where used. Receipt-line and procurement correction relationships are separately typed. There is no generic cross-table JSON target, caller-selected relationship graph, or new global Asset version register.

The pair identifies the whole correction for provenance and consequence linkage. It must remain possible to retrieve its root and both members without timestamp or UUID ordering.

## Decision 6 — Effective head identifies current replacement authority

EFFECTIVE HEAD for a root is the ordinary root when no accepted generation exists. Otherwise it is the CORRECTED row of that root's greatest committed, complete correction generation.

The head is derived from immutable root and generation history. Any maintained head metadata is only a projection, must agree with that history, and is updated in the correction transaction. It cannot independently authorize admission or hide an incomplete generation. Committed malformed history fails admission and health rather than silently falling back to an older head.

## Decision 7 — Each reversal cancels the previously effective authority

Generation 1's REVERSAL administratively cancels the root's authority. Generation 2's REVERSAL cancels generation 1's CORRECTED authority; generation 3 cancels generation 2's CORRECTED authority, and so on.

Both members nevertheless reference the ordinary root. The root plus generation identifies which earlier authority is cancelled: the root at generation 1, or the CORRECTED member of generation g - 1 thereafter. No correction-target chain is needed. Raw history presentation must explain that an administrative cancellation is not a physical inverse event and must identify the authority cancelled by each generation.

## Decision 8 — Generations provide deterministic order

A root without corrections has expected correction generation 0. Accepted generations are 1, 2, 3 and so on, allocated from authoritative committed generation history while holding the governing lock. One root/generation identifies one pair, and the next accepted generation is the previous generation plus one.

Neither clocks, UUIDs nor lexical IDs order authority. An aborted correction commits no generation and cannot leave an accepted half-pair. At most one pair is effective for a root: the greatest complete generation. A mutable active flag is not an alternative authority. Exhausted version or generation capacity rejects atomically rather than wrapping or reusing a value.

## Decision 9 — Repeat correction preserves every earlier generation

A correction may itself prove wrong. Admit another pair against the same ordinary root when the class's current admission rules still hold. Allocate the next generation; retain all earlier pairs and their Actors, reasons and times unchanged.

The new CORRECTED member carries a complete replacement of the correctable domain values, not a patch that depends on replaying earlier correction payloads. If a bounded API accepts partial input, it must materialize the complete intended replacement from locked effective authority and the supplied values before appending. Unchanged corrected values are not silently reset to the original mistake.

## Decision 10 — Durable pair and graph invariants

PostgreSQL must enforce that the root exists, is an ordinary record, and belongs to the same organization, entity and history class as both members. Each member belongs to exactly one pair; each pair has exactly one REVERSAL and one CORRECTED; both agree on root, generation, reason, Actor and correction occurrence time.

Require unique root/generation allocation, no self-reference, no correction-row roots, and no cycles or ambiguous effective branches. Typed composite relationships protect tenancy; complete-pair and role coherence must hold at transaction completion, including permitted direct runtime SQL. Pair/history UPDATE, DELETE and TRUNCATE remain prohibited for fleetops_app.

Python request validation is not a substitute for durable constraints and narrow write-boundary checks. Temporary construction of a pair inside its transaction is permissible; committing a malformed pair is not.

## Decision 11 — One immutable nonblank reason

The request supplies one free-text reason. Trim surrounding whitespace, reject blank-after-trim, preserve its meaning, and copy the normalized value identically to both members. Adopt the existing history-reason limit of 1 through 4,000 characters after normalization, including rejection of whitespace-only text.

The server must not paraphrase the reason or supply a default that conceals its absence. The stored reason is immutable. There is no controlled reason-code taxonomy in v0.1. Correction-derived resolution notes identify the correction and its reason rather than inventing an operator statement.

## Decision 12 — Correcting Actor comes from the credential

The correcting Actor is the current credential-derived HUMAN Actor under ADR-006, revalidated at the durable boundary. The caller cannot choose an Actor through request fields, SQL parameters, row values or an arbitrary Actor GUC. Missing, invalid, expired, revoked or tenant-mismatched credential authority rejects without writes.

The original and every prior generation preserve their recorded Actors. Both new members record the same correcting Actor. Server-derived correction consequences are attributable to that same authenticated action; a caller-selected SYSTEM Actor is not a substitute. Ordinary role separation and credential confidentiality remain unchanged.

## Decision 13 — Administrative and corrected domain times remain distinct

Original occurred_at and recorded_at are never overwritten. Both correction members carry the same correction_occurred_at claim: when the administrative correction action occurred. Each recorded_at is database/server recording time and cannot be supplied by the caller. All timestamps remain UTC and finite; ordinary timezone-aware input rules continue to apply.

When the corrected domain fact has an occurrence time, the CORRECTED member carries the replacement domain occurrence value separately. If that value is not being corrected, retain the current effective domain occurrence claim. It must never be derived by replacing it with correction time or server recording time. An existing occurred_at column on a correction row may represent administrative occurrence only if the separate domain occurrence value and API meanings remain explicit.

Effective assignment intervals and other temporal fact reconstruction use the replacement domain occurrence value. Audit history exposes the administrative occurrence and recording times as well. No clock determines generation, event succession or produced-version authority, and disagreeing claims are not silently clamped or reordered.

## Decision 14 — Asset corrections produce two consecutive global versions

For lifecycle, movement, ownership, custody and assignment corrections, resolve trusted organization and credential authority, identify the tenant-scoped Asset, and acquire its shared FOR UPDATE row lock before admission or expected-version validation.

With current locked Asset version N and matching request expected_version, allocate REVERSAL.result_version = N + 1 and CORRECTED.result_version = N + 2. The final assets.version is N + 2. Both rows are raw global-version producers, each appearing exactly once in combined version provenance. They never share a produced version.

This is one governed compound correction transaction, not two separately committable calls to ordinary operations. It does not grant a version bypass, per-class counter, shared register or permission to call an ordinary inverse physical operation. Ordinary operations continue to produce one version.

## Decision 15 — First correction requires the root at the global head

For generation 1, EFFECTIVE HEAD is ROOT ORIGINAL. After holding the Asset lock, require request expected_version = assets.version and effective_head.result_version = assets.version.

Also verify ordinary-root identity, tenancy, generation 0, authoritative history completeness, current projection agreement, and domain preconditions. This is stricter than being the latest event in one class. A lower root version cannot be admitted merely because a later global event changed another fact. The expected version is a concurrency token, not permission to choose a historical state.

## Decision 16 — Repeat correction checks the effective head, not the root's old version

For generation g > 1, derive the current effective CORRECTED member under the same Asset lock. Admission requires its result_version to equal current assets.version, and the request expected_version to equal that current version. The immutable root's original result_version is not required to equal the current Asset version after generation 1.

For a root at v10, generation 1 produces REVERSAL v11 and CORRECTED v12. The effective head and Asset version are then both v12, so generation 2 may produce REVERSAL v13 and CORRECTED v14. Both new rows still reference the root at v10. Derive the pre-root domain source as specified in Decision 22; generation 2 replaces the same original operation rather than acting physically from generation 1's mistaken destination.

## Decision 17 — An intervening global operation blocks further correction

If the root's effective CORRECTED head is v12 and another version-producing operation commits v13, that root is no longer eligible: effective_head.result_version differs from assets.version. A request carrying the current expected_version v13 still rejects; a fresh token cannot waive historical eligibility.

This applies to later ordinary operations of the same class, operations of another class, and correction activity belonging to another root. No later history is removed, rolled back or replayed to reopen eligibility. Receipt/configuration records do not become Asset version producers merely to perform this check.

## Decision 18 — Eligibility follows global authority, not class-local recency

The root's effective head must be the current global version-producing authority. Being the latest movement, ownership change, custody change, assignment or lifecycle event is insufficient when another class has advanced the Asset.

Cross-class operations may depend on the recorded facts they observed. The v0.1 gate does not presume those dependencies harmless. Preserve D8 orthogonality when a correction is admitted: it changes only its own factual projection and the shared Asset version, not unrelated Asset facts.

## Decision 19 — No historical descendant replay

Slice 10 builds no replay engine and no facility for cascading reinterpretation of later Asset events. If unrelated global history follows the target's effective head, reject without history, projection or version writes.

Reading effective pre-root history for replacement validation is reconstruction of existing authority, not replay or mutation of descendants. A future facility that admits older effective heads or propagates changed preconditions through later operations requires separate governance. Caller acknowledgement or an Exception waiver cannot override this boundary.

## Decision 20 — Non-version-producing histories remain non-version-producing

Receipt-line and procurement correction histories do not carry Asset result_version or increment an Asset merely because their records relate to one. Configuration remains non-version-producing and deferred from correction. Initial physical and assignment creation witnesses remain excluded from global version accounting.

For admitted non-version-producing corrections, lock the stable target/owner row, derive current complete correction generation, and validate the request's expected generation after acquiring the lock. Generation 0 means no accepted correction. Allocate only the next generation. There is no last-writer-wins behavior.

Receipt correction does not implicitly issue movement, ownership, custody, lifecycle or assignment corrections. Any authorized consequential Asset-history correction is a distinct typed operation subject to its own admission. This ADR does not authorize a cross-domain cascade to evade the creation boundaries in Decisions 34–37.

## Decision 21 — One transaction contains the complete correction

One operation commits eligibility validation, generation allocation, REVERSAL, CORRECTED, effective-head change, affected projection and every required domain consequence in one transaction. Failure in any part leaves none of that correction committed. Retain the governing locks until transaction completion.

For Asset histories this includes both global versions and the final Asset projection. For receipt lines it includes all affected effective comparisons, immutable new Exception observations, correction provenance and permissible Exception status events/projections. A valid terminal Exception case is processed without a status transition, not treated as a failed consequence.

Do not return success after writing only the pair or defer required receiving consequences to an eventually consistent repair job. Python retains workflow orchestration; PostgreSQL enforces durable integrity and the justified atomic boundaries.

## Decision 22 — Validate the replacement from pre-root effective authority

Derive the class's authoritative domain value immediately before the ordinary ROOT ORIGINAL from effective history, not from its mutable current projection or a caller-supplied source. Use ADR-007's immutable baseline for a first physical-history operation and ADR-008's initial-unassigned witness for a first assignment. Missing required authority rejects; do not synthesize it.

Every generation validates its CORRECTED replacement as the operation that should have been recorded at that root, using that same pre-root source. Ordinary tenant, required-value, lifecycle and evidence constraints apply to the replacement. REVERSAL is an administrative cancellation and is not validated or exposed as an ordinary inverse domain operation. Its payload identifies the cancelled assertion; it must not assert false inverse physical endpoints.

Before correcting, separately verify that current projections agree with current effective authority. Deriving a valid historical replacement must not become a way to conceal existing projection corruption. Initial lifecycle creation at global version 1 is not an ordinary replaceable edge: this ADR does not reopen the creation bundle or invent a pre-creation domain state.

## Decision 23 — Raw and effective history answer different questions

Raw history returns the ordinary root and every correction member, including superseded generations, with identity, role, generation, references, Actor and times. For a corrected root, effective history selects only the greatest complete generation's CORRECTED member; for an uncorrected root, it selects the ordinary root. Administrative REVERSAL members never masquerade as effective physical events.

Order effective Asset history by its selected producers' result_version, retaining class-local gaps. The latest-effective-global admission rule ensures a replacement is admitted before any unrelated later producer; it cannot move authority across already-committed descendants. Pre-root reconstruction excludes the root and its generations and uses preceding effective class authority.

A CORRECTED member's complete replacement payload and separate domain occurrence time supply factual interpretation. Raw producer versions remain visible even when their factual assertions are superseded. An effective-history query must not hide malformed pairs or use a stored current projection as the source of truth.

## Decision 24 — Maintain only the affected projection

At commit, set the relevant projection directly to the newest CORRECTED result: lifecycle current_state, movement current_location_id, ownership owner_party_id, custody custodian_party_id, or assignment current_assignment_id as governed below. No externally committed intermediate reversal projection exists.

Update the projection, its required updater attribution and Asset version in the same transaction as the pair. Preserve unrelated projections and all initial witnesses. Effective receipt and procurement values are derived from immutable correction history; this decision does not create an independently authoritative mutable receipt or procurement record. Exception status has its separate event-maintained projection.

## Decision 25 — Factual reconciliation and raw version accounting remain separate

Compare factual Asset projections against effective history. Independently prove that every global version from 1 through assets.version has exactly one raw producer across lifecycle, movement, custody, ownership and assignment histories. Both correction members and all superseded correction generations remain in that raw union.

Do not remove administrative REVERSAL versions from accounting, count a pair as one produced version, or count both a root and its replacement as simultaneously effective facts. Retain missing, duplicate and ahead-of-Asset version detection, valid class-local gaps, and independent initial baseline/witness completeness checks. No shared Asset version register or projection-derived history repair is introduced.

## Decision 26 — Lifecycle correction

correct_transition admits an ordinary lifecycle root belonging to the Asset and organization only when the expected-version and effective-head/global-version checks pass. The CORRECTED replacement must be a legal ordinary lifecycle edge from the effective state immediately before the root. REVERSAL need not be a legal inverse edge because it asserts administrative cancellation only.

ON_HOLD predecessor selection uses effective lifecycle history and the replacement's pre-root source, not a reversed physical edge, timestamps or an unrelated global version. RETIRED restrictions remain evidence-gated; correction cannot manufacture evidence or reopen a permanent creation record.

This design does not add MAINTENANCE, a general no-op edge, or a cancel-only lifecycle operation. A proposed replacement that fails the existing graph rejects, even if the operator's desired outcome is to say that no lifecycle change should have been recorded.

## Decision 27 — Movement correction

correct_movement derives the effective location immediately before the root, including a valid unknown/null location under existing rules. It validates the corrected destination and applies the effective-head/global admission rule.

For pre-root A and erroneous A -> B, the new administrative REVERSAL cancels the previously effective assertion and CORRECTED records A -> C. The final current_location_id is C. Raw movement history identifies the reversal as administrative and must not assert B -> A physically occurred. Later ordinary movements use the corrected effective destination as their source authority.

## Decision 28 — Ownership correction

correct_ownership is admitted under the same Asset lock, expected-version and effective-head/global checks. Its source owner is the effective owner immediately before the ordinary root; its corrected destination owner is required and must be a valid same-organization Party.

The administrative REVERSAL does not assert a physical/legal transfer from the erroneous owner. The CORRECTED entry replaces the historical owner-change assertion. Only owner_party_id and the shared Asset version change; custody, location, lifecycle and assignment remain independent. The original creation owner is not a direct correction target.

## Decision 29 — Custody correction

correct_custody follows the same effective-head/global admission rule and derives its source from effective pre-root custody. The replacement custodian may be NULL where the existing custody contract permits unknown or unrepresented custody; represented Parties require the established tenant-safe validation.

REVERSAL does not fabricate a physical return of possession. Update only custodian_party_id and the shared Asset version. Ownership remains required and unaffected; nullable custody does not imply unknown ownership or an absent baseline.

## Decision 30 — Assignment correction

correct_assignment validates the complete replacement against effective assignment immediately before the ordinary root. Preserve the existing ACTOR/LOCATION/PARTY assignee vocabulary, paired NULL semantics and ordinary ASSIGN/REASSIGN/UNASSIGN preconditions. An unassigned-to-unassigned operation is not newly authorized.

The administrative REVERSAL does not create a physical unassignment or close an interval. Derive intervals from effective assignment events in result_version order, using the selected CORRECTED member's separate domain occurrence value where applicable. Exclude superseded generations and administrative rows from interval construction while retaining them in raw audit and version provenance.

If the replacement establishes an assignment, current_assignment_id references the effective CORRECTED establishing event; if it establishes unassigned, the projection is NULL. Validate current projection agreement before admission and preserve the independent initial-unassigned witness and unrelated Asset facts.

## Decision 31 — Configuration correction remains deferred

Configuration records remain append-only, non-version-producing and ordered by ADR-008's database-assigned configuration_seq. This ADR does not activate a configuration correction endpoint or replace that ordering with correction generations.

ADR-008 Decision 26's future D6 correction obligation remains. Handoff v1.3 names no configuration correction operation in Slice 10 and supplies no explicit requirement to activate one now. A later bounded decision must settle configuration correction content and effective-order consequences before implementation; deferral does not authorize overwriting an earlier configuration.

## Decision 32 — Receipt-header correction is excluded

The explicit handoff operation is correct_receipt_line. Slice 10 exposes no general receipt-header correction API. Header vendor, PO, dock, packing-reference and received_at facts remain immutable under the existing receiving contract.

Receipt occurrence remains the header's received_at claim. A receipt-line correction has its own administrative correction occurrence time but cannot use a new child occurrence claim to disguise a header-time correction. Header correction beyond this boundary remains deferred pending explicit governance.

## Decision 33 — Receipt-line corrections are typed immutable overlays

correct_receipt_line appends one REVERSAL/CORRECTED pair to typed receipt-line correction history. The root is the ordinary receipt_line, with immutable receipt identity. The newest complete CORRECTED generation supplies the full effective replacement of admitted line fields; prior generations and the original remain raw evidence.

Do not UPDATE or DELETE the original, insert a negative receipt line, reopen the sealed population, or reinterpret the pair as another physical delivery. Every original physical line contributes once to an effective population, through its root or current CORRECTED replacement; reversal entries are not quantities to sum. Captured original UOM remains unchanged, and a replacement UOM is a new explicitly recorded claim, not conversion of the original.

For this bounded correction workflow, require the receipt's existing immutable reconciliation/completion witness before admission. Complete ordinary capture through the existing receiving workflow first; do not invent completion or modify its witness. This supplies a closed physical population for atomic correction-derived reconciliation.

Lock the same PO before the receipt where a PO exists, preserve receiving's READ COMMITTED fresh-view requirement, and validate expected root correction generation after these locks. Both ordinary capture and correction retain the existing receipt serialization boundary. The pair, replacement validation, evaluation provenance and required Exception consequences commit together.

## Decision 34 — Receipt eligibility preserves creation and typed receiving facts

A nonserialized no-Asset line is correctable within the existing receiving domain: its replacement Item remains nonserialized, its quantity remains positive and finite, and its UOM, condition, optional packing quantity and other admitted fields meet their existing constraints. A correction cannot convert that line into an unrecorded serialized Asset creation.

For a normal serialized line, retain its received Asset identity, Item identity, canonical identifier relationship, initial transition, physical baseline and initial-unassigned witness. Reject any change requiring deletion/replacement of that bundle, alteration of creation owner/custodian/dock facts, or transfer of canonical identity. Corrections to line-only quantity/UOM/condition/comparator/packing/notes are admissible only where they preserve those facts; serialized quantity is exactly 1 for every governed UOM on both normal and conflict paths. No correction introduces fractional or aggregate serialized units.

For a SERIAL_MISMATCH no-Asset observation, preserve the observation-only admission class. Corrected observed identifier type/value must still identify a valid same-organization canonical conflict under ADR-012; derive conflicting_asset_id from that authority, never caller testimony. An identifier correction that would require retroactively creating a normal Asset, clearing the conflict into a normal receipt, or modifying the existing conflicting Asset rejects. Other corrected observation facts retain the existing serialized Item, required-owner, nullable-custodian and quantity-1 rules.

A replacement comparator, if supplied, must be an explicit exact PO-line version in the unchanged receipt's PO and organization. Retaining an originally admitted comparator does not re-admit it as a new delivery merely because later supersession occurred. Selecting a different comparator requires the ADR-010 issued/active-leaf check under the PO lock; never silently select the new leaf. Preserve the exact selected corrected context separately from the raw line. A NULL comparator has the existing unexpected-item meaning and cannot acquire a fictional expected line.

Every affected classification must be derivable from corrected facts under the ten-type matrix. Unsupported creation, baseline, canonical-identifier or header consequences reject the whole operation. Terminal Exception workflow status is not an unsupported physical consequence and never supplies a rejection reason.

## Decision 35 — Asset identity cannot be corrected out of existence

D1 opaque identity is permanent. Slice 10 cannot delete an Asset, reuse its UUID, replace or transplant that identity, move its canonical namespace to another Asset, or claim that its recorded creation never existed.

Keep the complete original receiving bundle and its provenance visible. An erroneous creation assertion requiring capabilities beyond eligible line corrections is deferred for separate governance. This ADR introduces no voided Asset state, identity-merge function, tombstone substitution, replacement Asset shortcut or rewriting of initial global version 1.

## Decision 36 — Initial physical facts and assignment witness are not direct targets

asset_initial_facts and asset_initial_assignment_facts remain separate immutable creation evidence under ADR-007 and ADR-008. Neither is a direct Slice 10 correction target, and neither is copied from a current projection to manufacture historical authority.

Reject a requested correction that requires replacing either witness or changing the initial lifecycle creation bundle. Do not disguise a wrong creation owner, custodian or location as a later physical operation. ADR-007's future explicit correction-history obligation remains available for a separately governed design. Missing creation facts remain visible to health even when later effective history supplies a coherent current value.

## Decision 37 — Canonical Asset identifier correction remains deferred

Canonical MANUFACTURER_SERIAL, PCB_SERIAL, MAC, IMEI and OTHER claims retain existing immutable provenance and non-NULL (org_id, type, value) uniqueness. Slice 10 does not correct, release, move or overwrite those canonical claims.

A readable identifier observation on an eligible receipt line is a different fact. It may be corrected through that line's typed overlay only within Decision 34's existing no-Asset conflict contract. A new effective canonical-identifier history and uniqueness model requires a dedicated later decision. D1's editable human-readable fields do not themselves authorize overwriting this receiving-established canonical namespace; ordinary authorized descriptive Asset edits remain outside this correction workflow.

## Decision 38 — Procurement correction preserves amendments and receipt comparators

ADR-009 Decision 26 explicitly assigns true historical procurement record corrections to Slice 10. Provide a typed PO-line correction operation under D6; do not omit that obligation because the handoff lists four minimum correctors. A real change in supplier expectation continues through ADR-009 supersession, never through the correction operation. Authorized DRAFT authoring remains its existing separate workflow.

For this bounded correction surface, the root is an ordinary immutable line version in an ISSUED PO. Lock its tenant-scoped PO before checking expected correction generation and reference eligibility. A complete CORRECTED replacement may correct line business claims item_id, quantity, uom, unit_price and expected_date, subject to existing tenant, finite numeric, date and governed-UOM constraints. Record a corrected UOM explicitly as a new historical claim; never infer a conversion or reinterpret the original snapshot from today's Item default. Root UUID, organization, PO, logical line number, supersedes_line_id, original Actor and original timestamps cannot be correction payload targets.

The v0.1 boundary rejects business-value correction of a line version already bound as any receipt's comparator, including an admitted comparator without a physical line. This deliberately includes price and date as well as Item/quantity/UOM so existing receipt context cannot change. It also considers comparator bindings introduced through earlier receipt corrections. Reference eligibility is checked under the same PO lock used by receiving; an unlocked earlier absence check is insufficient.

For an unreferenced version, derive effective corrected procurement values from the newest complete pair without changing its raw issued row or supersession lineage. A later receiving comparator binding must retain both the exact ordinary PO-line UUID and the effective procurement correction generation used, with a typed reference to the CORRECTED source when generation is nonzero. The caller selects that UUID and expected correction generation; validate both against admitted authority after acquiring the PO lock. A stale generation rejects without silently selecting a newer correction source. Treat an omitted generation as 0 only when the selected version has no correction, preserving the existing uncorrected request meaning. Existing accepted receipt bindings mean uncorrected generation 0 and are not retargeted or backfilled from current values. A new binding freezes further business corrections of that version under the preceding rule. A receipt continues using its permanently selected expectation source, not a dynamic latest correction lookup.

These source bindings preserve ADR-009/010's exact-comparator purpose while admitting previously unreferenced record mistakes. They are typed provenance, not a new PO version counter, replacement supersession pointer or shared Asset register. Ordinary amendment creation, active-leaf derivation and preservation of all earlier expectations remain unchanged. No PO-header, close/cancel or accounting workflow is introduced.

## Decision 39 — Exception observation and workflow are separate authority

Slice 10 adds workflow to immutable Exception observations. The logical Exception includes the handoff's type, severity, entity_type/entity_id, legitimate related references, opening Actor/time, status, resolution attribution/time and resolution note. Preserve ADR-012's explicit receiving relationships and ten existing receiving types, including UOM_MISMATCH.

Workflow authority is append-only exception_events; status and resolution summaries are maintained projections. Observation identity, type, relationships, source facts, opening attribution and original times are not mutable workflow fields. A receiving observation may be associated with a dedicated workflow projection record; implementing the handoff's logical Exception must not relax the original receiving table's immutable-observation boundary.

A newly opened observation starts OPEN. Before its first status change, that immutable opening observation supplies OPEN authority; thereafter the latest authoritative status event supplies it. Existing Slice 9 observations can acquire their OPEN workflow projection from their own original opening facts without inventing historical status changes or attributing a newly fabricated event to an old Actor. Missing workflow projections are discrepancies after establishment, not permission to reconstruct a status from a possibly corrupted projection.

The handoff's older nine-receiving-type wording is already qualified by AMR-001/ADR-011/012. GENERAL and SYNC_CONFLICT are workflow vocabulary, not alternate receiving classifications; this decision supplies no generic caller-selected receiving Exception producer or offline sync capability. MISSING_LOT and BALANCE_NEGATIVE remain non-producing materials reservations.

## Decision 40 — Minimal terminal Exception status graph

The only status-change edges are:

| From | Permitted next status |
| --- | --- |
| OPEN | ACKNOWLEDGED, RESOLVED, WAIVED |
| ACKNOWLEDGED | RESOLVED, WAIVED |
| RESOLVED | None |
| WAIVED | None |

No reopening, repeated same-status transition or terminal-to-terminal conversion is admitted through the workflow. Every event has a credential-derived Actor, occurrence-time claim and server recording time. RESOLVED and WAIVED require a nonblank normalized note using the existing 1–4,000-character reason convention. Acknowledgement may carry a note without inventing a resolution.

Handoff v1.3 specifies these status values and append-only event authority, but no different transition graph. This bounded graph therefore fills the unspecified workflow choice without changing a controlled architecture decision.

## Decision 41 — Terminal workflow does not veto valid receipt correction

Exception disposition is not authority over physical receipt facts. An otherwise valid receipt correction must not fail merely because a related historical Exception is RESOLVED or WAIVED.

Evaluate the corrected facts and apply Decisions 42–49 using the actual authoritative workflow state under lock. Terminal status remains terminal; no forbidden transition is needed to record corrected reality. Correction eligibility, tenant validation, sealed population, creation constraints and pair atomicity still apply independently. A waiver neither blocks truth correction nor permits an otherwise invalid correction.

## Decision 42 — A false OPEN observation is resolved

If the corrected effective receipt facts no longer support an existing OPEN Exception's governed assertion and relationships, append an OPEN -> RESOLVED exception_event in the same transaction. Link that event to the responsible receipt correction pair through a typed same-context relationship.

Preserve the original observation. The normalized resolution note states that corrected receipt reality superseded its assertion and includes or references the submitted correction reason without changing its meaning. The event's Actor is the authenticated correcting Actor, its occurrence claim is the administrative correction occurrence, and its recorded_at is server-set. Update only the workflow projections.

## Decision 43 — A false ACKNOWLEDGED observation is resolved

Apply the same consequence to an ACKNOWLEDGED observation that becomes false: append ACKNOWLEDGED -> RESOLVED with the responsible correction-pair reference, note, credential-derived Actor and separate administrative occurrence/server recording times.

The original acknowledgement event and observation remain immutable. Do not overwrite the acknowledgement or disguise the correction as another physical receipt. Pair, resolution event and projection consequences commit together.

## Decision 44 — An already RESOLVED false observation stays RESOLVED

If corrected receipt reality no longer supports an observation whose authoritative status is already RESOLVED, the otherwise eligible correction succeeds. Keep status RESOLVED and preserve its existing resolution Actor, time and note.

Do not append a redundant RESOLVED event, reopen the workflow or overwrite the earlier resolution with the correcting Actor. Typed correction-evaluation provenance retains the relationship between the receipt correction and the affected historical observation without pretending another status transition occurred.

## Decision 45 — A WAIVED false observation stays WAIVED

If corrected receipt reality makes a WAIVED observation false, the otherwise eligible correction succeeds and status remains WAIVED. Preserve the waiver event, Actor, times and note.

Do not reopen it, convert it to RESOLVED, or append any illegal terminal transition. Record the correction's relation to the affected observation through immutable evaluation provenance, separately from workflow status. Terminal waiver does not preserve a false effective receipt assertion or veto correction.

## Decision 46 — A still-supported Exception keeps its workflow status

When an existing observation's governed disagreement and required typed relationships are still supported by corrected effective facts, leave its status unchanged, whether OPEN, ACKNOWLEDGED, RESOLVED or WAIVED. Do not automatically acknowledge, resolve, waive or reopen it.

Determine support from the existing type predicate and required context, not merely from a matching type label or a status value. Preserve its original derivation provenance even when current effective values differ. Workflow disposition and whether a disagreement is currently supported are distinct questions; the current projection cannot decide factual truth.

## Decision 47 — New disagreement instances create new immutable observations

If corrected effective facts introduce a disagreement not represented by the surviving observation instance, create a new immutable Exception with the existing governed type and relationship shape. It begins OPEN, retains the correction-derived source context and authenticated attribution, and does not mutate an earlier observation.

Apply the ten existing receiving predicates, single-valued condition rule, server-derived classifications, correct received-Asset versus conflicting-Asset roles and same-tenant/context validation. A changed actual canonical conflict must derive its actual owner; an arbitrary same-tenant Asset is not acceptable context.

Prevent duplicate observations of the same disagreement instance. A still-supported existing instance is retained without creating another row just because a correction ran. When a disagreement ceases and later reappears, or its required relationship assertion changes, the new instance gets a new observation; a terminal older observation is not reopened. Uniqueness must identify that instance and immutable source context, not permanently prohibit every later row sharing the old root-line/type combination.

## Decision 48 — Recompute every affected receipt-local effective population

In the correction transaction, evaluate line-specific predicates and all affected receipt/exact-comparator populations using one coherent effective receipt view. Each root line contributes its selected complete CORRECTED values or its original values exactly once. Preserve the original sealed physical population; correction rows are not additional arrivals.

If a line changes comparator, evaluate both the old and newly selected comparator populations. Previously admitted receipt comparator commitments remain historical receiving context and are not erased by changing one line's effective link. An explicitly selected new comparison is recorded as typed correction context, without adding physical lines or editing the sealed comparator/completion records. A comparator with no remaining contributing line is still evaluated under its governed receipt-local expectation.

Preserve ADR-011 exactly: one receipt plus one exact expectation source; full expected quantity for that receipt; no earlier/later receipt accumulation or remaining-fulfillment calculation; exact-token UOM comparability; and no UOM conversion. Any linked mismatched-UOM effective line blocks a complete SHORT/OVER/equality conclusion for its comparator, even if the comparable subtotal meets or exceeds expectation. Substitutions and eligible conflict observations retain their existing contribution rules. QUANTITY_VARIANCE remains packing-specific.

Persist enough typed immutable evaluation provenance to identify the causing pair, exact expectation sources and the effective root/generation sources used for the evaluated population. A source at generation 0 means the original; a nonzero source resolves to a complete CORRECTED member. This preserves why an observation was derived after later corrections and must not rely on timestamps or a subsequently changing latest-view query. Newly derived Exceptions and any correction-to-existing-Exception links reference this context. The provenance is a domain consequence, not a third correction member or an Asset version register.

Apply the status-specific outcomes in Decisions 42–47. Preserve all original observations, captured UOM, raw comparator relationships and the initial completion witness. Required new observations, event/projection changes, provenance and the correction pair commit or roll back together.

## Decision 49 — Terminal observations do not block recomputation or new instances

RESOLVED and WAIVED are terminal workflow facts about their historical observations. They neither prevent calculation from corrected effective receipt reality nor reserve a type forever against a genuinely new disagreement instance.

A false terminal observation retains its status without another status event. A still-supported terminal observation likewise keeps its status. A newly introduced or reappearing disagreement creates a new OPEN observation when required by Decision 47, with its own immutable derivation context and instance identity. No duplicate is created solely because an existing observation is terminal.

## Decision 50 — Exception status changes use narrow append-event authority

A dedicated operation locks the stable Exception workflow owner/projection row, derives authoritative status from the latest event or immutable OPEN origin, and checks the projection against that authority. Validate the request's expected status after the lock, then validate the proposed graph edge and note. A mismatch or stale request rejects without writes or repair.

Status events require deterministic per-Exception sequence order assigned under that lock; timestamps and UUIDs are not workflow ordering authority. Each event records same-organization Exception identity, prior and resulting statuses, credential-derived Actor, occurrence claim, server recording time and the required note. A correction-derived event additionally references its valid causing correction pair. The sequence is not an Asset global version.

Append the event and update status/resolution projections atomically. Ordinary runtime cannot directly UPDATE status or resolution summaries and cannot UPDATE, DELETE or TRUNCATE events or observations. Resolution summary fields describe the event that actually established the terminal state; an already-terminal correction never replaces them.

Receipt correction locks its PO where applicable, then receipt, then affected Exception workflow rows in a fixed deterministic identity order before reading their authoritative statuses. Standalone workflow operations lock only their Exception workflow owner and do not acquire receipt/PO locks afterward. This avoids opposite lock acquisition and serializes a concurrent waiver/resolution with correction consequence processing. The declared order is for locking, not for ordering factual authority.

## Decision 51 — Correction of a correction retains the same root

The only repeat-correction model is same ROOT ORIGINAL plus a new generation. Both new members keep the root reference. Their REVERSAL cancels the formerly effective head identified by the prior generation; their CORRECTED member becomes the new head.

For Asset histories, validate the prior effective CORRECTED head against the locked current global version, not the root's obsolete result_version. For receipt/procurement histories, validate the expected current correction generation under the stable owner lock. All earlier raw rows remain auditable. Direct targeting of a correction member is rejected rather than implicitly retargeted to its root.

## Decision 52 — Concurrent Asset corrections have one winner

Every version-producing correction uses the shared tenant-scoped Asset FOR UPDATE lock before validating expected_version, effective head or allocating versions. Check both request expected_version = assets.version and root effective_head.result_version = assets.version under the retained lock.

Two contenders carrying the same expected version cannot both succeed. The winner produces exactly N+1 and N+2; the loser waits, observes the changed version and rejects with no pair, projection or version writes. The same contention rule applies between correction and ordinary movement, lifecycle, ownership, custody or assignment operations. A supplied future token cannot bypass effective-head or history/projection validation.

## Decision 53 — Concurrent non-version corrections serialize by owner and generation

A non-version-producing correction locks the stable tenant-scoped owner before reading correction generations or dependency eligibility. Receipt-line corrections use the PO-then-receipt order; procurement corrections use the PO. Validate expected generation against immutable complete pair history after lock acquisition and allocate one next generation.

Two operations expecting the same generation have one winner. The loser observes the committed newer generation and rejects rather than overwriting it. Corrections to different lines in one receipt still serialize on the receipt so aggregate evaluation and Exception consequences cannot be based on incompatible populations.

Procurement correction and receiving comparator admission contend on the same PO lock. If receiving binds first, a business-value correction rejects as referenced. If correction commits first, receiving binds the admitted effective correction source explicitly. Neither outcome rewrites an existing comparator or uses a stale pre-lock snapshot.

## Decision 54 — Effective reconciliation preserves complete raw provenance

Factual reconciliation selects ordinary uncorrected roots and effective CORRECTED heads. It excludes administrative REVERSAL assertions and superseded generations from effective facts, without excluding their raw produced versions from the union used for global Asset-version integrity.

Preserve exactly one raw producer for every produced global version, including all generations' REVERSAL and CORRECTED members. Non-version receipt/procurement corrections, configuration, initial witnesses and Exception events remain outside that Asset union.

All affected ordinary-operation admission, history/interval reconstruction and health queries must consistently use this correction-aware authority after Slice 10 is implemented. Updating only the correction endpoint while leaving other readers to interpret raw reversal rows as physical events is incomplete implementation. Reconciliation remains read-only.

## Decision 55 — Health accepts valid corrections and exposes corruption

A valid complete correction pair and coherent effective projection are normal history, not corruption merely because the raw root was wrong. Health must flag incomplete pairs, duplicate roles, invalid/skipped generations, missing or nonordinary roots, invalid tenancy/context, ambiguous branches, mismatched pair metadata, impossible produced versions and illegal effective domain state.

Also retain existing missing-baseline/witness checks, projection disagreement, raw global-version gaps/duplicates and ahead-of-Asset history checks. Receipt correction evaluations, their source generations, Exception relationships and workflow projections must be internally coherent. A later generation cannot conceal corruption in an earlier raw pair.

Health and reconciliation report discrepancies; they do not delete malformed rows, rewrite history, infer witnesses from projections, choose an arbitrary branch or repair status from itself.

## Decision 56 — Correction APIs are typed and bounded

Provide typed correction operations for transition, movement, assignment and receipt line as named in Handoff v1.3. Include correct_ownership and correct_custody because its Slice 6 physical histories explicitly reserve their full correction workflow for Slice 10. Include the typed procurement PO-line correction required by ADR-009 Decision 26 within Decision 38's eligibility boundary.

Each operation names its class-specific ordinary root, legitimate corrected domain claims, reason and correction occurrence claim. Asset operations require expected_version; non-version operations require expected correction generation. The server assigns row/pair identities, new generation, produced versions, effective head, recording time and Actor. Reject caller attempts to choose those authority fields.

Responses and raw/effective history reads expose enough typed identity, role, generation and attribution to distinguish correction from physical action and reconstruct the pair. Exact route spelling and schema names remain implementation details. There is no unrestricted POST /corrections, generic JSON authority, arbitrary cross-class target, or direct correction endpoint for excluded classes.

## Decision 57 — Exception workflow APIs append events rather than mutate observations

Provide dedicated typed status-event action(s) and the handoff's open-Exception listing by entity. Inputs identify a visible Exception, expected current status, requested permitted status, event-time claim and applicable note. Actor, event ordering and record time are server-owned.

Validate entity and receiving-context relationships through the existing typed authorities. Listing or resolving an Exception cannot mutate its original observation or invent/suppress a receiving classification. A caller cannot attach an arbitrary correction pair to a workflow request; correction-caused resolution linkage is derived inside the validated receipt correction transaction. No direct status PATCH or generic observation-update API is authorized.

## Decision 58 — Reason does not pull evidence storage forward

Correction requires a reason but does not require the Slice 11 attachment subsystem. Existing evidence-ref seams remain inert or restricted as already governed; an unverifiable identifier must not be accepted as evidence.

A correction cannot bypass an existing evidence-gated operation such as retirement. The CORRECTED replacement must satisfy those domain restrictions, so unsupported retirement remains inadmissible until the governed evidence capability exists. This decision creates no upload, attachment storage or evidence-management endpoint.

## Decision 59 — Offline and materials scope stays deferred

No offline correction queue, correction-sync protocol, idempotent capture facility, stock/lot correction, materials ledger, UOM conversion, RMA or logistics workflow is introduced. Existing correlation seams and future Exception vocabulary do not activate those capabilities.

Correction generations are online authoritative admission, not an offline operation ordering scheme. D4/D12 future physical-quantity rules do not authorize negative receipt lines or materials correction in Slice 10. Preserve the current build order and all deferred non-goals.

## Decision 60 — Deterministic movement acceptance

The handoff's exact requirement is:

> Correction test: a mis-keyed movement is corrected; three rows exist (original, reversal, correct); projection equals the correct location; the original row is unchanged.

Use a coherent Asset with pre-root location A, exactly one raw movement root A -> B at current global version N, and no later global producer. The authenticated correction request expects N, supplies a nonblank reason and administrative occurrence claim, and specifies the intended replacement A -> C with its domain occurrence claim.

Generation 1 produces one administrative REVERSAL at N+1 and one CORRECTED A -> C at N+2. Both reference that ordinary root, share pair identity/generation/reason/Actor/administrative occurrence, and commit with current_location_id = C and assets.version = N+2. The original remains byte-identical. The raw movement history has exactly three rows; the effective movement history contains the corrected A -> C. No physical B -> A event is asserted. Global version accounting retains all three producers at their original/new versions.

For repeat-correction proof before any unrelated event, generation 2 consumes the effective CORRECTED head at N+2, appends N+3/N+4 and retains the same root reference. Raw movement history then has five rows; the three-row assertion belongs to the first-generation fixture, not every later audit history.

The other exact handoff acceptance requirements remain:

> Permission test: exceptions rows cannot be UPDATEd by fleetops_app except through the projection function; exception_events cannot be UPDATEd or DELETEd at all.

> Reason-required test: a correction without a reason is rejected.

The permission exception applies only to controlled workflow projections; it never permits editing the receiving observation. Runtime TRUNCATE and the existing stronger immutability/tenancy protections remain prohibited as governed.
