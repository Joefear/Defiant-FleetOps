# ADR-003 — Catalog Identity and External Reference Cardinality

## Status

Accepted

## Context and authority

Slice 3 of the current [Build Handoff v1.2](FleetOps_v0.1_Build_Handoff_v1.2.docx) contains an internal inconsistency. Its `external_references` derivation proposes uniqueness on `(org_id, system, reference_type, external_value)`, while its acceptance requirements say that two items may share a distributor part number. The proposed constraint would reject that required behavior when both items attach the same reference within one organization and external namespace.

This ADR resolves that schema-derivation ambiguity before Slice 3 code exists. Implementation authority remains:

1. Frozen FleetOps Architecture & Boundary document.
2. Accepted Architecture Decision Records (ADRs).
3. Current FleetOps build handoff.
4. Active slice/task prompt.

The frozen [Architecture & Boundary document](FleetOps_Architecture_Boundary_v0.1.docx), with its [working Markdown transcription](FleetOps_Architecture_Boundary_v0.1.md), governs this decision. [ADR-001](ADR-001.md) continues to govern implementation responsibilities, and [ADR-002](ADR-002.md) continues to govern tenancy enforcement and tenant-safe references.

## Decision 1 — FleetOps identity remains internal

FleetOps opaque IDs identify FleetOps entities. Every entity's internal identifier is permanent, never changes, never repeats, and carries no meaning. Under the existing implementation convention, that identifier is a UUIDv7; human-readable display codes remain separate, editable fields.

Manufacturer part numbers, distributor part numbers, ERP item codes, ticket numbers, carrier identifiers, and all other external identifiers remain references. One FleetOps entity may carry many external references from many systems.

An external value never becomes FleetOps primary identity. No external identifier is promoted to a primary key or used as one. These rules preserve D1 and D2.

## Decision 2 — External references may be non-unique across entities

An external reference value may legitimately refer to more than one FleetOps entity. Examples include:

- A distributor part number that does not distinguish manufacturer revision.
- An external catalog grouping multiple internal revisions.
- A legacy external system whose identifier granularity is coarser than FleetOps.

Therefore, `external_references` MUST NOT enforce global uniqueness on:

```text
(org_id, system, reference_type, external_value)
```

For external-reference uniqueness, prevent only duplicate attachment of the same reference to the same FleetOps entity. Use the conceptual constraint:

```sql
UNIQUE (
    org_id,
    entity_type,
    entity_id,
    system,
    reference_type,
    external_value
)
```

A single external reference may therefore map to zero, one, or multiple FleetOps entities. Zero means that a search finds no attachment; it does not permit an attachment to a nonexistent entity.

## Decision 3 — Reverse lookup is not identity resolution

Within the authenticated organization, lookup by `system + reference_type + external_value` is a search operation. It may return zero, one, or multiple FleetOps entities. The API and service must not assume uniqueness or arbitrarily choose one result.

Every returned entity is identified by its FleetOps opaque ID. No operation may mutate or address a FleetOps entity solely on the assumption that an external identifier is unique. The caller must also supply the FleetOps ID or resolve it through an explicit disambiguation step before the operation addresses or mutates the entity.

## Decision 4 — Item catalog uniqueness

Within one FleetOps organization, the following combination uniquely identifies a catalog entry for duplicate-prevention purposes:

```text
(org_id, manufacturer_party_id, manufacturer_part_number, revision)
```

This is a duplicate-prevention constraint, NOT the entity primary key. The opaque FleetOps UUID remains identity; neither the manufacturer part number nor this combination replaces it.

`revision` may be NULL when the manufacturer provides no usable revision. For duplicate prevention, NULL revisions must compare as equivalent. On PostgreSQL 16, use a uniqueness mechanism equivalent to:

```sql
UNIQUE NULLS NOT DISTINCT (
    org_id,
    manufacturer_party_id,
    manufacturer_part_number,
    revision
)
```

Another implementation is permitted only if it has identical semantics. Two rows with the same organization, manufacturer, and manufacturer part number and with `revision` NULL must be rejected as duplicate catalog entries. Different revisions remain distinct items. The same manufacturer part number from different manufacturers is allowed.

## Decision 5 — Manufacturer is a Party, not a vendor

`manufacturer_party_id` references the existing Party model. The referenced party must belong to the same organization and carry the `MANUFACTURER` role. The relationship must be tenant-safe under ADR-002.

A distributor or vendor that sold the part does not become its manufacturer merely because it appears on a purchase record. This preserves D7's manufacturer/vendor distinction. Do not create a separate manufacturer table.

## Decision 6 — Tenancy

`items` and `external_references` are tenant-owned tables and remain subject to all applicable ADR-002 requirements. They require:

- Non-null `org_id` referencing `organizations`.
- PostgreSQL RLS with both `USING` and `WITH CHECK` protection.
- Fail-closed behavior when organization context is missing, with no default tenant authority.
- Transaction-local organization context derived from trusted authenticated server context, preserving pool safety.
- Tenant-safe relationships, including composite organization-scoped foreign keys wherever an ordinary FK applies.
- Adversarial isolation tests whose relevant operations execute as `fleetops_app` against real PostgreSQL 16.
- No `TRUNCATE` privilege for `fleetops_app`.

The polymorphic `(entity_type, entity_id)` target of `external_references` cannot use one ordinary FK to a specific table. The application/service must verify that the target entity exists, belongs to the authenticated organization, and has a supported `entity_type` before attaching the reference. Unsupported types, missing targets, and cross-organization targets must be rejected. Polymorphism does not weaken tenant isolation; reverse searches and attachment/list operations remain within the authenticated organization under RLS.

## Handoff conflict resolution

ADR-003 resolves the Slice 3 Build Handoff v1.2 inconsistency between:

1. The proposed global uniqueness constraint on external reference values, `(org_id, system, reference_type, external_value)`.
2. The acceptance requirement that two items may share a distributor part number.

ADR-003 preserves the acceptance behavior. For Slice 3 implementation, the external-reference uniqueness rule in Decision 2 supersedes the conflicting lower-tier handoff uniqueness tuple.

No other Slice 3 handoff requirement is superseded. The handoff remains the current handoff and is preserved as written; its historical text does not need revision solely for this correction. This explicit, bounded supersession records the resolution before implementation rather than silently choosing a constraint in code.

## Required Slice 3 test implications

Slice 3 must prove all of the following:

1. The same item cannot receive the identical external reference attachment twice.
2. Two different items CAN share the same `org_id`, `system`, `reference_type`, and `external_value`.
3. Reverse lookup of that shared reference returns both FleetOps IDs rather than arbitrarily choosing one.
4. No write API addresses an entity by `external_value` alone as though it were a unique identity; entity operations use the supplied or explicitly disambiguated FleetOps ID.
5. Duplicate catalog entries with the same manufacturer, manufacturer part number, and revision are rejected within one organization.
6. The same manufacturer and manufacturer part number with different revisions are allowed as distinct items.
7. Two NULL-revision rows with the same manufacturer and manufacturer part number are rejected within one organization.
8. The same manufacturer part number from different manufacturers is allowed.
9. `manufacturer_party_id` pointing to another organization, or to a same-organization party without the `MANUFACTURER` role, is rejected.
10. RLS and ADR-002 isolation remain intact for both tables, including missing-context behavior, cross-tenant read/write protection, tenant-safe references, trusted transaction-local context and pool reuse, and absence of `TRUNCATE` privilege. Polymorphic attachment checks reject missing targets, cross-organization targets, and unsupported entity types. Shared-reference searches cannot expose another organization's entities.

The database assertions must use real PostgreSQL 16. Isolation assertions must execute as `fleetops_app` and preserve ADR-002's distinction between rows filtered by `USING` and new rows rejected by `WITH CHECK`.

## Architectural status and scope

ADR-003 is an implementation decision subordinate to the frozen Architecture & Boundary document. It does not amend D1, D2, D7, D13, or D18. It resolves a lower-tier schema-derivation ambiguity before code exists.

Item UOM remains a default only; changing it must not reinterpret historical lines or movements under D13. D18's catalog export-classification fields and controlled flag remain required, with export-control enforcement deferred as specified by the frozen architecture. All other Slice 3 requirements remain in force.

This document records the pre-Slice 3 decision only. It does not begin Slice 3 or introduce production code, migrations, or tests.
