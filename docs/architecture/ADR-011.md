The preceding ADR-011 gate stopped without creating a file. The handoff defines SHORT as "PO line quantity exceeds received quantity across its receipt lines" but does not explicitly distinguish one receipt from several receipt headers. ADR-010 preserves that comparison and requires each Exception to belong to one receipt; it does not uniquely select an accumulation scope. The distinction changes results and cannot be silently chosen in implementation.

The reopened gate explicitly authorizes **receipt-local** scope. This ADR records that bounded decision: the complete comparison population is the lines in one receipt referencing one exact immutable PO-line version. It does not claim the handoff had already selected this scope or that Exception receipt ownership alone logically required it. No explicit higher-tier rule requires historical accumulation across receipt headers. The SHORT/OVER inequalities remain unchanged; this decision specifies their receiving population.

## Decision 1 — Raw UOM facts remain independent

The immutable PO-line `uom` is the expected-UOM snapshot. The receipt-line `uom` is the actual receiving observation. Each quantity remains recorded with the UOM under which it was captured.

Neither fact is normalized into the other. A later Item-default change does not refresh either historical line. The expectation comes from the exact referenced PO-line version, never the current Item default or a dynamically selected successor.

## Decision 2 — No unit conversion in v0.1

FleetOps v0.1 performs no unit conversion. This ADR authorizes no conversion table, canonical base unit, dimensional graph, multiplier/divisor, conversion factor, automatic CM-to-M or G-to-KG conversion, vendor/package conversion, or external conversion service.

Mathematical equivalence is not system authority: knowing that 100 CM physically equals 1 M does not authorize FleetOps to compare converted quantities. Item descriptions, MPNs, revisions, notes, external references, vendor text, and packaging descriptions also supply no hidden conversion authority. The existing governed UOM vocabulary is unchanged.

## Decision 3 — Direct comparability requires exact tokens

Expected and actual quantities are directly comparable only when their exact governed UOM tokens are equal:

```text
expected_uom == actual_uom
```

| Expected | Actual | Directly comparable |
| --- | --- | --- |
| 2 EA | 1 EA | Yes. |
| 1 M | 0.5 M | Yes. |
| 1 M | 100 CM | No. |
| 1 KG | 1000 G | No. |

Do not infer dimensions, aliases, physical equivalence, or a canonical unit. Matching tokens permit arithmetic; token equality alone does not establish quantity equality.

## Decision 4 — UOM_MISMATCH records incomparability

For a PO-backed receipt line, FleetOps derives `UOM_MISMATCH` when its actual UOM differs from its exact comparator's expected UOM. This is the canonical token for amended D5's UOM mismatch category.

It means only that the expected and actual UOM differ and FleetOps lacks governed conversion authority to compare the quantities. It establishes neither equality, SHORT, OVER, SUBSTITUTION, QUANTITY_VARIANCE, nor successful or failed conversion.

For 1 M expected and 100 CM observed, preserve both facts and record UOM_MISMATCH. Never compare the raw numbers 1 and 100 as though their units agreed. An unexpected line with no PO comparator has no expected UOM for this rule; its UNEXPECTED_ITEM meaning remains under ADR-010.

## Decision 5 — UOM_MISMATCH has typed relationships

UOM_MISMATCH is a first-class immutable receiving Exception under ADR-010, with this shape:

| Relationship | Requirement |
| --- | --- |
| `receipt_id` | Required: the receipt containing the observation. |
| `receipt_line_id` | Required: the incompatible actual receipt line. |
| `po_line_id` | Required: the exact immutable expectation-version UUID referenced by that line. |
| `asset_id` | Optional where naturally associated with an actual serialized unit in that receiving reality. |

The receipt line must belong to the referenced receipt, and its comparator must be the referenced PO line. Any Asset must belong to that same receiving reality. All references must satisfy Decision 29.

The authoritative actual and expected UOM remain on the receipt line and immutable PO line. Do not add duplicate authoritative UOM columns to the Exception merely for convenience. Any later snapshot need requires explicit justification without replacing the source facts.

Each applicable incompatible receipt line yields its own meaningful UOM disagreement under ADR-010. An optional Asset association does not authorize duplicating the same line's UOM disagreement once per unit. Independently true Item or condition disagreements remain separate rows.

## Decision 6 — The server derives classification

The caller supplies actual Item, quantity, UOM, and other permitted receiving observations. FleetOps validates the exact comparator and mechanically derives UOM_MISMATCH when the tokens differ.

A caller cannot choose an arbitrary exception type, suppress the mismatch, assert comparability, or replace the derived result with SHORT, OVER, or another classification. The observation is business input; discrepancy classification is server responsibility.

## Decision 7 — Quantity reconciliation is receipt-local

SHORT, OVER, and quantity equality are evaluated within **one receipt and one exact immutable PO-line comparator**.

For authenticated organization O, receipt R, and comparator L, the comparison set is:

```text
S(R, L) = all receipt_lines in O satisfying:
    receipt_line.receipt_id = R.id
    AND receipt_line.po_line_id = L.id
```

Earlier and later receipts are excluded even when they reference L. Lines referencing any other PO-line UUID are excluded even when their Item, UOM, PO, or business line number matches.

This is the bounded Slice 9 meaning of cumulative quantity "across its receipt lines": accumulation across S(R, L), not across receipt headers. An HTTP request or batch boundary is not a replacement for receipt identity. The handoff's ability to capture a delivery in one call or line by line does not authorize either cross-receipt accumulation or changing the comparison population to only the current request payload.

## Decision 8 — Exceptions describe their receipt event

ADR-010 Decision 10 requires every Slice 9 Exception to belong to exactly one receipt. Receipt-local SHORT/OVER fit that model: they describe the disagreement between the physical receiving event represented by R and the immutable expectation L.

The receipt reference identifies the observation's context; the exact PO-line reference identifies its expectation. This ADR expressly chooses receipt-local scope within those relationships. It does not turn the Exception into a mutable measure of eventual supplier fulfillment.

A later receipt does not rewrite, cancel, resolve, or reinterpret an earlier immutable receiving Exception.

## Decision 9 — No cross-receipt fulfillment state

Slice 9 introduces no cumulative PO-fulfillment balance, remaining-to-receive projection, open quantity, supplier-delivery completion state, shipment schedule, or partial-delivery authorization model.

Do not subtract earlier receipts from L's expected quantity before comparing R. Each receipt uses that comparator's full immutable expected quantity. A receipt-local SHORT is not a claim that the supplier will never complete the order; equality is not a claim that the PO is finally fulfilled.

## Decision 10 — Same-receipt SHORT

For R and L, when every line in S(R, L) is directly comparable and their quantity total is below L's expected quantity, derive SHORT for that receipt/comparator:

```text
sum(actual_quantity in S(R, L)) < L.quantity
```

Example: 2 EA expected and 1 EA received in R1 yields SHORT on R1. No earlier receipt reduces the expectation or contributes to this total.

Preserve ADR-010's SHORT shape: required receipt and exact PO-line references, NULL `receipt_line_id`, and no fabricated missing-unit Asset. Where the receiving comparison includes an expectation for which none arrived, the empty received set contributes zero; the existing ADR-010 requirement for SHORT without an actual receipt line still applies. This does not invent a receipt line, unit, or separate quantity ledger.

## Decision 11 — Same-receipt OVER

For R and L, when every line in S(R, L) is directly comparable and their total exceeds L's expected quantity, derive OVER for that receipt/comparator:

```text
sum(actual_quantity in S(R, L)) > L.quantity
```

Example: 2 EA expected and 3 EA received in R1 yields OVER on R1. The expected quantity remains unchanged. This is a comparison with R1's actual total, not with the supplier's deliveries across all receipts.

## Decision 12 — Same-receipt equality

When every line in S(R, L) is directly comparable and its total equals L's expected quantity, derive neither SHORT nor OVER solely from quantity.

Other independently true exceptions may still exist. Equality is a quantity conclusion for this receipt/comparator, not a new exception type or PO-completion state. A comparable subtotal cannot establish equality when any incompatible line belongs to S(R, L).

## Decision 13 — Later receipts are independent

For one unchanged comparator expecting 10 EA:

| Receipt | Actual quantity | Result |
| --- | --- | --- |
| R1 | 8 EA | SHORT on R1. |
| R2 | 4 EA | SHORT on R2. |

R2 is not OVER from 8 + 4 = 12. R2 is compared with 10 EA, not with a computed remaining quantity of 2 EA. The SHORT on R1 remains an immutable statement about R1.

Later receipt creation neither updates prior Exceptions nor combines them into a current fulfillment projection. Independence applies in both directions: an earlier receipt cannot change the later receipt's population, and a later receipt cannot change the earlier receipt's history.

## Decision 14 — Mixed UOM blocks a complete local quantity conclusion

Within S(R, L), only lines whose actual UOM exactly equals L's UOM can enter a numeric subtotal. If **any** line in that same set has a different UOM:

1. Derive UOM_MISMATCH for each applicable incompatible line.
2. Preserve its raw quantity and UOM without conversion.
3. Do not derive SHORT, OVER, or quantity equality for R/L from the comparable subset.

For 10 M expected and lines of 4 M plus 300 CM in R1, the comparable subtotal is 4 M. The 300 CM line yields UOM_MISMATCH. FleetOps cannot conclude SHORT, OVER, or equality for R1/L.

An incompatible quantity is neither zero nor an additional number in the expected UOM. The block also applies when the comparable subtotal alone equals or exceeds the expectation: this gate requires a completely comparable population for the overall quantity conclusion. It does not block comparison for another comparator in the same receipt.

## Decision 15 — Incompatibility does not cross receipts

An incompatible line in R1 does not block numeric reconciliation in R2.

For one comparator expecting 10 M:

| Receipt | Actual quantity | Result |
| --- | --- | --- |
| R1 | 300 CM | UOM_MISMATCH; no SHORT, OVER, or equality. |
| R2 | 8 M | SHORT on R2. |

R1 remains historically incomparable. R2 is fully comparable within its own set and is evaluated normally. No perpetual comparator-wide mismatch flag or cross-receipt suppression state is introduced.

## Decision 16 — Same-receipt multi-line aggregation

When all lines in S(R, L) match the expected UOM token, sum their quantities normally. For 10 EA expected and lines of 4 EA and 5 EA in the same receipt against L, the total is 9 EA and yields SHORT.

Aggregation groups by the receipt and exact comparator, not by request, actual Item, Asset count, business line number, or UOM token alone. An Item substitution remains independently classified under Decision 20; it does not silently remove a linked, same-UOM actual quantity from the comparison.

## Decision 17 — Comparator versions never aggregate

Receipt-local scope also remains bounded to the exact immutable `purchase_order_lines.id` selected under ADR-010. Never combine predecessor and successor versions or different immutable versions sharing `line_number`.

Each R/L pair is independently reconciled. This grouping rule does not authorize receiving against a stale predecessor: ADR-010 still requires explicit targeting and same-organization, same-PO, ISSUED active-leaf admission under the shared PO lock. Grouping history by exact UUID cannot bypass that admission boundary.

## Decision 18 — Later supersession preserves the old comparison

If a receipt was committed against L1, a later L2 superseding L1 does not retarget that receipt, change its expected UOM, recompute its quantity exceptions, rewrite its UOM_MISMATCH, or merge receipt histories.

L1 remains the authoritative expected snapshot for that historical comparison. L2's Item default, UOM, quantity, and lineage position do not reinterpret L1. No automatic historical reclassification follows procurement supersession.

## Decision 19 — QUANTITY_VARIANCE remains packing-specific

Preserve the exact handoff meaning: receipt-line quantity disagrees with the packing-reference count.

QUANTITY_VARIANCE is independent of expected-versus-actual UOM comparability. It is not a substitute for SHORT, OVER, UOM_MISMATCH, arbitrary PO quantity disagreement, or cross-receipt fulfillment variance. A mismatch does not by itself establish packing-count disagreement; an independently supported packing disagreement is not suppressed by a mismatch.

## Decision 20 — SUBSTITUTION remains Item disagreement

SUBSTITUTION means a receipt line linked to a PO line carries a different Item. UOM difference alone does not imply substitution.

Expected Item A / M and actual Item B / CM can independently yield SUBSTITUTION and UOM_MISMATCH. Expected and actual Item differences and UOM differences are separate facts; neither classification suppresses the other when both are true. Actual Item remains authoritative for any created Asset.

## Decision 21 — Other exception meanings remain orthogonal

DAMAGED, OPENED, SERIAL_UNREADABLE, and SERIAL_MISMATCH retain their existing meanings. UOM_MISMATCH does not suppress or replace an independently true condition. ADR-010's one-row-per-meaningful-disagreement rule remains binding.

This does not bypass existing admission or identifier uniqueness. In particular, ADR-010's atomic failure for a conflicting required readable identifier is unchanged; this ADR grants no new way to commit an invalid or incomplete serialized-unit bundle.

## Decision 22 — Packing counts are separate facts

Packing quantities do not authorize engineering-unit conversion. Do not infer box-to-EA, reel-to-EA, or container-to-KG relationships.

Two boxes do not establish 2 EA; one reel does not establish 5,000 EA. Preserve supported packing-count observations separately from engineering quantity and UOM. QUANTITY_VARIANCE retains its packing-specific meaning without a packaging model, new packaging tokens, or units-per-package authority.

## Decision 23 — No caller conversion inputs

Receiving requests must reject reconciliation-authority fields such as:

- `conversion_factor`
- `normalized_quantity`
- `equivalent_quantity`
- `canonical_uom`
- `normalized_uom`
- `units_per_package`

Do not accept these as overrides, silently apply them, or reinterpret equivalent metadata as conversion instructions. Existing request models inherit `InputModel` with `extra="forbid"`; strict receiving models must retain that rejection convention and expose no conversion inputs. Exact endpoint and model layout remain Slice 9 implementation work.

## Decision 24 — Reality capture continues

A different UOM does not invalidate otherwise valid physical receiving reality. Capture actual Item, actual quantity, actual UOM, exact comparator, and the derived UOM_MISMATCH.

All other receiving admission rules still apply, including governed UOM vocabulary, valid quantity and relationships, credentials, exact-comparator authority, and serialized creation requirements. UOM incomparability alone must not force rejection or falsification of the observed facts.

## Decision 25 — Asset creation follows physical units

One actually observed serialized physical unit creates one Asset when all receiving admission requirements are met. Do not create fractional Assets or infer Asset count from quantity conversion.

UOM mismatch alone does not suppress a valid physical unit. ADR-010's complete creation bundle remains atomic: actual serialized Item, RECEIVED/version 1 Asset, initial lifecycle transition, physical baseline, initial-unassigned witness, identifiers, receipt provenance, and applicable Exceptions. Preserve explicit owner, optional custodian, required dock, and credential-derived Actor authority. Nonserialized reality still creates no Asset or inventory balance in v0.1.

## Decision 26 — Reconciliation never mutates the PO

UOM or quantity reconciliation never changes the PO, expected quantity, expected UOM, Item, unit price, expected date, line number, attribution, or supersession lineage.

The exact expectation remains immutable. A discrepancy is represented as an Exception, never by procurement mutation, creation of a fake expected line, or retargeting a receipt to make it agree.

## Decision 27 — Receipt observations are not normalized

Do not rewrite actual receipt UOM or quantity into expected units. Do not persist a normalized quantity as though it were physically observed.

The raw captured quantity, UOM, actual Item, and exact comparator remain historical receiving truth. Later Item changes, procurement amendments, other receipts, or human knowledge of conversion factors cannot rewrite that observation.

## Decision 28 — Exceptions remain immutable observations

UOM_MISMATCH, SHORT, and OVER follow ADR-010's receiving Exception immutability. Ordinary runtime cannot UPDATE, DELETE, or TRUNCATE them. This ADR introduces no mutable resolution state or automatic cancellation of historical Exceptions.

A later receipt does not resolve or delete an earlier receipt's Exception, even if a person could calculate an eventual supplier total outside FleetOps. Corrections and exception-resolution workflows remain Slice 10 under the existing correction doctrine; this ADR does not implement or redesign them.

## Decision 29 — Tenancy and Actor remain mandatory

Receipt, receipt line, exact PO-line comparator, and optional Asset must belong to the authenticated organization and a coherent receiving context. Same-tenant but unrelated references are insufficient.

Preserve ADR-002 tenant-safe foreign keys where applicable, durable relationship enforcement, fail-closed RLS with USING and WITH CHECK, and explicit tenant checks at any elevated boundary. API-only validation does not establish durable relationship safety.

Exception attribution uses the same credential-derived receiving Actor as its receipt operation under ADR-006. No caller-selected Actor, organization-only authority, separate exception authority, or alternate machine credential mechanism is introduced. Required observation/occurrence time and server-set recording time remain separate facts under D11 and ADR-010.

## Decision 30 — The frozen acceptance result is unchanged

The Section 9 fixture uses directly comparable unit-count UOM, with matching EA tokens a compatible fixture choice. The architecture does not freeze literal token spelling for the scenario; the fixture must ensure valid direct quantity comparisons without conversion.

The delivery still yields exactly:

1. One SUBSTITUTION.
2. One SERIAL_UNREADABLE.
3. One SHORT.
4. One UNEXPECTED_ITEM.

It creates exactly nine Assets: six workstations, one scanner, one printer, and one network appliance. The unexpected accessory remains a nonserialized receipt line with no Asset and no inventory balance. The absent scanner creates no fictional unit.

No UOM_MISMATCH is introduced into this fixture. Preserve the handoff's full-delivery or line-by-line capture requirement and ADR-010's exact-four cardinality without double-counting intermediate capture. Exact API/transaction mechanics belong to Slice 9; they must satisfy these existing requirements without weakening immutability or changing the receipt-local population.

## Decision 31 — Future fulfillment and conversion require governance

Cross-receipt PO fulfillment, remaining/open quantity, supplier completion, shipment schedules, and partial-delivery authorization require separate explicit governance if later needed. They are not inferred from receipt-local Exceptions.

Unit conversion likewise requires separate decisions for dimensions, allowed unit pairs, factors, provenance, factor versions, precision, rounding, effective dates, packaging, and historical reproducibility. No such capability or authority is introduced here.

Evidence storage, labels, offline/idempotent capture, corrections, integrations, and the materials ledger remain in their governed later slices or versions. This design gate does not reopen any of them.

## Bounded handoff refinement

For Slice 9, this ADR records exactly these refinements:

1. Arithmetic requires exact-token expected/actual UOM equality.
2. Differing UOM on a PO-backed receipt line derives UOM_MISMATCH.
3. No conversion occurs.
4. SHORT, OVER, and quantity equality are receipt-local.
5. The population is all lines in the same receipt referencing the same exact immutable PO-line comparator.
6. Earlier and later receipts are excluded.
7. Mixed UOM within that receipt/comparator prevents SHORT, OVER, and equality conclusions.
8. Incompatible UOM in another receipt does not block this receipt.
9. Exact comparator UUID remains the version boundary.
10. Frozen Section 9 acceptance remains unchanged.

SHORT still means expected quantity exceeds received quantity; OVER still means received exceeds ordered. This ADR specifies which receiving population supplies that quantity. It neither changes those inequalities nor introduces remaining-quantity arithmetic. QUANTITY_VARIANCE and the other existing exception meanings are preserved.

ADR-010's nine existing handoff classifications remain; amended D5 authorizes the additional UOM_MISMATCH category. This is not authority to add other exception categories. No architecture, earlier ADR, or handoff file is edited, and no Handoff v1.4 is created in this gate.

## Database and API consequences

Slice 9 must store actual UOM on the receipt line and obtain expected UOM from the exact immutable PO-line comparator. Python retains receiving orchestration and mechanical exception derivation under ADR-001; PostgreSQL retains durable invariants, tenancy, attribution, and justified atomic boundaries. This ADR grants no blanket SECURITY DEFINER authority.

The local quantity rule can be expressed without conversion or a fulfillment projection:

```text
S = receipt lines for the authenticated tenant, receipt R, and exact comparator L
incompatible = lines in S whose uom differs from L.uom

derive UOM_MISMATCH for each applicable incompatible line
if incompatible is nonempty:
    make no SHORT / OVER / equality conclusion for R and L
otherwise:
    compare the sum of S.quantity with L.quantity
```

This describes semantics, not a selected SQL function, endpoint, storage projection, or capture-finalization protocol. Implementation must preserve the complete receipt population, atomic receiving obligations, exact exception cardinality, and comparator admission; an HTTP payload is not the cumulative set.

Existing seams support the decision: `UnitOfMeasure` already contains exact governed tokens; procurement snapshots `items.uom` into each line; the existing PO lock serializes expectation authoring and supersession; strict `InputModel` rejects extra fields. Receipt schema, query/index choices, transaction sequencing, and runtime proofs remain the separately opened Slice 9 implementation.
