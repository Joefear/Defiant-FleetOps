# ADR-005 — Global Asset Version Semantics Across Orthogonal History

## Status

Accepted

## Context and authority

[ADR-004](ADR-004.md) introduces `result_version` for deterministic state-transition ordering and fixes initial Asset history semantics. Its Decision 4 also requires permanent equality between `assets.version` and the latest state transition's `result_version`, and its Decision 5 requires that latest transition version to equal `expected_version` before admitting a normal state transition.

Those equality requirements work only while state transitions are the sole operation class that increments `assets.version`. The current [Build Handoff v1.2](FleetOps_v0.1_Build_Handoff_v1.2.docx) requires Slice 6 movement, custody, and ownership functions and Slice 7 assignment/unassignment functions to increment the same Asset version. Under D8, those operations are orthogonal to lifecycle state and do not create `asset_transitions` rows. A global Asset version and the state-transition history therefore cannot be treated as the same contiguous sequence.

This ADR resolves that cross-slice implementation conflict before Slice 5 schema exists. Implementation authority remains:

1. Frozen FleetOps Architecture & Boundary document.
2. Accepted Architecture Decision Records (ADRs).
3. Current FleetOps build handoff.
4. Active slice/task prompt.

The frozen [Architecture & Boundary document](FleetOps_Architecture_Boundary_v0.1.docx), with its [working Markdown transcription](FleetOps_Architecture_Boundary_v0.1.md), governs this decision. [ADR-001](ADR-001.md) retains layer responsibilities, [ADR-002](ADR-002.md) retains tenancy and tenant-safe reference requirements, and [ADR-003](ADR-003.md) retains catalog identity and external-reference rules.

ADR-005 explicitly and narrowly supersedes only the two incompatible asset-version assumptions in ADR-004 identified below. ADR-004 remains preserved as written. This document-only corrective design gate does not begin Slice 5 or authorize production code, tests, migrations, or changes to the frozen architecture or Build Handoff v1.2.

## Decision 1 — Asset.version is the global operational version

`assets.version` is the optimistic-concurrency version for the Asset as a whole. Every versioned consequential Asset operation shares it, including these operation classes when introduced:

- State transition.
- Location movement.
- Custody change.
- Ownership change.
- Assignment and unassignment.

A successful versioned operation consumes `expected_version = N` and produces `assets.version = N + 1`. Two competing operations that both expect N cannot both succeed, including operations from different classes.

## Decision 2 — One shared row-lock protocol

Every database function performing a versioned Asset operation MUST use the same concurrency protocol:

1. Resolve trusted organization context under ADR-002.
2. Identify the target Asset within that organization.
3. Acquire a PostgreSQL row lock on that Asset, using semantics equivalent to `SELECT ... FROM fleetops.assets WHERE ... FOR UPDATE`, with the target identified by its FleetOps ID and trusted organization.
4. Only after the row lock is held, read and validate the locked `assets.version` against `expected_version`.
5. Validate the operation's authoritative history and other preconditions.
6. Append the operation's immutable history row.
7. Update the relevant maintained projection or projections.
8. Set `assets.version = expected_version + 1`.
9. Commit the history and projection changes atomically in the same transaction, retaining the Asset row lock through completion.

No versioned operation may read a version, decide that it matches, and acquire the Asset lock afterward. The version comparison is a post-lock check; an earlier service read cannot satisfy it.

This protocol applies to Slice 5, Slice 6, Slice 7, and every later versioned Asset operation. It does not replace authoritative-history validation or ADR-002's explicit tenant checks for SECURITY DEFINER functions. The projection remains a concurrency aid and may never be the sole basis for admitting authoritative history under D3.

## Decision 3 — The row lock serializes cross-class version production

The Asset row lock is the durable concurrency boundary shared across operation classes. For example, a state transition and a movement both expect version 7 and attempt to lock the same Asset row.

One obtains the lock first, validates version 7, writes its history, and produces version 8. The second obtains the lock afterward, observes version 8, and rejects its stale `expected_version = 7`. The rejected operation produces no history or projection changes.

Two different operation classes therefore cannot legitimately produce the same global Asset version. The lock and the version check protect one shared sequence even though the resulting history rows reside in different tables.

## Decision 4 — No shared Asset version register

Do not create an `asset_version_log`, `asset_version_register`, `asset_event_sequence`, `global_asset_event` table, or equivalent separate register solely to enforce cross-history `result_version` uniqueness.

One PostgreSQL UNIQUE constraint cannot span several history tables. A separate table is nevertheless unnecessary for concurrency correctness because every successful versioned operation:

- Holds the same Asset row lock.
- Advances from N to N + 1 exactly once.
- Records N + 1 in the immutable history row belonging to its operation class.

The shared protocol prevents legitimate duplicate global result versions. A separate register would duplicate version bookkeeping already represented by the maintained `assets.version` and the authoritative immutable history rows. This does not make the projection an independent history authority.

Do not build a separate version register without a later demonstrated requirement and explicit design decision. Future reconciliation must remain able to detect inconsistent history or projections without treating a register as necessary for normal concurrency enforcement.

## Decision 5 — State is orthogonal to other versioned facts

Movement, ownership, custody, and assignment may increment `assets.version` without changing lifecycle state. Consequently:

```text
latest asset_transitions.result_version < assets.version
```

may be valid and is not, by itself, corruption. If a state transition produces version 2 and a movement produces version 3, the latest state-transition result version remains 2 while the Asset version is 3. That is consistent with D8.

## Decision 6 — Result version is the global version produced by that event

For `asset_transitions`, `result_version` records the global Asset version produced by that particular state transition. It is not a contiguous state-transition sequence. Gaps are valid when other versioned operation classes occupy intervening versions.

| Operation | Global result version | State-transition result version |
| --- | --- | --- |
| Initial RECEIVED transition | 1 | 1 |
| State transition | 2 | 2 |
| Movement | 3 | No state-transition row |
| Assignment | 4 | No state-transition row |
| State transition | 5 | 5 |

The state-transition result versions in this example are `1, 2, 5`. No synthetic lifecycle transitions fill the movement or assignment gaps.

## Decision 7 — Initial transition remains unchanged

ADR-004 initialization remains:

```text
Asset:
    version = 1
    current_state = RECEIVED

Initial transition:
    result_version = 1
    from_state = NULL
    to_state = RECEIVED
```

There is no version 0 authoritative Asset state. The coherent initial pair, its atomic creation by the future receiving workflow, and controlled Slice 5 fixtures remain governed by ADR-004. Initial-transition checks still require NULL to RECEIVED at result version 1 and prohibit NULL `from_state` on later transitions.

## Decision 8 — Transition result-version uniqueness and ordering

Preserve ADR-004's positive, non-null `result_version` and the database constraint:

```sql
UNIQUE (org_id, asset_id, result_version)
```

Within `asset_transitions`, `MAX(result_version)` identifies the authoritative latest STATE transition for an Asset in its organization. Because global Asset version increases monotonically, each later state transition has a higher result version than every earlier state transition, even when intervening versions belong to other operation classes.

Do not create a separate `transition_seq`. Neither `occurred_at`, `recorded_at`, nor UUID ordering replaces result-version ordering of authoritative state history.

## Decision 9 — Normal state-transition preconditions

For `transition_asset` with `expected_version = N`, the concurrency boundary comes first: identify the tenant-scoped target and acquire its Asset row lock. Only after that lock is held may the function validate the expected version.

The atomic function then verifies all of the following:

1. The target Asset belongs to the trusted organization.
2. The locked `assets.version == N`.
3. The authoritative latest Asset transition exists.
4. That latest transition's `result_version <= N`.
5. That latest transition's `to_state` equals the requested `from_state`.
6. `assets.current_state` equals that authoritative latest transition's `to_state`.

The function MUST NOT require `latest transition.result_version == N`. Intervening orthogonal operations may have incremented the global version without changing state.

If the latest transition's `result_version > assets.version`, reject as inconsistent. Missing history, a stale expected version, a wrong from-state, or a corrupted state projection also rejects with no writes. These conditions do not remove other governing preconditions, including authenticated attribution, tenant-safe references, evidence restrictions, and Python lifecycle-graph validation.

## Decision 10 — Successful state transition

On a successful state transition with `expected_version = N`, the operation writes:

```text
new asset transition.result_version = N + 1
assets.current_state = requested to_state
assets.version = N + 1
```

The transition insert and projection updates occur atomically under the Asset row lock. A state transition changes no location, owner, custodian, or assignment projection. Equality between the newly inserted transition's result version and Asset version holds at the successful transition's completion; a later orthogonal operation may then advance the Asset version.

## Decision 11 — State reconciliation

Permanent state reconciliation requires:

```text
assets.current_state == latest asset transition.to_state
```

Missing transition history is a discrepancy. Reconciliation also reports impossible version direction, including `latest transition.result_version > assets.version`; transition admission rejects that inconsistency.

State reconciliation must not permanently require `assets.version == latest transition.result_version`. A lower latest state-transition version is not alone a discrepancy because other operation classes may legitimately have advanced the global version.

During Slice 5, before other versioned operation classes exist, equality naturally holds for coherent Assets and may be asserted as a Slice-5-local proof. It is not a permanent cross-slice invariant or a permanent transition-admission precondition. A valid gap does not excuse a state mismatch or missing history, and agreement on state does not by itself prove the global version complete.

## Decision 12 — Future history tables record the produced global version

When Slices 6 and 7 introduce versioned Asset history operations, the immutable history row created by each successful operation must record the global Asset version that operation produced, using `result_version` or equivalent terminology.

Examples include `asset_movements.result_version`, `asset_custody_changes.result_version`, `asset_ownership_changes.result_version`, and assignment/unassignment result-version provenance. Exact schemas, including the representation of assignment and unassignment history, remain owned by those slices.

No Slice 6 or Slice 7 history tables are introduced by this gate or pulled into Slice 5.

## Decision 13 — Future global version reconciliation

Once multiple version-producing Asset history classes exist, global version reconciliation must reason across ALL of them. It should be able to prove conceptually that, for one Asset, every global version from 1 through `assets.version` is represented exactly once by the operation that produced it.

That may be implemented by a tenant-scoped UNION/query across version-producing history classes or another equally auditable method. The eventual check must be able to distinguish valid gaps within one history class from missing or duplicate versions across the combined history.

Do not implement that union in Slice 5, when only state-transition history exists. Do not create a shared version-register table merely to simplify the future query. State reconciliation and global version reconciliation answer separate questions; exact implementation of the latter belongs to the slices introducing the additional history classes.

## Decision 14 — ON_HOLD ordering

The ON_HOLD previous-state behavior preserved by ADR-004 and defined in Build Handoff v1.2 Section 3 — v0.1 Asset Lifecycle remains valid. Previous lifecycle state is found from authoritative state-transition history ordered by `result_version`.

Gaps caused by movement, ownership, custody, or assignment do not affect that ordering. For example:

```text
READY state transition: result_version 5
movement: global result_version 6
ON_HOLD state transition: result_version 7
```

The prior lifecycle state is READY. Looking for a state-transition row at global version 6 would be incorrect; that version belongs to movement. ON_HOLD does not implicitly change location, ownership, custody, or assignment.

## Decision 15 — Cross-class concurrency

Asset version is deliberately shared so all versioned operation classes compete on the same optimistic-concurrency token and the same Asset row lock. No independent `state_version`, `location_version`, `custody_version`, `ownership_version`, or `assignment_version` is introduced in v0.1.

A stale operation must re-read current Asset facts before deciding whether a retry remains valid. It must not bypass the conflict by using a separate per-class token or applying last-writer-wins behavior.

## Bounded supersession of ADR-004

ADR-005 supersedes only these ADR-004 implications:

1. **Permanent equality with latest state-transition version:** ADR-004 Decision 4's requirement that `assets.version == latest transition.result_version` is replaced by Decision 11 above. State equality, missing-history detection, and rejection/reporting of a latest transition version greater than the Asset version remain permanent requirements. Asset/latest-transition version equality remains valid as a Slice-5-local proof and immediately after a successful state transition.
2. **Equality as a transition precondition:** ADR-004 Decision 5's requirement that `latest transition.result_version == expected_version` is replaced by Decision 9 above. The locked Asset version must equal the expected version, while the latest authoritative state-transition result version must be less than or equal to it.

This bounded correction also governs repetitions or implications of those two equality assumptions in ADR-004's handoff-refinement and test-implication sections, including its version/result-version mismatch wording. It does not discard the unaffected tests or weaken history-verified state admission.

ADR-004 remains governing for:

- Initial Asset version 1 / RECEIVED and no version 0 authoritative state.
- Positive, non-null `result_version`, per-history uniqueness, and authoritative state-transition ordering.
- Initial NULL to RECEIVED transition and later non-null from-state checks.
- The `evidence_ref` function seam.
- The Slice 5 NULL-only evidence rule.
- Retirement remaining fail-closed until disposal evidence is verifiable.
- Serialized-Item Asset eligibility.
- Descriptive-update attribution.
- Receiving-owned production Asset creation and the prohibition on manual onboarding.
- Slice 4 Location reparenting deferral.

The lifecycle graph, immutable-history permissions, projection-write restrictions, atomic N to N + 1 transition result, authenticated attribution, tenant boundaries, and all other unaffected ADR-004 requirements remain in force. ADR-004 is not rewritten, and this ADR does not amend the frozen architecture or Build Handoff v1.2.

## Required Slice 5 test implications

These requirements belong to future Slice 5 implementation. This document-only gate introduces no tests and claims no implementation test result. Slice 5 must prove:

1. Initial Asset version and initial transition result version both equal 1.
2. A successful transition expecting N produces transition `result_version = N + 1` and `assets.version = N + 1` atomically.
3. `transition_asset` acquires and holds the Asset row lock before evaluating the version precondition.
4. Two concurrent transition calls with the same expected version have exactly one winner.
5. During Slice 5, with no other versioned operation classes yet, Asset version naturally equals the latest transition result version for coherent history.
6. Transition logic does not encode that equality as a permanent contract; it permits the authoritative latest transition version to be less than the locked Asset version when the other preconditions hold.
7. The latest state transition is selected by `MAX(result_version)` within the organization and Asset.
8. `occurred_at` cannot reorder authoritative state history.
9. Reconciliation detects `current_state != latest transition.to_state`.
10. Reconciliation detects `latest transition.result_version > assets.version`.
11. Missing transition history is a discrepancy.
12. No `transition_seq` is introduced solely to make state transitions contiguous.
13. No Asset version log, register, sequence table, or global event table is introduced for shared version bookkeeping.
14. No Slice 6 or Slice 7 history tables are created.

All unaffected Slice 5 acceptance requirements and prior invariant tests remain mandatory. Database and concurrency proofs use real PostgreSQL 16; isolation assertions retain ADR-002's runtime-role and adversarial requirements. Do not weaken tests to make implementation pass.

## Future Slice 6 and Slice 7 review requirements

Future Slice 6 and Slice 7 prompts must explicitly require:

- The same Asset `SELECT ... FOR UPDATE` protocol.
- Version comparison only after lock acquisition.
- One immutable history row carrying the global version produced by each successful versioned operation.
- Atomic history, relevant projection, and `assets.version` updates under that lock.
- Concurrency tests across operation classes, proving two operations expecting the same version cannot both succeed or produce duplicate global result versions.

A future reviewer must BLOCK a new versioned Asset function that uses a different locking protocol. These are obligations for those future slices, not authorization to implement them now.

## Architecture consistency and scope

ADR-005 preserves:

- **D3:** History remains authoritative, projections are maintained atomically, and the locked version check does not substitute for authoritative-history validation.
- **D8:** Lifecycle state remains orthogonal to location, ownership, custody, and assignment; version changes do not require invented state transitions.
- **D12:** Version mismatches reject consequential state/location changes, with no last-writer-wins path or separate per-class concurrency tokens.
- **D10:** Authenticated Actor attribution remains unchanged.
- **D11:** Event time and record time remain distinct; neither supplies authoritative state-transition order.
- **D18:** Trusted organization context, tenant-safe relationships, and tenant boundaries remain unchanged.

No frozen architecture section is amended. This ADR records the corrective design decision only. It creates no production capability, starts no Slice 5 implementation, and changes no production code, tests, migrations, prior ADRs, or handoff. A collision with a controlled architectural section requires STOP and an Architecture Amendment Request, not a workaround in implementation.
