## Part I — Expectation version at receipt

### Decision 1 — Receiving references an exact PO-line version

A PO-backed receipt line permanently references the exact immutable `purchase_order_lines.id` used as its expectation comparator. That opaque FleetOps UUID identifies one line version.

Persisting only `line_number`, a current-active lookup, a dynamically resolved lineage, or an external ERP/vendor line identifier is insufficient. Receipt history must answer which exact expectation version was compared, including after later procurement amendments.

### Decision 2 — Caller selects the exact version; server validates authority

The PO-backed receiving request identifies the exact PO-line version UUID being received against. The UUID is a target, not an assertion of authority.

FleetOps independently validates that the selected version belongs to the authenticated organization and the receipt's PO, is an ISSUED expectation, and is the active leaf of its ADR-009 lineage at admission. The caller cannot authorize receiving against an obsolete predecessor by supplying its UUID.

### Decision 3 — Stale expectation fails closed

Receiving against an already-superseded selected version rejects as stale. It writes no partial receiving result. The caller/operator must retry against the intended current expectation.

The server must not silently select the new leaf, compare against one version while persisting another, dynamically rewrite the comparator, or mutate the PO. This preserves the caller's explicit target and the historical expectation actually admitted.

### Decision 4 — Comparator validation and supersession share the PO lock

Receiving uses the same tenant-scoped purchase-order row as procurement's serialization boundary. Conceptual admission is:

1. Authenticate Actor and organization through the established credential boundary.
2. Identify the receipt's PO within that organization.
3. Acquire its row lock in a mode sufficient to serialize with procurement supersession.
4. Load the selected line version under the retained lock.
5. Validate the same-organization and same-PO relationships and ISSUED expectation.
6. Verify from the authoritative lineage that the selected version is still active.
7. Persist that exact UUID with the receiving reality and required transaction bundle.
8. Commit, retaining the lock until transaction completion.

The exact lock mode and statement implementation belong to Slice 9. The established `FOR NO KEY UPDATE` procurement boundary demonstrates the available seam; this ADR does not rewrite it. An unlocked earlier read cannot satisfy admission. Waiting for the PO lock must not permit a stale pre-lock view to authorize receiving after a committed supersession.

### Decision 5 — Concurrent supersession versus receiving

When supersession and receiving contend on the same PO lineage, one transaction establishes its authoritative state first:

- If supersession commits first, receiving against the predecessor observes the successor after acquiring the lock and rejects stale.
- If receiving validates and commits first, its receipt permanently references that then-active version. A subsequent amendment preserves that historical reference.

Implementation must prove actual transaction blocking and lock retention, not merely sequential outcomes. No PO-wide version counter, procurement event register, or separate lineage authority is introduced.

### Decision 6 — Line number is not receipt comparator identity

`line_number` groups versions of a logical procurement line. It does not identify the version compared at receipt. Receipt relationships use the opaque line-version UUID; timestamps and UUID ordering do not substitute for ADR-009 lineage authority.

## Part II — Receiving exception model

### Decision 7 — Exceptions are first-class immutable disagreement records

Slice 9 introduces tenant-owned Exception records describing disagreements involving expected procurement facts and/or observed receiving reality. Each row is a historical observation, with durable relationships explaining that observation.

These rows are not mutable workflow state in Slice 9. Ordinary runtime authority cannot rewrite, delete, or truncate them. No generic JSON-only exception relationship model is permitted. Slice 10 retains exception resolution, its status projection/event history, and correction workflows.

### Decision 8 — Exact Slice 9 exception vocabulary

Preserve all nine handoff Slice 9 names and meanings:

| Type | Handoff meaning |
| --- | --- |
| `SHORT` | PO-line quantity exceeds received quantity across its receipt lines. |
| `OVER` | Received quantity exceeds ordered quantity. |
| `SUBSTITUTION` | A receipt line linked to a PO line carries a different Item. |
| `DAMAGED` | Receipt-line condition is DAMAGED. |
| `OPENED` | Receipt-line condition is OPENED. |
| `SERIAL_UNREADABLE` | A serialized unit uses the UNREADABLE identifier representation. |
| `SERIAL_MISMATCH` | A captured serial conflicts with an identifier already on record. |
| `UNEXPECTED_ITEM` | A receipt line has no PO-line expectation. |
| `QUANTITY_VARIANCE` | Receipt-line quantity disagrees with the packing-reference count. |

The frozen acceptance scenario produces `SUBSTITUTION`, `SERIAL_UNREADABLE`, `SHORT`, and `UNEXPECTED_ITEM`. Those four do not replace the full governed vocabulary.

`SERIAL_UNREADABLE` is the exact spelling. The lower-tier implementation prompt's `UNREADABLE_IDENTIFIER` spelling is superseded and must not become an alias or additional exception type. Future materials-only types are not introduced unless the handoff explicitly requires them in the opened slice; Slice 10's later reservations do not activate materials in Slice 9.

### Decision 9 — Explicit relationship columns

Exceptions use explicit typed references with nullability appropriate to their type. Conceptual fields are:

| Field | Authority or purpose |
| --- | --- |
| `id` | Permanent opaque FleetOps Exception identity. |
| `org_id` | Required authenticated tenant scope. |
| `exception_type` | Governed classification derived from receiving facts. |
| `receipt_id` | Required receipt containing the receiving/reconciliation context. |
| `receipt_line_id` | Nullable reference to actual receiving reality, required by applicable types. |
| `po_line_id` | Nullable exact immutable expectation-version reference, required by applicable types. |
| `asset_id` | Nullable created Asset reference, required for SERIAL_UNREADABLE. |
| `actual_item_id` | Optional typed reference only where useful or required by the governed model; the receipt line already identifies actual Item. |
| `actor_id` | Credential-derived authenticated cause. |
| `occurred_at` or `observed_at` | Applicable occurrence/observation-time claim under D11. |
| `recorded_at` | Database/server-set record time, distinct from occurrence time. |
| Detail/reason text | Only where governed; never a substitute for typed relationships. |

Derive expected Item through `po_line_id` rather than duplicate `expected_item_id` unless the handoff requires a snapshot. Exact physical field names belong to Slice 9. Occurrence and recording timestamps remain separate UTC facts; the client cannot supply authoritative `recorded_at`, organization, or performing Actor.

Untyped `related_refs` JSON cannot be the sole relationship authority. This gives Slice 9 a precise receiving model without implementing Slice 10's generalized resolution workflow.

### Decision 10 — All exceptions belong to a receipt

Every Slice 9 reconciliation exception belongs to exactly one receipt. `receipt_id` is required, including for a SHORT whose missing quantity has no physical receipt line. The receipt supplies the observed receiving context without pretending a missing unit arrived.

### Decision 11 — SUBSTITUTION relationships

SUBSTITUTION means that the expected PO-line Item differs from the physically received Item. It requires `receipt_id`, `receipt_line_id`, and `po_line_id`.

The receipt line records actual Item; the exact PO-line version records expected Item. Neither is rewritten to erase the difference. If the actual unit is serialized, its Asset references actual Item. An `asset_id` may also be linked where the implementation naturally associates the disagreement with one unit, subject to Decision 15's cardinality and exact-scenario requirements.

### Decision 12 — SERIAL_UNREADABLE relationships

SERIAL_UNREADABLE requires `receipt_id`, `receipt_line_id`, and `asset_id`. `po_line_id` is present when that unit was received against a PO expectation and is NULL for an unexpected/non-PO unit where the governing receiving contract permits it.

The existing Asset identifier is the canonical identifier fact: `value = NULL` with a nonblank unreadable reason. The Exception records the observed condition for receiving reconciliation. It does not replace the identifier record or supply a fabricated serial.

### Decision 13 — SHORT does not require a receipt line

SHORT means that expected quantity exceeds actual received quantity, preserving the handoff's comparison across the PO line's receipt lines. It requires `receipt_id` and the exact `po_line_id`.

`receipt_line_id` is NULL: the missing quantity is not a physically received row. A SHORT may record shortage quantity if the handoff's numeric exception model requires it; this decision does not invent an additional quantity ledger.

Do not create a zero-quantity receipt line, fictional missing-Item row, or Asset for a unit that never arrived. The real received portion remains ordinary receipt reality.

### Decision 14 — UNEXPECTED_ITEM relationships

UNEXPECTED_ITEM means physically received reality has no matching PO-line expectation. It requires `receipt_id` and `receipt_line_id`; `po_line_id` is NULL.

If the unexpected Item is serialized and the handoff requires its Asset, `asset_id` may link that created Asset. Do not create a fake PO line. The frozen accessory's nonserialized treatment is specified separately in Decision 32.

### Decision 15 — One row per disagreement instance

Each independently meaningful disagreement creates one Exception row. Unrelated disagreements are not collapsed into a generic row, and one condition is not automatically counted under multiple types.

The frozen scenario must produce exactly four Exception rows. Substitution, shortage, unreadability and unexpected arrival each retain their own evidence and relationships; an implementation must not produce a fifth row by mechanically double-counting one of those conditions.

### Decision 16 — Server derives mechanical exceptions

FleetOps derives mechanically established classifications from validated expectation and receipt facts. Expected Item A versus actual Item B derives SUBSTITUTION; expected quantity 2 versus actual total 1 derives SHORT; a receipt line with no matched expectation derives UNEXPECTED_ITEM.

The client cannot select an arbitrary exception type to suppress, manufacture, or replace these results. The server derives classification without changing either expectation or observed reality.

### Decision 17 — Observed unreadability derives SERIAL_UNREADABLE

Unreadability is an operator-observed fact. Receiving input may state that the identifier is unreadable and provide its required nonblank reason.

FleetOps creates the existing unreadable identifier representation and derives SERIAL_UNREADABLE in the same applicable creation transaction. The caller supplies the observation, not arbitrary exception authority.

### Decision 18 — Exception relationship constraints

Slice 9 must durably enforce at least these relationship shapes:

| Exception | Receipt | Receipt line | Exact PO-line version | Asset |
| --- | --- | --- | --- | --- |
| `SUBSTITUTION` | Required | Required | Required | Optional where associated with a unit. |
| `SERIAL_UNREADABLE` | Required | Required | Required when PO-backed; otherwise NULL. | Required |
| `SHORT` | Required | NULL | Required | No fabricated missing-unit Asset. |
| `UNEXPECTED_ITEM` | Required | Required | NULL | Optional for an actually created serialized Asset. |

All references are same-tenant. An identified receipt line must belong to the identified receipt. Any Asset reference must belong to that receiving reality. A PO-line reference must agree with the receipt's PO and, where a receipt line is present, its exact comparator; a different valid same-tenant UUID is not interchangeable.

Use ADR-002 tenant-safe foreign keys wherever applicable and durable relationship checks for the remaining shapes. RLS remains fail-closed with `USING` and `WITH CHECK`, no runtime TRUNCATE, and explicit tenant checks at any elevated boundary. Physical names and constraint mechanisms remain implementation details; API-only validation is insufficient.

## Part III — Production Asset creation inputs

### Decision 19 — Owner is explicit receiving business input

Each serialized-unit receiving input explicitly supplies non-null `owner_party_id`. FleetOps validates that it identifies a Party in the authenticated organization. It answers whose Asset this is.

Owner is not inferred from vendor, manufacturer, performing Actor, custodian, or organization context alone. The same Party may legitimately hold more than one relationship, but equality must follow the supplied and validated business facts rather than a default assumption. Existing vendor-role requirements remain separate.

### Decision 20 — Custodian is optional receiving input

Initial `custodian_party_id` may be supplied when known and must identify a same-organization Party. If no custodian is represented at receiving, NULL is valid under ADR-007. Ownership and custody do not supply defaults for one another.

### Decision 21 — Receipt dock is initial Asset location

For a serialized Asset created by receiving, the validated receipt `dock_location_id` is the first known physical location. Creation writes the same value into:

```text
assets.current_location_id = receipt.dock_location_id
asset_initial_facts.initial_location_id = receipt.dock_location_id
```

A later scan/move to a rack, station, room, or other Location creates normal Slice 6 movement history from this dock baseline. Production receiving must not record NULL initial location when the receiving transaction knows the dock where the unit arrived.

### Decision 22 — Dock location is compatible with later scanning

The frozen scenario's later scan into a Location represents movement from the receiving dock to the subsequent storage/use Location. It does not require an unknown location at receipt.

Recording dock, subsequent scanned Location, and later movements preserves the complete known physical timeline. It changes no frozen acceptance requirement and requires no Architecture Amendment Request. ADR-007's general ability to represent an unknown initial Location remains intact; this production receiving path has a known dock.

### Decision 23 — Dock is required for serialized production creation

A production receiving transaction creating serialized Assets requires a valid same-organization `dock_location_id`. It references the existing Location model; this decision creates no separate dock entity or new Location vocabulary.

If a broader receipt without a dock is allowed for a future case, it cannot create a production serialized Asset until a valid initial physical location is established under an accepted rule. This ADR does not authorize such a future path or NULL-location serialized production creation in Slice 9.

### Decision 24 — Owner and location are creation facts

Validate owner, optional custodian and dock before Asset creation. The same validated values populate the Asset projection and ADR-007 `asset_initial_facts` atomically.

Do not reconstruct a baseline later from whichever values the mutable projection contains. This preserves independent authority for the first movement, custody change and ownership change.

### Decision 25 — Initial assignment remains unassigned

ADR-008 remains unchanged. Every created Asset receives exactly one immutable `asset_initial_assignment_facts` witness, positively recording that it entered FleetOps unassigned. `current_assignment_id` is NULL at creation.

The witness remains separate from the physical baseline. Neither witness produces an additional global version; version 1 is represented exactly once by the initial lifecycle transition.

### Decision 26 — Complete creation bundle

For each serialized received unit, one production receiving transaction creates coherently:

1. The required receipt/receipt-line reality relationship and provenance.
2. The Asset against the actual serialized Item, with `current_state = RECEIVED`, `version = 1`, explicit owner, optional custodian, receipt dock as current location, and `current_assignment_id = NULL`.
3. The initial immutable lifecycle transition: `from_state = NULL`, `to_state = RECEIVED`, `result_version = 1`.
4. Exactly one ADR-007 physical baseline with the same owner, optional custodian and dock.
5. Exactly one ADR-008 initial-unassigned witness.
6. Required Asset identifier records.
7. Applicable derived receiving Exception rows for that received unit.

All components succeed or fail together. Required Actor and occurrence/recording facts describe the same validated creation operation. Failure cannot leave a projection, history row, witness, identifier, linkage or unit exception committed alone.

No version-1 movement, custody-change, ownership-change or assignment event is added. ADR-005's single global Asset version remains intact. Python retains workflow responsibility; durable invariants and any justified atomic database boundary remain subject to ADR-001, ADR-002 and ADR-006 rather than introducing a general privileged procedure framework.

### Decision 27 — No manual Asset creation

Receiving retains production Asset-creation authority. There is no `POST /assets` or separate runtime endpoint for physical baselines, initial-assignment witnesses, or initial lifecycle transitions. The receiving boundary creates the complete bundle; controlled administrative fixtures do not become an alternative production onboarding path.

### Decision 28 — Performing Actor is credential-derived

Receiving derives its performing Actor under ADR-006 through `current_authenticated_actor()` or the same verified credential authority. Required runtime attribution across the creation records uses that authenticated Actor. Organization context alone is insufficient, and another active same-org Actor cannot be supplied as a substitute.

`owner_party_id` is a business Party reference, not the performing Actor. Receiving an Item does not establish ownership or imply an Actor-to-Party ownership relationship. The existing HUMAN bearer boundary is preserved; typed machine Actors do not gain a new credential mechanism here.

### Decision 29 — Existing identifier input contract

Receiving uses the Slice 5 identifier contract and vocabulary: `MANUFACTURER_SERIAL`, `PCB_SERIAL`, `MAC`, `IMEI`, and `OTHER`. Readable identifiers record actual observed values.

An unreadable identifier stores NULL `value` and a nonblank `unreadable_reason`. It still belongs to the permanent opaque Asset identity. Do not store a placeholder serial, an invented value, or the marker text as a shared readable serial. The applicable SERIAL_UNREADABLE Exception accompanies the canonical identifier fact.

### Decision 30 — Duplicate identifier failure is atomic

If a required readable identifier violates existing uniqueness, the serialized-unit creation transaction fails. Preserve the existing uniqueness boundary on `(org_id, type, value)` for non-null values.

The failure leaves no partial Asset, initial transition, physical baseline, assignment witness, receipt-unit linkage or orphan Exception from that attempted creation. Use existing database constraints within the atomic receiving boundary; do not weaken uniqueness, reuse an existing Asset as the new unit, or commit an incomplete bundle to absorb the error. This decision does not rename or remove the handoff's SERIAL_MISMATCH classification.

## Part IV — Acceptance-scenario consequences

### Decision 31 — Exact four exceptions

The frozen scenario produces exactly four Slice 9 Exception rows:

1. SUBSTITUTION.
2. SERIAL_UNREADABLE.
3. SHORT.
4. UNEXPECTED_ITEM.

There is no UNREADABLE_IDENTIFIER type and no fifth exception caused by double-counting one of these conditions.

### Decision 32 — Exact nine Assets

The scenario creates exactly nine serialized Assets: six workstations, one delivered barcode scanner, one label printer, and one network appliance. Each starts RECEIVED at version 1 with its complete creation bundle.

The unexpected accessory is nonserialized in this scenario. It creates receipt reality and UNEXPECTED_ITEM only, with no Asset or inventory balance. This acceptance-specific fact does not imply that every unexpected Item in FleetOps is nonserialized.

### Decision 33 — Short scanner

Two scanners are expected and one physically arrives. Persist the one real scanner's receiving reality and create one SHORT against the exact scanner expectation-version UUID, with the receipt reference and `receipt_line_id = NULL` on that Exception.

Do not create a second scanner receipt row or Asset. The absent quantity remains a disagreement with expectation, not invented physical reality.

### Decision 34 — Substituted workstation

Receive the substituted workstation as its actual Item/configuration and create its Asset against that actual Item. SUBSTITUTION links the actual receipt reality to the expected immutable PO-line version. The PO remains unchanged; this decision does not pull configuration-application work into receiving merely to conceal the substitution.

### Decision 35 — Serial-unreadable workstation

The affected workstation receives a normal permanent Asset UUID. Its manufacturer-serial identifier uses the existing NULL-value/nonblank-reason representation. Exactly one SERIAL_UNREADABLE records the observed condition. No serial is fabricated.

## Part V — Source of truth and scope

### Decision 36 — Exceptions do not mutate expectation

Creating receiving reality or an Exception has no side effect on `purchase_orders`, `purchase_order_lines`, or supersession lineage. An exception explains divergence without resolving it by rewriting either historical record. Every PO line remains byte-identical across the acceptance delivery.

### Decision 37 — Exception is not health corruption

A legitimate receiving disagreement is business truth. Its existence alone does not indicate broken database reconciliation health. Operational integrity checks continue to compare maintained projections with their authoritative histories; receiving Exceptions record expectation-versus-reality disagreements. Neither surface silently repairs the other.

### Decision 38 — Nonserialized reality does not activate materials

Slice 9 may record nonserialized receipt reality under the handoff, including the unexpected accessory. It creates no Lot, Stock Unit, stock balance, or stock movement. Those primitives remain v0.4; a receipt quantity is not a materials inventory ledger.

### Decision 39 — Evidence remains deferred

Slice 9 does not implement evidence storage. Any explicitly governed `evidence_ref` seam before Slice 11 remains fail-closed and NULL-only. This does not waive D17 or the complete v0.1 receiving-evidence acceptance requirement; implementation remains in its assigned later slice.

### Decision 40 — No corrections, labels or offline capture

This ADR does not authorize receipt corrections, labels, offline capture, or idempotent capture operations. They remain in their later slices. It introduces no exception-resolution workflow, integration, procurement approval, accounting calculation, or materials capability.

## Bounded handoff refinement

ADR-010 refines Slice 9 in exactly these respects:

1. PO-backed receiving explicitly targets an exact immutable PO-line version UUID; FleetOps validates active-leaf authority under the shared PO lock.
2. Stale comparator selection rejects rather than silently retargeting.
3. Exceptions use explicit typed nullable relationships; SHORT needs no fictional receipt line. The handoff's relevant-line requirement applies to the actual relationships that exist for each disagreement, including NULL PO-line reference for unexpected reality.
4. The exact spelling is SERIAL_UNREADABLE, correcting the lower-tier implementation prompt.
5. Serialized Asset owner is explicit same-org receiving input.
6. Initial custodian is optional and independent of ownership.
7. The validated receipt dock supplies authoritative initial Asset location.
8. Receiving creates the complete ADR-004/007/008 authority bundle atomically, with ADR-006 Actor binding and applicable identifiers, provenance and unit Exceptions.

All other Slice 9 requirements remain governing. In particular, D13 preserves each receipt line's captured UOM and forbids reinterpretation after Item-default changes; the existing UOM vocabulary is not expanded. Handoff quantity, condition, vendor, unit-price provenance, tenant isolation and remaining exception semantics are not replaced. Asset cost continues to resolve through receipt line to the referenced PO line's unit price, without an Asset cost column.

Slice 10's broader exception resolution/state and correction doctrine remain future work. This bounded receiving model supplies first-class observations now without implementing that later workflow. No earlier ADR or handoff file is changed, and no v1.4 is required solely for ADR-010.
