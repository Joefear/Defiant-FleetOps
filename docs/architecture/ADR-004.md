# ADR-004 — Asset Transition Initialization, Versioning, and Evidence Seam

## Status

Accepted

## Context and authority

Slice 5 of the current [Build Handoff v1.2](FleetOps_v0.1_Build_Handoff_v1.2.docx) requires immutable Asset transition history, a maintained Asset projection, optimistic `expected_version`, `transition_asset(...)`, nullable `asset_transitions.evidence_ref`, and reconciliation against authoritative history. Before the Slice 5 schema exists, implementation needs deterministic transition ordering, coherent initialization, an evidence parameter before evidence storage exists, serialized-Item eligibility, descriptive-update attribution, and a clear production creation boundary.

Implementation authority remains:

1. Frozen FleetOps Architecture & Boundary document.
2. Accepted Architecture Decision Records (ADRs).
3. Current FleetOps build handoff.
4. Active slice/task prompt.

The frozen [Architecture & Boundary document](FleetOps_Architecture_Boundary_v0.1.docx), with its [working Markdown transcription](FleetOps_Architecture_Boundary_v0.1.md), governs this ADR. [ADR-001](ADR-001.md) continues to govern layer responsibilities, [ADR-002](ADR-002.md) governs tenancy and tenant-safe references, and [ADR-003](ADR-003.md) governs catalog identity and external-reference cardinality.

This ADR refines implementation only. It does not amend the frozen architecture, begin Slice 5, create production capability, or authorize changes to production code, tests, committed migrations, prior ADRs, or Build Handoff v1.2.

## Decision 1 — Asset version initialization

A newly established Asset begins with:

```text
version = 1
current_state = RECEIVED
```

Its authoritative initial transition has:

```text
result_version = 1
from_state = NULL
to_state = RECEIVED
```

There is no version 0 authoritative Asset state. When the production creation workflow is introduced, it must create the initial Asset projection and initial RECEIVED transition atomically.

Slice 5 exposes no production Asset creation. Controlled Slice 5 fixtures may create the coherent Asset/initial-transition pair for testing; they do not establish a production onboarding path.

## Decision 2 — Result version is authoritative order

`asset_transitions` carries:

```sql
result_version integer NOT NULL
```

The database requires a positive `result_version` and enforces:

```sql
UNIQUE (org_id, asset_id, result_version)
```

Authoritative transition ordering for an Asset is by `result_version`. Its latest authoritative transition is the row with `MAX(result_version)` for that Asset within its organization.

Neither `occurred_at`, `recorded_at`, nor UUID ordering may determine the authoritative transition sequence. Under D11, `occurred_at` is an event-time claim, while `recorded_at` records database ingestion time and is set server-side. Both timestamps remain distinct UTC facts; neither replaces `result_version`.

## Decision 3 — Initial transition check

Database constraints must enforce semantics equivalent to all of the following:

- `result_version = 1` requires `from_state IS NULL` and `to_state = RECEIVED`.
- `result_version > 1` requires `from_state IS NOT NULL`.
- No later transition may use NULL `from_state`.
- No initial transition may begin in any state other than RECEIVED.

Use the smallest clean CHECK constraint or constraints with identical behavior, together with the positive, non-null result-version requirement. Initialization is the sole NULL-from-state case; it is not a general transition escape hatch.

## Decision 4 — Projection version must reconcile with history

`assets.version` is a maintained projection. After every successful transition:

```text
assets.version == transition.result_version
```

Reconciliation must compare at minimum:

```text
assets.current_state == latest authoritative transition.to_state
assets.version == latest authoritative transition.result_version
```

An Asset without authoritative transition history is a reconciliation discrepancy, not an Asset to omit from the result. State mismatch and version/result-version mismatch must also be reported.

A projection may be used for locking and concurrency checks, but never as the sole authority for admitting new history. Reconciliation compares the projection against history, preserving D3's prohibition on a projection validating itself.

## Decision 5 — Transition version rule

For a normal transition, the caller supplies `expected_version = N`. Within the atomic transition operation, `transition_asset` verifies all of the following:

- `assets.version == N`.
- The latest authoritative transition's `result_version == N`.
- The latest authoritative transition's `to_state` equals the requested `from_state`.
- `assets.current_state` agrees with that authoritative history.

On success, the same transaction writes:

```text
new transition.result_version = N + 1
assets.version = N + 1
assets.current_state = requested to_state
```

Any mismatch, including missing authoritative history, rejects the operation with no writes. The expected-version concurrency requirement remains: two competing transitions with the same expected version cannot both succeed, and the version increments once for the one successful transition.

Python retains lifecycle-graph legality and authorization under ADR-001. The database function retains atomic history/projection enforcement and ADR-002's explicit trusted-organization and tenant-safe reference checks. This decision does not move the lifecycle graph into PostgreSQL or weaken immutable-history and projection-write permissions.

## Decision 6 — evidence_ref is in the function contract now

The Slice 5 transition function interface includes nullable `evidence_ref`. Conceptually:

```text
transition_asset(
    asset_id,
    expected_version,
    from_state,
    to_state,
    reason,
    actor_id,
    occurred_at,
    evidence_ref,
    client_op_id
)
```

Exact SQL parameter naming follows repository conventions. `actor_id` comes from authenticated Actor context, not a caller-selected attribution identity; organization authority remains the trusted context defined by ADR-002.

This explicitly refines the lower-tier Build Handoff v1.2 Slice 5 function signature, which omits `evidence_ref` even though its `asset_transitions` definition contains that field and the frozen architecture defines transitions as carrying evidence. The parameter is present from the first Slice 5 implementation so the interface need not be replaced when evidence becomes available.

## Decision 7 — Non-null evidence fails closed until evidence exists

Slice 5 has no evidence subsystem and must not accept an arbitrary non-null `evidence_ref` as valid evidence. The Slice 5 database must require:

```sql
evidence_ref IS NULL
```

Use a temporary CHECK constraint or equivalent durable database rule. A service-only check is insufficient for this restriction. The function still accepts the nullable parameter, but any non-null value is rejected with no transition or projection write.

When the real attachment/evidence subsystem exists, Slice 11 may remove the temporary NULL-only restriction, add the real tenant-safe evidence relationship, and validate evidence existence and provenance under D17 and ADR-002.

Do not fabricate evidence UUIDs or build evidence storage in Slice 5. This seam does not replace immutable, content-addressed evidence or its capture-time provenance requirements.

## Decision 8 — Retirement remains fail-closed

The lifecycle graph retains the legal RETIRED edges defined in Build Handoff v1.2 Section 3 — v0.1 Asset Lifecycle: IN_STOCK to RETIRED and OUT_OF_SERVICE to RETIRED. RETIRED remains terminal and requires disposal evidence.

Because Slice 5 cannot yet possess valid evidence, a successful production transition to RETIRED is unavailable in Slice 5. The Python service rejects RETIRED execution until disposal evidence is verifiable. This does not remove RETIRED or its legal incoming edges from the graph and does not authorize an evidence-free retirement path.

## Decision 9 — Assets require serialized Items

In v0.1, an Asset may reference only an Item with `serialized = true`. Non-serialized Items do not create Asset rows. This preserves the later receiving contract:

```text
serialized received unit -> Asset
non-serialized receipt line -> no Asset and no inventory balance in v0.1
```

Prefer durable PostgreSQL enforcement. If the existing Items schema supports the established fixed-discriminator/composite-FK technique cleanly, use that pattern. The committed identity and catalog migrations already use fixed discriminators for HUMAN Actor linkage and MANUFACTURER Party-role membership.

For example, a future implementation may establish an organization-scoped unique target including `items.serialized` and give the Asset a generated or fixed TRUE discriminator referencing it through a composite tenant-safe FK. Such enforcement must preserve eligibility when the referenced Item is updated as well as when the Asset is inserted or its reference is changed.

The exact schema technique is not mandated; the invariant is. Do not rely solely on a race-prone service SELECT when a clean database invariant is practical. Any required schema addition belongs to future implementation, not an edit to a committed migration in this gate.

## Decision 10 — Asset descriptive update attribution

Asset display and descriptive metadata may be mutable where D1 and the handoff permit it. Every production descriptive Asset update records:

```text
updated_by_actor_id
updated_at
```

`updated_by_actor_id` comes from authenticated Actor context and uses an ADR-002 tenant-safe relationship. `updated_at` is server/database time. The descriptive update and its attribution are recorded together; request data cannot select the performing Actor or supply the update time.

These fields describe the current record's attribution, following the existing catalog convention. They do not introduce an immutable lifecycle-history subsystem for descriptive metadata and do not authorize direct updates to maintained projection columns.

## Decision 11 — No production manual Asset creation

Slice 5 does not expose `POST /assets` or any equivalent general manual Asset onboarding operation. Production Asset creation authority belongs to receiving.

When Slice 9 is implemented, receiving each serialized physical unit creates its Asset and initial RECEIVED transition atomically, with the receiving provenance required by that slice. A controlled Slice 5 fixture is not a production creation workflow.

Defiant hardware that exists before FleetOps go-live must not create a manual-Asset shortcut. Its future go-live path is a deliberate receipt-based inventory-establishment workflow under the receiving boundary.

Exact treatment of incomplete historical vendor/procurement provenance is re-derived when Slice 9 is implemented. FleetOps must not invent false provenance merely to initialize existing hardware. This ADR does not design that later workflow or pull receiving into Slice 5.

## Decision 12 — Slice 4 reparenting remains deferred

As an implementation consequence only, `0005_space_cycle_guard` correctly protects the currently authorized INSERT-only Location write surface. Existing Location parent edges are not mutable through the production runtime permissions.

Do not broaden the trigger or grant `parent_location_id` UPDATE as part of ADR-004 or Slice 5. Future Location reparenting requires a dedicated concurrency-safe design. Merely adding `AFTER UPDATE OF parent_location_id` is insufficient by itself: concurrent parent changes must also be analyzed and made cycle-safe.

No Slice 4 code change is authorized by this ADR. The committed cycle guard and its existing tests remain unchanged.

## Handoff refinement boundary

This ADR explicitly refines only these Slice 5 implementation details in Build Handoff v1.2:

1. **Deterministic latest transition:** positive, organization/Asset-unique `result_version` supplies authoritative order; timestamps and UUIDs do not. Reconciliation includes version agreement and missing history, and admission checks both history and projection.
2. **Initial transition and version:** the coherent initial pair is Asset version 1 / RECEIVED and transition result version 1 / NULL to RECEIVED, with database checks excluding other initial states and later NULL from-states.
3. **Evidence parameter and availability:** the conceptual `transition_asset` signature includes nullable `evidence_ref`; Slice 5 durably accepts only NULL, and production retirement fails closed until disposal evidence is verifiable. The real evidence relationship remains later work.
4. **Serialized-Item eligibility:** only serialized Items may back v0.1 Assets, preferably enforced durably in PostgreSQL.
5. **Descriptive-update attribution:** every production descriptive update records the authenticated Actor and server/database update time.
6. **Production creation boundary:** receiving owns creation of the Asset plus initial transition; Slice 5 provides controlled fixtures only, with no manual production onboarding route.

The function-signature refinement supersedes the handoff's omission of `evidence_ref`; the other points fix or strengthen the named implementation details without rewriting the handoff. Build Handoff v1.2 remains the current handoff and is preserved as written, as are ADR-001, ADR-002, and ADR-003.

This ADR does not supersede the lifecycle graph, immutable-history rule, transition concurrency requirement, corrupted-projection rejection, ON_HOLD orthogonality, or Slice 6+ work. It neither implements nor redesigns later movement, custody, ownership, assignment, receiving, correction, or evidence workflows. Later slices must continue to reconcile their requirements against the governing authority order before implementation.

Where the handoff says "Section 3" for lifecycle, future prompts should say "Build Handoff v1.2 Section 3 — v0.1 Asset Lifecycle" to avoid confusion with the frozen Architecture's Section 3 boundary section.

## Required Slice 5 test implications

These are requirements for future Slice 5 implementation, not tests introduced or claimed to pass by this document-only gate. Slice 5 must prove:

1. A coherent initial fixture has Asset version 1 / RECEIVED plus transition result version 1 / `from_state NULL` / `to_state RECEIVED`.
2. An initial transition in any other state is rejected.
3. A later transition with NULL `from_state` is rejected.
4. A duplicate `result_version` for one Asset within its organization is rejected.
5. A successful transition from version N produces exactly `result_version = N + 1`, with the projection advanced atomically to the same version and requested state.
6. Reconciliation detects state mismatch, version/result-version mismatch, and missing history.
7. `occurred_at` ordering cannot redefine authoritative latest history.
8. A non-null `evidence_ref` is rejected by the Slice 5 database with no transition or projection writes.
9. The transition function interface already carries `evidence_ref`.
10. An Asset cannot reference an Item with `serialized = false`.
11. Descriptive PATCH records `updated_by_actor_id` from authenticated context and `updated_at` from server/database time; caller-supplied attribution and timestamps cannot override them.
12. No `POST /assets` or equivalent production manual creation route exists.
13. The prior Location cycle guard remains unchanged.

The original Slice 5 acceptance requirements remain mandatory: projection-write and immutable-history permissions, competing transitions with one success and one version increment, corrupted-projection rejection and reconciliation, READY to RETIRED rejected in Python before any database call, and ON_HOLD transitions preserving location, custody, ownership, and assignment. Legal RETIRED edges must remain in the graph while production execution without verifiable disposal evidence is rejected.

Database proofs use real PostgreSQL 16. ADR-002's tenancy requirements and adversarial checks continue to apply, including runtime-role execution for isolation assertions, explicit SECURITY DEFINER tenant checks, and tenant-safe references. Prior invariant tests must remain green and must not be weakened.

## Architectural status and scope

ADR-004 is subordinate to the frozen Architecture & Boundary document. It preserves D1 opaque identity; D3 authoritative history and maintained projections; D5 expectation versus physical reality; D8 lifecycle orthogonality; D10 authenticated Actor attribution; D11 occurrence versus record time; D17 evidence doctrine; and D18 tenancy. D6's immutable-history and correction doctrine remains unchanged.

Serialization eligibility does not choose serialization policy per Item class. The temporary lack of executable retirement in Slice 5 does not remove disposal evidence or retirement from the completed v0.1 acceptance scenario. The receiving boundary does not permit invented historical provenance.

This document records a pre-Slice 5 implementation decision only. It creates no production capability and begins no Slice 5 code. A collision with a controlled architectural section requires STOP and an Architecture Amendment Request, not a workaround in implementation.
