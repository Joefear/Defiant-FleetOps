# ADR-001 Implementation decision

Originally recorded from Section 1 of FleetOps_v0.1_Build_Handoff_v1.1.docx; aligned with the current [Build Handoff v1.2](FleetOps_v0.1_Build_Handoff_v1.2.docx).

Recorded here, not in the architecture document, so that a future language change does not amend the architecture.

**Decision:** Python 3.13+ / FastAPI / Pydantic v2 / SQLAlchemy 2.x / Alembic / PostgreSQL 16 core. TypeScript + React (Next.js) PWA capture client with IndexedDB offline store. pytest for all server-side proof.

**Status:** Accepted

**Reason:** Transactional, human-paced workload with no systems-language performance requirement; existing Defiant testing discipline is pytest-based; ecosystem maturity; velocity on correctness questions (legal transition, provenance preserved, offline conflict, history reconstruction) outweighs runtime characteristics.

**Rejected:** C++ (no upside). Rust for the core (velocity cost with no compensating requirement). Both remain open for FleetOps Edge at v0.5, decided against actual hardware; Go is the likely first choice there.

## 1.1 Layer responsibility

**PostgreSQL:** Foreign keys and uniqueness; immutable-history permissions (no UPDATE/DELETE for the application role on history tables); projection write restrictions (column-level grants); atomic transition and movement functions; organization isolation; transactional outbox table; database-level invariants and reconciliation queries.

**Python service:** Allowed lifecycle transition graph; authorization decisions; exception generation; receipt reconciliation; offline conflict semantics; workflow orchestration; integration trust evaluation (v0.5).

**pytest:** Proves both layers keep honouring the frozen contracts. Every slice ships invariant tests and adversarial (negative) tests, not just behaviour tests.

**PWA client:** Scan-first capture; local operation queue; sync; conflict surfacing. Holds no authority; every operation is validated server-side.

PostgreSQL enforces durable invariants and justified privilege boundaries. Python remains the main workflow and orchestration layer. PostgreSQL is not to become a stored-procedure application. SECURITY DEFINER functions are permitted only where either:

1. Atomicity across authoritative-history insertion and maintained-projection update requires them, such as transition, movement, assignment, ownership, or custody change.
2. A narrowly scoped privilege-boundary operation cannot be safely expressed through ordinary RLS-protected access.

Category 2 must be explicitly justified by an accepted implementation ADR, expose the smallest possible interface, use a fixed safe `search_path` or fully qualified objects, receive only the minimum required privileges, and have adversarial tests proving the boundary.

For v0.1, `resolve_session(token_digest)` under [ADR-002](ADR-002.md) is the approved authentication-bootstrap example of category 2. This does not authorize arbitrary stored procedures or any additional function.

## Authority and build coordination

Implementation authority is ordered as follows:

1. Frozen FleetOps Architecture & Boundary document
2. Accepted Architecture Decision Records (ADRs)
3. Current FleetOps build handoff
4. Active slice/task prompt

The frozen Architecture & Boundary document is the highest authority. Accepted ADRs may refine implementation choices only within the frozen architecture. The current build handoff derives and coordinates implementation from the architecture and accepted ADRs. An active slice/task prompt applies the handoff to one bounded unit of work.

Each lower tier may add implementation detail, narrow scope, or impose stricter acceptance criteria, but may not contradict, weaken, silently override, or reinterpret a higher tier. When two tiers conflict, the higher tier governs and the implementer must STOP until the lower-tier conflict is corrected, rather than choose whichever instruction is easier.

A conflict with the frozen architecture is handled through the Architecture Amendment Request process. A conflict among ADRs, the handoff, and the active prompt that does not require an architecture amendment is corrected in the lower-tier document before implementation proceeds. No commit, migration, code comment, implementation shortcut, or active prompt can amend a higher-tier governing document.

FleetOps_v0.1_Build_Handoff_v1.2.docx is the current implementation handoff. After v1.2 is accepted, it supersedes v1.1 for all future implementation prompts. v1.1 remains unchanged as historical record. Supersession does not rewrite previous work or previous checkpoints. The frozen architecture remains above both handoff versions.
