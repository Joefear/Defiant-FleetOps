## 1. Problem and controlled architecture collision

An immutable PO line expects `1 M`; the actual receipt captures `100 CM`. FleetOps must preserve both facts. Current authority supplies no governed conversion with which to conclude equality, SHORT, or OVER. The UOM difference also does not establish a disagreement with a packing-reference count, so it cannot by itself justify QUANTITY_VARIANCE.

Comparing the raw numbers `1` and `100` as though their units matched would produce a false quantity conclusion. Treating `100 CM` as `1 M` would instead introduce conversion authority that v0.1 does not have, even where a human knows the physical equivalence.

[Section 5 / D5](../FleetOps_Architecture_Boundary_v0.1.md#d5-expectation-and-reality-are-separate-records-permanently) currently states:

> Where they disagree, the disagreement becomes a first-class exception record. The v0.1 exception types are: short, over, substitution, damaged, opened, unreadable identifier, serial mismatch, unexpected item, quantity variance. Missing lot is added with the materials layer.

D5 also requires receiving personnel always to be able to record what is actually in front of them. D13 preserves the UOM under which each quantity was captured. Together these require preservation of the mixed-UOM observation, but D5's enumerated v0.1 categories contain no truthful classification for its incomparability.

[Section 12](../FleetOps_Architecture_Boundary_v0.1.md#12-change-control) controls Sections 5 through 10. It requires revision of the governing document with a stated reason and directs implementation that cannot satisfy a controlled section to file an amendment request rather than solve the conflict in code. Adding a first-class disagreement category changes D5; it is not merely an ADR refinement.

Without an amendment, implementation must reject physically valid reality, misclassify it, silently convert it, or leave a known disagreement without a first-class exception. All four outcomes violate the architecture's intent. Remaining stopped is the compliant present boundary; adding the narrow category is the recommended resolution.

## 2. Existing vocabulary review

The exact nine Slice 9 definitions in [Build Handoff v1.3](../FleetOps_v0.1_Build_Handoff_v1.3.docx), also preserved in [ADR-010 Decision 8](../ADR-010.md), are:

| Canonical type | Existing meaning | Why UOM difference alone does not satisfy it |
| --- | --- | --- |
| `SHORT` | PO-line quantity exceeds received quantity across its receipt lines. | Requires comparable expected and cumulative actual quantities; differing tokens supply no valid inequality. |
| `OVER` | Received quantity exceeds ordered quantity. | Requires comparable quantities; raw numeric magnitude across different units is insufficient. |
| `SUBSTITUTION` | A receipt line linked to a PO line carries a different Item. | Item identity and UOM are independent facts. |
| `DAMAGED` | Receipt-line condition is DAMAGED. | A unit difference is not physical damage. |
| `OPENED` | Receipt-line condition is OPENED. | A unit difference is not an opened condition. |
| `SERIAL_UNREADABLE` | A serialized unit is received with the UNREADABLE identifier marker. | A unit difference is not an unreadable identifier. |
| `SERIAL_MISMATCH` | A captured serial conflicts with an identifier already on record. | A unit difference is not an identifier conflict. |
| `UNEXPECTED_ITEM` | A receipt line has no PO line. | The unresolved case has an exact PO-line expectation. |
| `QUANTITY_VARIANCE` | Receipt-line quantity disagrees with the packing-reference count. | The unresolved case concerns expected versus actual UOM, not packing-reference disagreement. |

None means that the expected and actual UOM tokens differ without conversion authority. Later exception-management categories and materials reservations do not authorize an additional Slice 9 classification or a generic substitute for this missing D5 category.

## 3. Proposed D5 amendment and canonical name

Propose exactly one additional v0.1 exception type. Architecture prose uses **UOM mismatch**; the proposed implementation enum/token is **`UOM_MISMATCH`**. There are no aliases. This follows the existing distinction between architecture prose such as “unreadable identifier” and the canonical implementation token `SERIAL_UNREADABLE`.

The controlled meaning proposed for D5 is: the receipt's actual UOM differs from the immutable expected PO-line UOM, and FleetOps has no governed conversion authority by which to compare the quantities. This is a disagreement between expectation and reality. It does not itself assert that the quantities would be equal, short, or over after conversion.

The following is the exact proposed D5 patch for a later application gate. The exception-list paragraph gains only the new category; the added paragraph defines its limited meaning. All other D5 text remains unchanged. This patch is proposal text only and has not been applied to either architecture artifact.

```diff
@@ -119 +119,3 @@
-Where they disagree, the disagreement becomes a first-class exception record. The v0.1 exception types are: short, over, substitution, damaged, opened, unreadable identifier, serial mismatch, unexpected item, quantity variance. Missing lot is added with the materials layer.
+Where they disagree, the disagreement becomes a first-class exception record. The v0.1 exception types are: short, over, substitution, damaged, opened, unreadable identifier, serial mismatch, unexpected item, quantity variance, UOM mismatch. Missing lot is added with the materials layer.
+
+UOM mismatch records that the actual unit of measure captured on a receipt line differs from the immutable unit of measure on its expected purchase order line, and that FleetOps has no governed conversion authority by which to compare the quantities. It does not assert that the quantities are equal, short, or over after conversion, and does not authorize unit conversion.
```

## 4. Narrow semantics and no-conversion boundary

If accepted and applied, the proposed classification applies when `expected_uom != actual_uom`, using exact governed UOM tokens, **and** no separately governed conversion mechanism authorizes comparison. For v0.1 there is no such mechanism. This request neither introduces one nor assumes that a future mechanism exists.

| Expected fact | Actual fact | Proposed reconciliation consequence |
| --- | --- | --- |
| `1 M` | `100 CM` | `UOM_MISMATCH`; no equality, SHORT, or OVER conclusion from `1` versus `100`. |
| `1 KG` | `1000 G` | `UOM_MISMATCH`; no inferred equivalence or converted quantity. |
| `2 EA` | Cumulative receipt of `1 EA` | Directly comparable quantity; normal `SHORT` logic applies. |

The amendment would authorize only a truthful disagreement classification. It would not authorize unit conversion, canonical-unit normalization, conversion factors, dimension graphs, rounding, precision policy, vendor-pack conversion, an external conversion service, or a caller-supplied conversion factor. It would not change the governed UOM vocabulary.

The absence of `UOM_MISMATCH` would not itself establish quantity equality. Matching tokens allow direct quantity comparison; the quantities must still be reconciled under the existing meanings.

### Existing exception meanings remain intact

- `SHORT` remains expected quantity exceeding cumulative received quantity when directly comparable. For v0.1, direct quantity comparison requires the exact same UOM token unless future architecture explicitly grants conversion authority. UOM mismatch does not itself establish SHORT.
- `OVER` remains received quantity exceeding ordered quantity when directly comparable. UOM mismatch does not itself establish OVER.
- `QUANTITY_VARIANCE` remains receipt-line quantity disagreeing with the packing-reference count. It is not broadened to cover differing engineering UOM, arbitrary expected/actual quantity differences, or conversion.
- `SUBSTITUTION` remains actual Item differing from expected Item. UOM difference alone does not establish substitution. Expected Item A / M versus actual Item B / CM may produce both `SUBSTITUTION` and `UOM_MISMATCH` only where the later Slice 9 design establishes two independently meaningful disagreements under the one-disagreement-per-row contract. Two rows must not be forced where the facts support only one condition.
- `DAMAGED`, `OPENED`, `SERIAL_UNREADABLE`, `SERIAL_MISMATCH`, and `UNEXPECTED_ITEM` retain their existing meanings without modification.

### Raw facts and receiving recordability

D13 remains unchanged. The PO line retains its immutable expected UOM snapshot, including the exact version selected under ADR-009 and ADR-010. The receipt line retains the actual quantity and actual UOM under which that quantity was captured. Neither fact is normalized, rewritten, or reinterpreted to make it agree with the other or with a later Item default.

A mixed-UOM observation must not be rejected merely because FleetOps cannot convert it. Under the proposed amendment, FleetOps records the physical fact and its `UOM_MISMATCH` disagreement. Existing validation, tenant boundaries, and exact-comparator admission rules remain applicable; the proposal creates no general validation bypass.

For `1 M` expected and `100 CM` actual, the actual receipt fact is stored with `100 CM`, the expectation remains `1 M`, and `UOM_MISMATCH` records the unresolved comparison. No SHORT, OVER, or equivalence is inferred from those incomparable numeric values.

## 5. Multiple lines, packing counts, and later relationship design

For cumulative comparison against one **exact PO-line version**, receipt lines whose UOM exactly matches that expectation may be aggregated in that UOM. Differing-UOM lines must not be blindly summed into the expected quantity total or treated as zero received. The incomparable subset is represented by `UOM_MISMATCH` under the later governed design.

A subtotal of comparable lines is not a complete cumulative received total while linked incomparable quantities remain unresolved. It must not be presented as such to conclude SHORT, OVER, or equality. The exact aggregation algorithm, exception cardinality, and interactions with SHORT/OVER remain ADR-011 and Slice 9 work after amendment; this request does not settle those implementation details.

Packing/count observations remain separate from engineering-UOM quantity. Do not infer boxes to EA, reels to EA, or containers to KG without future conversion/package governance. `QUANTITY_VARIANCE` remains packing-reference-specific; a UOM mismatch does not automatically produce it. This request adds neither packaging tokens nor a packaging model.

The likely typed relationship shape for later ADR-011 consideration is:

| Proposed relationship | Candidate requirement |
| --- | --- |
| `receipt_id` | Required. |
| `receipt_line_id` | Required: the actual captured observation. |
| `po_line_id` | Required: the exact immutable expected comparator. |
| `asset_id` | Optional where the received reality is serialized. |

This table is a **design proposal for ADR-011**, not an accepted schema or additional controlled architecture patch. ADR-011 must settle the exact shape and cardinality while preserving ADR-010's tenant-safe typed references, same receiving context, exact comparator linkage, and one-disagreement-per-row rules. The D5 amendment adds the classification and its meaning; it does not absorb the ADR's implementation design.

No materials ledger, inventory conversion, package conversion, evidence capability, correction workflow, labels, offline capture, or ERP conversion integration is introduced or accelerated. ## 7. Alternatives and risks

The template options are: (a) honour the present list at the cost of keeping affected work stopped; (b) amend D5 narrowly as proposed; or (c) defer the affected capability, leaving Slice 9 incomplete and requiring separate governance for any scope change. Option (b) is recommended. Neither (a) nor (c) permits declaring Slice 9 complete with the collision unresolved.

The following implementation workarounds are rejected:

| Alternative | Reason for rejection |
| --- | --- |
| A. Treat different UOM as SHORT/OVER. | Raw numeric comparison across incomparable units is invalid. |
| B. Reuse QUANTITY_VARIANCE. | Its governed meaning is packing-reference disagreement. |
| C. Reuse SUBSTITUTION. | Item identity and UOM are independent. |
| D. Silently convert. | No conversion provenance, precision, or versioning authority exists. |
| E. Reject the receipt because the units differ. | D5 requires receiving personnel to record physical reality. |
| F. Leave the disagreement unclassified. | D5 requires first-class disagreement records. |

| Risk | Mitigation and remaining consequence |
| --- | --- |
| UOM_MISMATCH becomes a substitute for proper future conversion. | Define it only as an incomparability signal, never a conversion result. Any future conversion capability requires separate governance. |
| SHORT/OVER are not concluded for differing UOM even when humans know the units are equivalent. | Truthful incomparability is preferable to unauthorized conversion in v0.1. Preserve the raw observations; future conversion governance may resolve the gap. Do not infer that an unresolved comparison is a fulfilled expectation. |
| Exception counts increase for suppliers using different packaging/UOM. | Where an observation independently satisfies the proposed UOM condition, the exception accurately records a normalization gap instead of silently asserting agreement. Packaging observations stay separate; no unsupported packaging vocabulary or conversion is inferred. |
