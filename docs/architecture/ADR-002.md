# ADR-002 — Tenancy Enforcement and Tenant-Safe References

## Status

Accepted

## Decision

Organization isolation is enforced by PostgreSQL row-level security (RLS) on every tenant-owned table.

### Trusted organization context

The organization context used by RLS is derived from trusted authenticated server context. For authenticated requests, the authority chain is:

```text
SHA-256 of the presented bearer token
    -> resolve_session(token_digest)
    -> trusted organization, user, and HUMAN actor
    -> transaction-local PostgreSQL organization context
    -> ordinary tenant-owned access under RLS
```

The request does NOT choose its organization. Tenant context must NEVER derive authority from:

- JSON body `org_id`.
- Query parameter `org_id`.
- Form data.
- Caller-supplied `actor_id`.
- Arbitrary request headers.
- External integration payloads.
- Scanned payloads.
- Client-selected organization values.

If such fields exist later, they are data to validate against authenticated context, never authority.

For the intentionally unauthenticated v0.1 `POST /auth/login` path, there is one configured/seeded organization. Login may establish that organization's transaction-local context from trusted server configuration, query the user normally under RLS, verify the Argon2 password hash, and create a session. The caller does not choose the organization. The separate bootstrap command likewise obtains its organization context from trusted server configuration.

Do not require or introduce `resolve_login_user(username)` in v0.1. Future multi-organization login naming/realm semantics are deliberately deferred. If later requirements need a context-free login resolver, that requires a deliberate ADR update rather than silently broadening the authentication-resolution exception below.

### Transaction-local context and pool safety

Organization context is transaction-local. Conceptually use:

```sql
SET LOCAL fleetops.org_id = '<organization uuid>';
```

Or use the transaction-local equivalent:

```sql
SELECT set_config('fleetops.org_id', '<organization uuid>', true);
```

Request tenancy must not use a persistent session-level `SET`. Database connections are pooled and reused; organization context from request A must not survive and become authority for request B.

Every request performing ordinary tenant-owned database work establishes its organization context inside the transaction that performs the work. The authentication-resolution exception below permits only credential resolution before that context exists. After successful resolution, begin or continue the request transaction with transaction-local organization context before any ordinary tenant-owned access. When that transaction ends, the context ends with it.

The custom setting is NOT itself authentication. It is only the database representation of organization identity already established by trusted server-side authentication, with the limited trusted-configuration login/bootstrap paths described above.

### Fail-closed reads and writes

For direct table access, a `fleetops_app` transaction with no active organization context:

- Sees ZERO rows from tenant-owned tables.
- Cannot INSERT tenant-owned rows.
- Cannot UPDATE tenant-owned rows.
- Cannot DELETE tenant-owned rows.

This is intentional behavior, not an accidental consequence of NULL comparison semantics. No helper, policy, or future convenience change may substitute a permissive/default organization when context is absent. Absence of organization context means no tenant authority.

The narrowly scoped `resolve_session(token_digest)` exception below establishes trusted authentication context; it does not make direct tenant-owned table access context-free.

`fleetops_app` must be unable to SELECT tenant-owned rows outside the current organization at the database layer. RLS policies must protect reads and writes using both:

- `USING` predicates for visibility and target-row access.
- `WITH CHECK` predicates for inserted/updated tenant ownership.

A tenant boundary that prevents reading organization B but permits creating or moving a row into organization B is a failure. Application filtering may exist as defence in depth but is never the primary tenant-isolation mechanism.

`USING` filters existing rows. In ordinary statements, SELECT of an invisible cross-tenant row returns zero rows; UPDATE or DELETE targeting that row has `rowcount == 0` and leaves the target unchanged. No exception is required merely because `USING` filtered a row. The same filtering applies when organization context is absent.

`WITH CHECK` validates proposed new rows. INSERT proposing organization B under organization A is rejected with a PostgreSQL RLS error. UPDATE of a visible organization-A row that proposes a new row violating the tenant `WITH CHECK` is rejected with a PostgreSQL error. INSERT without organization context is likewise rejected. These semantics assume the statement has the necessary table/column privileges; separate privilege restrictions remain in force.

### Tenant-safe references

Every tenant-owned table must support tenant-safe references. Every foreign key from one tenant-owned record to another uses `org_id` as part of the relationship. The target provides:

```sql
UNIQUE (org_id, id)
```

The referencing table uses:

```sql
FOREIGN KEY (org_id, target_id)
REFERENCES target(org_id, id)
```

This ensures PostgreSQL rejects a cross-organization relationship even when both UUIDs independently exist.

### SECURITY DEFINER boundary

SECURITY DEFINER functions are a privileged boundary. Except for the narrowly scoped authentication-resolution exception below, every SECURITY DEFINER function operating on tenant-owned data must:

1. Obtain the trusted current organization context and reject missing organization context.
2. Explicitly compare every target tenant-owned row's `org_id` to that context.
3. Verify supplied tenant-owned references belong to that organization.
4. Reject cross-organization targets and reference mismatches before changing authoritative history or a projection.
5. Use a fixed, safe `search_path` or fully qualified object references.

A SECURITY DEFINER function must never depend on RLS alone, or on the function owner's RLS behavior, to provide its tenant check because it executes with elevated ownership authority.

### Authentication-resolution exception

The exception to requiring pre-existing organization context applies ONLY to credential-resolution functions whose purpose is to establish trusted authentication/tenant context. For Slice 2, the required and only permitted context-free resolver is `resolve_session(token_digest)`. It may execute as SECURITY DEFINER without existing organization context because a valid bearer credential must first be resolved into the trusted tenant/user/actor context required for the request.

The resolver must:

- Accept only a session-token digest, with exact digest matching; accept no organization, user, actor, or session identifier, enumeration filter, or alternate lookup key.
- Use a fixed, safe `search_path` and/or fully qualified object references.
- Execute with explicitly restricted privileges limited to the credential-resolution purpose, with PUBLIC EXECUTE revoked and EXECUTE granted only to the intended FleetOps runtime role, `fleetops_app`.
- Explicitly validate the matched session, linked user, and linked HUMAN actor, including their common organization and tenant-safe relationships, rather than relying on the function owner's RLS behavior.
- Return at most one minimal trusted authentication tuple: conceptually `org_id`, `user_id`, and `actor_id`, plus only status/version information genuinely required to establish the authenticated request.
- Never return the bearer token, stored token digest, or password hash.
- Return no row for an unknown digest, expired session, inactive/revoked session, inactive user, or inactive actor.
- Not modify tenant-owned data.

After successful resolution, the trusted server establishes the returned organization's transaction-local context in the request transaction; all ordinary tenant-owned access is then governed by RLS. The resolver is an authentication bootstrap boundary, not an alternative to RLS. It must not become a general context-free tenant lookup or a way to enumerate arbitrary users or sessions.

This authentication-resolution exception is an implementation mechanism required to make ADR-002's fail-closed RLS compatible with A2 bearer authentication. It does not weaken D18, permit arbitrary context-free tenant access, or amend the frozen architecture.

### Reusable policy mechanism

A dedicated migration/helper mechanism applies the standard RLS policy pattern to tenant-owned tables so later slices do not reinvent it. Slice 2 introduces this helper; this ADR records the convention and does not implement it.

RLS is row-level protection and does not govern every whole-table operation. `fleetops_app` must never receive TRUNCATE privilege on tenant-owned tables. The reusable grant/RLS helper must preserve that rule. RLS must not be treated as authorization for TRUNCATE or other administrative table-wide operations.

## Testing requirement

These tests are required against real PostgreSQL 16 in Slice 2 and later slices as the relevant tables, request paths, and functions are introduced.

### Required execution role

Every test intended to prove RLS isolation MUST execute the relevant SELECT/INSERT/UPDATE/DELETE as `fleetops_app`. A test performed only through `fleetops_migrator`, a table owner, or a superuser does NOT prove tenant isolation, because those identities can bypass ordinary RLS behavior.

Administrative connections may seed/setup the test fixture and inspect results, but the operation whose isolation is being asserted must run as `fleetops_app`.

### Missing-context adversarial test

An adversarial test must:

1. Connect as `fleetops_app`, not `fleetops_migrator` or a table-owner connection.
2. Set no organization context.
3. Attempt SELECT against populated tenant-owned data.
4. Receive zero rows.
5. Attempt tenant-owned INSERT and prove it is rejected with a PostgreSQL RLS error.
6. Attempt ordinary UPDATE and DELETE against existing tenant-owned rows using otherwise permitted operations; assert `rowcount == 0` and verify the target data remains unchanged.

Tests must assert PostgreSQL's actual semantics. A row filtered by `USING` does not require an exception. Separate permission-denial tests, including history/projection restrictions, continue to require permission errors where privileges are withheld.

### Minimum coverage

For every tenant-owned table, tests must prove:

- Organization A's SELECT of organization B's rows returns zero rows as `fleetops_app`.
- Organization A's ordinary UPDATE/DELETE targeting an invisible organization-B row has `rowcount == 0` and leaves the target unchanged, where the operation is otherwise permitted.
- INSERT proposing organization B under organization A is rejected with a PostgreSQL RLS error; UPDATE of a visible organization-A row proposing a new row violating the tenant `WITH CHECK` is rejected with a PostgreSQL error.
- No organization context means zero tenant-owned rows visible as `fleetops_app`.
- No organization context means INSERT is rejected and otherwise permitted ordinary UPDATE/DELETE affect zero rows, with target data unchanged, as `fleetops_app`.
- Composite tenant foreign keys reject creating or modifying cross-organization relationships, even when both referenced UUIDs independently exist.
- `fleetops_app` has no TRUNCATE privilege, including after the reusable grant/RLS helper is applied.

Request-context tests must prove that request body/header values cannot override the authenticated organization. Connection-reuse tests must prove that a pooled/reused connection cannot leak organization context across transactions.

For every SECURITY DEFINER function other than the explicitly scoped authentication resolver, adversarial tests must invoke the function from `fleetops_app` under organization A and attempt to target organization B. The function must reject the cross-organization target even though its owner can bypass RLS. Tests must also prove that missing organization context is rejected. The resolver instead must satisfy the credential-boundary tests below; its exception does not apply to other definer functions.

### Slice 2 authentication adversarial coverage

Slice 2 tests must prove:

1. Direct SELECT from populated `sessions` as `fleetops_app` with no organization context returns zero rows.
2. Direct SELECT from populated `users` as `fleetops_app` with no organization context returns zero rows.
3. `resolve_session(valid_digest)`, invoked as `fleetops_app` with no organization context, returns only the expected `org_id`/`user_id`/`actor_id` tuple and any strictly required status/version fields; no bearer token, stored digest, or password hash is returned.
4. Each invalid condition independently returns no row: unknown digest, expired session, inactive/revoked session, inactive user, and inactive actor.
5. `fleetops_app` cannot use the resolver to enumerate arbitrary users/sessions: only an exact valid credential digest resolves its linked tuple, with no alternate lookup keys or enumeration interface. Verify restricted EXECUTE grants, PUBLIC EXECUTE revocation, and the safe object-resolution configuration.
6. The issued raw token is not stored in reusable plaintext form, and the stored session digest equals SHA-256 of the issued token.
7. Resolution does not modify tenant-owned data, and ordinary access after successful resolution uses transaction-local organization context under RLS, preserving cross-tenant isolation and pool safety.

The minimum coverage above also requires Slice 2 to prove cross-tenant UPDATE/DELETE rowcount/data-unchanged semantics, INSERT/new-row `WITH CHECK` rejection semantics, and absence of TRUNCATE privilege.

## Reason

D18 requires organization scoping from the first migration. Application filtering alone can silently omit a tenant predicate and still appear correct in a single-organization deployment. RLS makes missing tenant scope fail at the database boundary.

Composite tenant-safe foreign keys prevent a different class of error: a valid UUID belonging to the wrong organization.

Definer functions cross the ordinary RLS privilege boundary, so their organization checks must be explicit and testable. Bearer-session resolution cannot require the organization context it exists to establish; the restricted credential resolver closes that bootstrap dependency while direct table access remains fail-closed.

## Consequences

- Slice 2 introduces the reusable RLS helper.
- All later tenant-owned tables use it.
- Slices introducing SECURITY DEFINER functions must add explicit organization-context checks and adversarial cross-tenant tests, except for the authentication resolver governed by the narrower credential-boundary requirements above.
- Slice 2 introduces `resolve_session(token_digest)` and its adversarial tests; v0.1 login uses trusted configured organization context and ordinary RLS access.
- The reusable grant/RLS helper must never grant `fleetops_app` TRUNCATE on tenant-owned tables.

## Slice 2 application

These conventions specify the bootstrap and authentication implementation for Slice 2 under the current [Build Handoff v1.2](FleetOps_v0.1_Build_Handoff_v1.2.docx):

- Database migration seeds one organization, one INTERNAL Defiant party, and one bootstrap HUMAN actor.
- The migration does NOT create a password-bearing user.
- A separate bootstrap command creates the initial user from configuration/environment, hashes the password with Argon2, and links it to the seeded HUMAN actor.
- No plaintext or reversible password enters a migration or source control.
- `POST /auth/login` is the sole Slice 2 unauthenticated write endpoint.
- Successful login may create a session.
- Failed login returns 401 and writes nothing in v0.1.
- Every other Slice 2 write requires authenticated actor context.

Do not introduce password-reset workflow, login-attempt audit tables, MFA, SSO, OAuth, an external IdP, or a role hierarchy.

### Session token storage

Bearer sessions use cryptographically secure random tokens with at least 256 bits of source entropy. The raw bearer token is returned to the client only at creation and is not stored in reusable plaintext form.

The database stores `SHA-256(raw bearer token)` or an equivalent fixed one-way cryptographic digest. SHA-256 is the Slice 2 convention and the required test expectation. The trusted server digests the presented bearer token before calling `resolve_session(token_digest)`.

Argon2 is used for human passwords, NOT bearer-session tokens. Human passwords have weak entropy and require deliberately expensive password hashing. Bearer tokens are already high-entropy random secrets; applying Argon2 on every authenticated request adds cost without addressing the password threat model.

### Handoff v1.2 and implementation precedence

[Build Handoff v1.2](FleetOps_v0.1_Build_Handoff_v1.2.docx) incorporates two implementation corrections: creation of the first password-bearing user by a separate bootstrap command outside the migration, and the narrowly scoped authentication-resolution SECURITY DEFINER exception. The migration seeds the organization, INTERNAL Defiant party, and bootstrap HUMAN actor. The bootstrap command creates the first user from trusted configuration/environment, hashes the password with Argon2, and links the user to that actor.

[ADR-001](ADR-001.md) and handoff v1.2 recognize ADR-approved privilege-boundary operations alongside atomic history/projection operations. For v0.1, `resolve_session(token_digest)` is the approved authentication-bootstrap example; its exception remains limited by this ADR's credential-resolution requirements. No other ADR-002 exception is broadened.

The prior v1.1 user-seeding discrepancy is incorporated into v1.2 and is no longer a live erratum.

Implementation authority is ordered as follows:

1. Frozen FleetOps Architecture & Boundary document
2. Accepted Architecture Decision Records (ADRs)
3. Current FleetOps build handoff
4. Active slice/task prompt

The frozen Architecture & Boundary document is the highest authority. Accepted ADRs may refine implementation choices only within the frozen architecture. The current build handoff derives and coordinates implementation from the architecture and accepted ADRs. An active slice/task prompt applies the handoff to one bounded unit of work.

Each lower tier may add implementation detail, narrow scope, or impose stricter acceptance criteria, but may not contradict, weaken, silently override, or reinterpret a higher tier. When two tiers conflict, the higher tier governs and the implementer must STOP until the lower-tier conflict is corrected, rather than choose whichever instruction is easier.

A conflict with the frozen architecture is handled through the Architecture Amendment Request process. A conflict among ADRs, the handoff, and the active prompt that does not require an architecture amendment is corrected in the lower-tier document before implementation proceeds. No commit, migration, code comment, implementation shortcut, or active prompt can amend a higher-tier governing document.

FleetOps_v0.1_Build_Handoff_v1.2.docx is the current implementation handoff. After v1.2 is accepted, it supersedes v1.1 for all future implementation prompts. v1.1 remains unchanged as historical record. Supersession does not rewrite previous work or previous checkpoints. The frozen architecture remains above both handoff versions.
