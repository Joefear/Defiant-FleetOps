# ADR-007 — Asset Initial Physical-Fact Baseline

## Status

Accepted

## Context and authority

Slice 6 stopped before implementation because its proposed first-change rule made the current Asset projection the sole authority for the first movement, custody change, or ownership change. When no history existed for a class, the proposal treated the locked projection as the creation baseline and copied it into the first history row's `from_*` field.

Frozen D3 states:

> A projection may be read for convenience and for concurrency checks, but it may never be the only basis on which authoritative history is admitted: expected-state validation must be resolvable against the transition record, and reconciliation must compare the projection to history rather than to itself.

[ADR-005](ADR-005.md), Decision 2, explicitly applies that restriction to Slice 6:

> The projection remains a concurrency aid and may never be the sole basis for admitting authoritative history under D3.

For example, an Asset enters FleetOps at Location A. Before its first movement, a privileged corruption changes `current_location_id` to B. A first move to C that trusts the projection records B to C. Its resulting projection and history agree, hiding the corruption that manufactured the prior fact. Custody and ownership have the same failure mode. Locking the Asset and authenticating the performer cannot establish whether the prior physical fact is true.

At checkpoint `03d2c93d110875afaea45d3c2d73484119ab8017`, migration `0006_assets` and its metadata contain current owner, custodian, and location projections. The initial lifecycle transition records `result_version = 1`, `from_state = NULL`, and `to_state = RECEIVED`; it records none of those initial physical facts. The INSERT invariant enforces version 1 / RECEIVED, and controlled Slice 5 fixtures create the Asset and initial lifecycle transition together. Neither supplies an independent physical-fact baseline. Existing state reconciliation cannot recover facts absent from lifecycle history.

This ADR supplies the minimum immutable creation record needed to validate those first changes. Implementation authority remains:

1. Frozen FleetOps Architecture & Boundary document.
2. Accepted Architecture Decision Records.
3. Current FleetOps Build Handoff v1.3.
4. Active slice/task prompt.

The frozen [source DOCX](FleetOps_Architecture_Boundary_v0.1.docx), with its [working Markdown transcription](FleetOps_Architecture_Boundary_v0.1.md), governs this decision. [ADR-001](ADR-001.md) retains layer and privilege-boundary responsibilities; [ADR-002](ADR-002.md) retains tenancy enforcement; [ADR-003](ADR-003.md) retains identity and catalog semantics; [ADR-004](ADR-004.md), [ADR-005](ADR-005.md), and [ADR-006](ADR-006.md) retain initialization, global-version, and authenticated-Actor requirements.

This is an implementation refinement under the frozen architecture. It changes no controlled architectural requirement and requires no Architecture Amendment Request. This document-only gate does not implement or reopen Slice 6. Its exact schema and tests belong to a separately opened Slice 6 implementation after this design gate closes.

## Decision 1 — Creation requires authoritative physical facts

Every Asset requires an immutable creation baseline containing at minimum:

- `initial_owner_party_id`, non-null.
- `initial_custodian_party_id`, nullable.
- `initial_location_id`, nullable.

These facts answer what ownership, custody, and location were recorded when the Asset entered FleetOps. They provide independent authority for the first later change. Ownership and custody remain separate facts; neither may be inferred from the other. A nullable initial custodian or location represents an unknown or unrepresented fact, not a missing baseline record.

## Decision 2 — The baseline produces no separate global version

The physical baseline is creation evidence, not an additional operational change. It consumes and produces no separate global Asset version and carries no operational `result_version`.

ADR-004/005 initialization remains:

```text
Asset:                       version = 1, current_state = RECEIVED
Initial lifecycle transition: result_version = 1, NULL -> RECEIVED
```

Global version 1 is represented exactly once by the initial lifecycle transition. Do not create movement, custody-change, or ownership-change rows at `result_version = 1` to initialize their facts. Do not introduce another version counter, a version register, or additional global-version producers for creation.

## Decision 3 — One immutable baseline record per Asset

Use one tenant-owned immutable record per Asset, conceptually `asset_initial_facts`, rather than separate baseline events in the three change-history classes. Its conceptual fields are:

| Field | Meaning |
| --- | --- |
| `asset_id` | Permanent FleetOps Asset identity. |
| `org_id` | Non-null tenant scope. |
| `initial_owner_party_id` | Non-null owner at creation. |
| `initial_custodian_party_id` | Nullable custodian at creation. |
| `initial_location_id` | Nullable Location at creation. |
| `actor_id` | Authenticated cause of the creation operation. |
| `occurred_at` | Effective creation time recorded by that operation. |
| `recorded_at` | Database/server time when the baseline was recorded. |

Under D11, occurrence and record time remain separate UTC timestamps. `occurred_at` preserves the creation operation's event-time claim; `recorded_at` is database/server-set and cannot be supplied by the client. A later migration or first-change request cannot invent the effective creation time from its own clock.

The exact schema, keys, constraints, and any equally precise table name belong to Slice 6. It must enforce one baseline per tenant-scoped Asset and preserve the existing UUID identity convention. Add a source/receipt reference seam only if the governing receiving design already requires it. Do not add assignment or unrelated future facts. Calling this creation evidence does not introduce attachment storage or replace D17 evidence requirements.

## Decision 4 — The baseline is immutable

The baseline is authoritative creation history, not a maintained projection. `fleetops_app` must have no UPDATE, DELETE, or TRUNCATE privilege on it. No operation may replace or overwrite its original facts as a correction.

A future correction of creation facts must follow D6 through explicit correction history: reversing and correct entries, references to what they correct, and a stated reason. The original baseline remains intact. This ADR does not design or implement that correction workflow and does not provide a general runtime baseline-creation endpoint.

## Decision 5 — Creation is one coherent transaction

Production Asset creation remains owned by Slice 9 receiving. For each serialized Asset, that creation transaction must create coherently:

- The Asset projection at version 1 / RECEIVED.
- The initial immutable lifecycle transition at result version 1 / NULL to RECEIVED.
- The initial physical-fact baseline.
- Receiving provenance and identifier records required by Slice 9.

The baseline and initial projections must describe the same owner, custodian, and location, established together from the validated creation facts. They must not be reconstructed later from whichever values the projections then contain. The creation operation records authenticated attribution and the applicable occurrence/record times across its records.

Slice 6 may create coherent Asset, initial-transition, and baseline triples only through controlled test fixtures using the established privileged setup convention. It does not introduce `POST /assets`, manual onboarding, or another production creation shortcut. Slice 9 still owns the serialized-Item rule, receipt linkage, and identifier or unreadable-marker requirements.

## Decision 6 — No migration-time projection backfill

Do not populate the baseline during migration by copying current Asset projections. An operation equivalent to the following is prohibited merely because history or a baseline is missing:

```text
INSERT baseline SELECT owner_party_id, custodian_party_id, current_location_id
FROM assets
```

Migration privilege does not turn a potentially corrupted current value into authoritative creation evidence. An existing Asset without an authoritative baseline remains explicitly incomplete. No migration-time synthetic change-history rows or inferred creation facts may hide that incompleteness.

## Decision 7 — Missing baseline fails first-change admission closed

If a Slice 6 operation is the first change of its history class and the Asset has no initial physical-fact baseline, reject it without writes. Do not trust the projection, insert a baseline lazily, infer it from current time, synthesize history, or silently repair the Asset.

Slice 6 physical-fact reconciliation reports a missing authoritative baseline as a discrepancy. The absence of a baseline row is distinct from a present baseline whose initial custodian or location is NULL. Before production receiving exists, incomplete Assets will primarily be controlled fixtures or development data; their presence does not authorize a production onboarding or repair path.

## Decision 8 — First movement validates the initial Location

Resolve trusted tenant and credential-derived Actor authority under ADR-002/006, then follow the shared ADR-005 protocol:

1. Identify the tenant-scoped Asset and acquire its `SELECT ... FOR UPDATE` row lock.
2. Only after acquiring the lock, validate `expected_version = N` against the locked Asset version.
3. Determine whether movement history exists using authoritative `result_version` ordering.
4. If no movement history exists, load the same-tenant immutable baseline and require `assets.current_location_id` to equal `baseline.initial_location_id`, including NULL equality semantics.
5. Reject a missing baseline or mismatching projection without history, projection, or version writes.
6. On agreement and satisfaction of the other movement preconditions, derive `from_location_id` from `baseline.initial_location_id`; append the requested destination with `result_version = N + 1`; update only `current_location_id` and global `version` atomically under the retained lock.

NULL-safe equality means two NULL values agree and NULL versus a non-null value disagrees, as with PostgreSQL `IS NOT DISTINCT FROM`. Destination validation and tenant-safe references remain required.

Once movement history exists, its latest row by `MAX(result_version)` supplies the authoritative prior Location. Validate the projection against that row's `to_location_id`, reject a history version ahead of the locked Asset version, and derive the next `from_location_id` from that history. The creation Location does not constrain a legitimately changed current Location.

## Decision 9 — First custody change validates the initial custodian

Use the same authenticated, tenant-scoped Asset lock and post-lock version validation. Before the first custody change, require `assets.custodian_party_id` to equal `baseline.initial_custodian_party_id` with the NULL-safe semantics in Decision 8. Missing baseline or disagreement rejects without writes.

Derive the first `from_custodian_party_id` from the immutable baseline. After custody history exists, validate against and derive the prior custodian from the latest custody row's `to_custodian_party_id`, ordered by `result_version`. Its result version must not exceed the locked Asset version.

A successful change records `result_version = N + 1` and updates only `custodian_party_id` and global `version` atomically. Nullable custody remains valid; owner, location, lifecycle state, and assignment do not change implicitly.

## Decision 10 — First ownership change validates the initial owner

Use the same authenticated, tenant-scoped Asset lock and post-lock version validation. Before the first ownership change, require `assets.owner_party_id` to equal `baseline.initial_owner_party_id`. Missing baseline or disagreement rejects without writes.

Derive the first `from_owner_party_id` from the immutable baseline. After ownership history exists, validate against and derive the prior owner from the latest ownership row's `to_owner_party_id`, ordered by `result_version`. Its result version must not exceed the locked Asset version.

The baseline owner and requested new owner must be non-null same-organization Parties. Every Asset continues to have an owner. A successful change records `result_version = N + 1` and updates only `owner_party_id` and global `version` atomically; it does not implicitly change custody, location, lifecycle state, or assignment.

## Decision 11 — Later operations preserve the baseline

Movement, custody change, ownership change, lifecycle transition, assignment, descriptive edits, and later operations do not modify the initial baseline. It remains the record of the physical facts captured at creation. Current projections and temporal change history evolve independently of that immutable record.

This requirement also applies when an operation returns a physical fact to its initial value. Returning to the same Location or Party is a later event, not replacement of creation history.

## Decision 12 — Reconstruction starts with the baseline

A complete physical-fact reconstruction uses the initial baseline followed by that class's change history in ascending `result_version` order. For location, this is `initial_location_id`, then each movement's prior/destination facts. Custody and ownership use their corresponding baseline and prior/new Party history.

The baseline exposes the initial fact even before any changes occur. A NULL initial Location or custodian remains an explicit unknown or unrepresented value; reconstruction must not invent one. Occurrence timestamps remain event-time claims and must not replace produced-version ordering of the changes. This decision supports the frozen acceptance requirement to reconstruct every Location without introducing a reporting subsystem.

## Decision 13 — Reconcile against the applicable history authority

For each tenant-scoped Asset, choose the authority independently for each physical fact:

| Projection | No change history for this class | Change history exists |
| --- | --- | --- |
| `current_location_id` | `baseline.initial_location_id` | Latest movement `to_location_id`. |
| `custodian_party_id` | `baseline.initial_custodian_party_id` | Latest custody change `to_custodian_party_id`. |
| `owner_party_id` | `baseline.initial_owner_party_id` | Latest ownership change `to_owner_party_id`. |

Use NULL-safe comparisons where facts are nullable. A missing baseline is a discrepancy; later change history does not restore missing creation truth. No change history by itself is not corruption when the baseline exists and the projection agrees. Once a class has history, a difference from its initial baseline is normal if the projection agrees with that class's latest authoritative row.

Latest means `MAX(result_version)`, never timestamp, UUID, or insertion order. A latest class version greater than `assets.version` remains a discrepancy; a lower class version alone is valid. Owner remains non-null. Preserve the existing lifecycle state reconciliation separately. Extend the authenticated tenant-scoped health surface to report missing baseline and physical-fact mismatches without silent repair; exact response details belong to Slice 6.

## Decision 14 — Global reconciliation excludes the baseline

Combined global-version reconciliation includes only the events that produced global Asset versions:

- `asset_transitions`.
- `asset_movements`.
- `asset_custody_changes`.
- `asset_ownership_changes`.
- Later version-producing classes when their slices introduce them.

The initial lifecycle transition supplies version 1. The physical baseline supplies fact authority and is excluded from this version-producing union/query. For a coherent Asset, every version from 1 through `assets.version` must still appear exactly once across producing history. Missing versions, duplicates across classes, and versions ahead of the Asset remain detectable; per-class gaps remain valid.

`asset_initial_facts` must not become a version register or shared sequence table. Baseline completeness and combined version completeness are separate checks; passing one cannot excuse failure of the other.

## Decision 15 — Baseline attribution follows ADR-006

Production baseline creation records the authenticated Actor causing the Slice 9 receiving/create operation. Actor authority must be derived or enforced at the durable database boundary through `current_authenticated_actor()` and the existing credential mechanism. No request field, SQL Actor selector, arbitrary Actor GUC, Party identity, or organization context alone may choose the performer.

Missing, invalid, expired, revoked, inactive, or tenant-mismatched credential authority fails closed under ADR-006. Controlled fixtures may use explicit independent migrator/admin setup as already governed; runtime execution through a SECURITY DEFINER function does not acquire that administrative exemption. This ADR adds no credential-issuance path or machine authentication mechanism.

## Decision 16 — The baseline is tenant-owned

The baseline has non-null organization scope and tenant-safe relationships to its Asset, owner Party, nullable custodian Party, nullable Location, and Actor. Cross-organization relationships must reject durably through composite tenant-safe foreign keys under ADR-002.

Apply the established RLS mechanism with both USING and WITH CHECK protection, fail-closed missing-context behavior, and no runtime TRUNCATE. Any elevated creation boundary must explicitly validate trusted organization and references rather than depend on owner RLS. Preserve ADR-006's independent credential domains and restricted runtime privileges. Tests asserting tenant isolation must execute as `fleetops_app`, not as a table owner.

## Decision 17 — Creation and change history have distinct authority

The baseline is authoritative only for the physical facts recorded at creation. It does not replace movement, custody, ownership, lifecycle, or receiving history. Each later change table remains authoritative for its own temporal events, and receiving records retain their provenance and physical-receipt authority.

The initial record must never become a mutable current-facts table or compete with change history for the current value. Before the first change it supplies the prior fact; after changes it remains the starting point for reconstruction.

## Decision 18 — Scope is limited to the creation-baseline seam

This ADR authorizes only the minimum design needed for D3-compliant first-change admission. A separately opened Slice 6 may implement the baseline schema, controlled fixtures, admission, reconciliation, and required proofs. This gate creates only this ADR and implements none of them.

It does not authorize assignment or an assignment baseline, configuration, receipts, purchase orders, corrections, evidence storage, offline capture, material inventory, or a version register. Production receiving remains Slice 9. The baseline does not weaken the current evidence seam, retirement restrictions, serialized-Item eligibility, Location reparenting deferral, or the prohibition on production manual Asset creation.

## Bounded handoff refinement

[Build Handoff v1.3](FleetOps_v0.1_Build_Handoff_v1.3.docx), Slice 6, leaves exact initialization/schema details to the opened slice while retaining history-verified admission. The invalid rule arose in the lower-tier Slice 6 prompt; it is not an existing v1.3 grant of projection-only authority.

Replace that lower-tier rule:

> When no class history exists, the current projection alone is the baseline.

With:

> When no class change history exists, validate the current projection against the immutable Asset initial physical-fact baseline and derive the first from_* value from that baseline.

This refinement supplies the missing first-change authority and its creation/reconciliation consequences. The one necessary Slice 9 consequence is atomic creation of the baseline alongside the already-required Asset, initial transition, and receiving provenance. It does not bring that workflow into Slice 6 or redesign receiving.

All other v1.3 Slice 6 obligations remain governing, including immutable history, authenticated Actor binding, explicit tenant checks, the shared Asset row lock, post-lock expected-version validation, N to N + 1 production, orthogonality, cross-class contention, per-class and global reconciliation, inert correction/client seams, and required prior regressions. The frozen architecture, ADR-001 through ADR-006, and v1.3 remain unchanged as source documents.

## Required Slice 6 test implications

These are future implementation obligations, not tests introduced or claimed to pass by this document-only gate. At minimum, Slice 6 must prove:

1. A coherent baseline and matching projection permit the first movement; its `from_location_id` comes from the baseline, including a NULL initial Location.
2. Privileged corruption of location before the first movement causes rejection, no history/version/projection writes, and no repair.
3. A coherent baseline and matching projection permit the first custody change, with its prior custodian derived from the baseline, including NULL custody.
4. Privileged corruption of custody before the first custody change causes rejection with no writes or repair.
5. A coherent baseline and matching projection permit the first ownership change, with its prior owner derived from the non-null baseline owner.
6. Privileged corruption of owner before the first ownership change causes rejection with no writes or repair.
7. Missing baseline causes all three first-change operations to fail closed without lazily creating a baseline or writing history.
8. No change history plus baseline/projection agreement reconciles cleanly, including agreement between nullable facts.
9. No change history plus baseline/projection mismatch reports a discrepancy, including NULL versus non-null mismatches; missing baseline is also reported distinctly from nullable facts.
10. Later movement validates against latest movement history rather than the original baseline, including a legitimate current Location differing from the initial one.
11. Later custody change validates against latest custody history rather than the original baseline.
12. Later ownership change validates against latest ownership history rather than the original baseline.
13. All three operation classes leave the complete baseline unchanged; runtime UPDATE, DELETE, and TRUNCATE on it are denied, and other existing operations cannot mutate it.
14. The baseline consumes no separate global version, carries no operational `result_version`, and is excluded from combined version reconciliation.
15. Global version 1 remains represented exactly once by the initial lifecycle transition, with no version-1 movement, custody, or ownership rows.
16. The forward migration performs no projection backfill: pre-existing Assets without baselines remain incomplete and reconcile as such. Migration round-trip checks preserve that rule and prior schema/security contracts.
17. Baseline relationships to Asset, owner, custodian, Location, and Actor reject cross-tenant references durably; RLS, missing-context behavior, one-baseline-per-Asset cardinality, required owner, and no-TRUNCATE restrictions are proved.
18. Baseline Actor attribution is enforced at the database boundary under ADR-006: a valid runtime credential binds its Actor, while same-org spoofing and organization-only authority fail. Slice 6 must exercise that invariant as `fleetops_app` through isolated test-only INSERT grants or an equivalent controlled probe, restoring production restrictions afterward. Privileged fixture attribution alone does not prove runtime binding. No production creation surface is introduced; Slice 9 must additionally prove authenticated baseline creation in its receiving transaction.

Database, immutability, and concurrency proofs use real PostgreSQL 16. Keep all unaffected v1.3 Slice 6 proofs, including five movements, equivalent custody/ownership sequences, corrupted later projections, shared-lock cross-class races, and complete/missing/duplicate/ahead global versions. Do not weaken existing tests to accommodate the baseline. Slice 9 must additionally prove its coherent creation transaction rolls back as a unit and preserves the original acceptance scenario.

## Architecture consistency and implementation gate

- **D3:** The initial baseline provides independent history authority before the first class change; later history provides it afterward. A projection never validates itself.
- **D6/D7:** Creation facts remain immutable, ownership and custody remain independent, and complete physical-fact timelines retain their initial facts and every later change.
- **D8/D12 and ADR-005:** Orthogonal operations preserve unrelated facts and contend on the same global Asset version and retained row lock. The baseline adds no version producer.
- **D10/D11/D18 and ADR-002/006:** Authenticated Actor attribution, separate UTC occurrence/record times, credential boundaries, and tenant-safe references remain mandatory.
- **ADR-004 and v1.3:** Version 1 / RECEIVED initialization, initial lifecycle history, serialized-Item eligibility, evidence/retirement restrictions, and receiving-owned production creation remain intact. The frozen acceptance scenario and deferred scope are unchanged.

No architectural amendment is needed for this independent immutable baseline. Implementation must STOP if it instead requires weakening D3, a second global version, a mutable or lazily synthesized baseline, production creation in Slice 6, or a version-register table. A conflict with the frozen architecture follows its change-control process; it cannot be resolved by an implementation shortcut.

This ADR records the design decision only. It creates no production capability, migration, test, correction workflow, or receiving implementation, and it does not itself begin Slice 6.
