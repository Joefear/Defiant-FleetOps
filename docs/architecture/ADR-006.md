# ADR-006 — Credential Issuance and Authenticated Actor Binding

## Status

Accepted

## Context and authority

Slice 5 review found that `transition_asset` can record another active same-organization Actor, that direct descriptive Asset UPDATE can retain false prior updater attribution, and that ordinary Asset INSERT does not enforce version 1 / RECEIVED initialization. The subsequent [corrective hardening report](../development/SLICE_5_CORRECTIVE_HARDENING_REPORT.md) records independent PostgreSQL reproductions and a deeper authentication defect.

[ADR-002](ADR-002.md) established opaque bearer sessions and `resolve_session(token_digest)` as the credential-resolution boundary. At committed checkpoint `e99397e6802ce7db68f58a7894302553b39bf8f1`, `0002_identity_auth.py` and the runtime grant helper also give `fleetops_app` ordinary SELECT and INSERT on users and sessions. Login verifies a password in Python and inserts a session using that same runtime role. Logout directly updates the session's active flag, and the separate bootstrap command uses runtime user INSERT.

Independent runtime-role probes confirmed that `fleetops_app` can choose an existing same-tenant user, choose a token digest it knows, insert a session, resolve that digest, and impersonate the linked HUMAN Actor without that user's password or original token. The role can also read another user's stored session digest. Hiding digest reads alone leaves credential issuance available. A role that can mint a credential cannot use possession of that credential as proof against itself.

The same weakness affects attribution-bearing writes. Current Actor, Party, Item, external-reference, Facility, and Location services pass performing Actor IDs from the HTTP dependency into ordinary SQL. The HTTP context is authenticated, but a same-role SQL caller can supply a different same-tenant Actor. Item and candidate Asset services also set updater attribution and database time themselves. Tenant-safe foreign keys prove tenant membership; they do not prove the authenticated cause of an operation. D10 requires that authenticated cause for consequential changes.

This ADR establishes a separate credential-issuance boundary and reusable database attribution derived from a credential that `fleetops_app` cannot mint or enumerate. Implementation authority remains:

1. Frozen FleetOps Architecture & Boundary document.
2. Accepted Architecture Decision Records.
3. Current Build Handoff v1.2.
4. Active slice/task prompt.

The frozen [source DOCX](FleetOps_Architecture_Boundary_v0.1.docx), with its [working Markdown transcription](FleetOps_Architecture_Boundary_v0.1.md), governs this ADR. This is an implementation decision subordinate to that architecture. The bounded supersession below refines prior implementation choices without modifying the earlier ADRs or [Build Handoff v1.2](FleetOps_v0.1_Build_Handoff_v1.2.docx). This document-only gate implements nothing and claims no Slice 5 fix.

## Decision 1 — Three execution privilege domains

v0.1 uses three distinct database privilege domains:

| Domain | Purpose and authority |
| --- | --- |
| `fleetops_migrator` | Schema/migration owner, deployment and administrative use only. Ordinary API requests never use it. |
| `fleetops_app` | Ordinary authenticated FleetOps runtime with RLS-protected domain access and permission to resolve a presented bearer credential. It cannot issue users or bearer credentials. |
| `fleetops_authenticator` | Narrow login-only database credential/role, used only by `POST /auth/login` for the minimum password-verification reads and issuance of one bearer session. It has no ordinary domain mutation authority. |

The app and authenticator credentials are separate server-side secrets, with separate connection paths. `fleetops_app` MUST NOT be a member of `fleetops_authenticator`, execute `SET ROLE fleetops_authenticator`, inherit its privileges, or reach them through an indirect membership or other privilege path. Neither operational credential may assume migrator authority. Authenticator authority must likewise not inherit or assume the ordinary app role.

A LOGIN role backed by a NOLOGIN privilege role is an acceptable implementation if independent credentials and the absence of escalation paths are preserved. This explicitly refines the prior two-role database convention; it does not introduce an application-user role hierarchy.

## Decision 2 — Authenticator is not a general application role

`fleetops_authenticator` exists only for the unauthenticated login boundary. It must not receive:

- Asset mutation, Item/catalog mutation, Party mutation, Actor mutation, or Facility/Location mutation privileges.
- `transition_asset` EXECUTE, movement or assignment privileges, or history mutation authority.
- Schema CREATE, role administration, TRUNCATE, BYPASSRLS, superuser authority, or ownership of tenant tables.

Its grants are limited to the minimum organization-scoped login reads and the session-issuance interface. Its credential must not automatically confer ordinary FleetOps SQL operational authority. Issuing credentials is itself trusted authority: compromise of the issuer can produce impersonating sessions. This design does not claim that a compromised issuer is harmless or that database role separation protects against compromise of the entire server process holding both secrets. Decision 20 defines that trust limit explicitly.

## Decision 3 — `fleetops_app` loses credential issuance

`fleetops_app` must have no direct ability to create authentication authority. Remove privileges allowing it to INSERT users, INSERT sessions, create password-bearing users, replace session credential material, or enumerate stored session-token digests. It must not alter password material, session-to-user links, or user-to-Actor links to turn a known credential into another identity.

The preferred runtime grant set provides no direct users/sessions table access. A specific remaining operation may justify only narrower, non-secret column access; login, resolution, and logout do not justify broad table privileges under this ADR. Direct SELECT of session digests is prohibited. Authentication resolution uses the approved resolver, not table inspection. Direct session UPDATE, including the old active-column logout grant, is removed under Decision 17.

Grant helpers and later migrations must preserve these removals rather than restoring the prior SELECT/INSERT defaults. Table, column, inherited, and PUBLIC privileges must all be considered.

## Decision 4 — `resolve_session` remains the only context-free resolver

Preserve the ADR-002 interface and behavior:

```text
resolve_session(token_digest)
```

It accepts only an exact SHA-256 session digest and returns at most the minimal organization/user/HUMAN Actor tuple. It returns no bearer token, digest, or password hash, validates session activity and expiry plus active same-organization user/HUMAN Actor relationships, and modifies nothing. Unknown, expired, revoked, or otherwise invalid credentials resolve no identity.

It remains the only authentication resolver permitted without existing organization context. No username, Actor ID, user ID, session ID, organization ID, enumeration filter, or alternate lookup key becomes a context-free authentication lookup. Its migrator ownership, safe object resolution, revoked PUBLIC EXECUTE, and intended runtime EXECUTE restriction remain intact. No context-free login-user resolver is introduced.

## Decision 5 — Login uses the authenticator credential

`POST /auth/login` uses a separate authenticator database engine/connection, never the ordinary app engine for issuance:

1. Trusted single-org v0.1 server configuration establishes transaction-local login organization scope.
2. The authenticator reads only the user and linked HUMAN Actor fields required for password verification and validity checks, through organization-scoped RLS access.
3. Python verifies Argon2id exactly as today, including invalid/unknown-user handling. Argon2 remains in Python and its parameters must not be weakened.
4. On success, Python generates a cryptographically secure bearer token with at least 256 bits of source entropy and computes its SHA-256 digest.
5. The authenticator invokes `issue_session` in the scoped login transaction.
6. After successful issuance, the raw bearer token is returned once as the client credential, with ordinary non-secret session metadata where needed.

The raw token is never stored. Bad password or unknown user returns 401 and writes no session. Inactive user or Actor cannot receive a valid session. Login scope comes from trusted configuration, not the request. Authenticator RLS must fail closed without scope; minimum column grants do not substitute for tenant isolation.

The server's configuration and connection validation must distinguish the app and authenticator credentials and actual execution roles. No privileged fallback is permitted. The authenticator engine is used only in login code, and ordinary authenticated request dependencies use the app engine.

## Decision 6 — Narrow `issue_session` privilege boundary

This ADR explicitly approves an [ADR-001](ADR-001.md) Category-2 privilege-boundary function, conceptually:

```text
issue_session(user_id, session_id, token_digest, expires_at)
```

Exact parameter order/names follow implementation conventions. The function is owned by `fleetops_migrator`, uses a fixed safe `search_path` and qualified references, has PUBLIC EXECUTE revoked, denies `fleetops_app` EXECUTE, and grants runtime EXECUTE only to `fleetops_authenticator`. SECURITY DEFINER is permitted only as needed to cross this narrow privilege boundary. The authenticator should not need direct sessions INSERT.

The function must:

- Require trusted login organization context; accept no organization or Actor ID argument.
- Verify the target user belongs to that organization and is active.
- Verify the linked Actor is HUMAN, active, and belongs to the same organization through tenant-safe relationships.
- Validate the digest's exact SHA-256 shape and the session expiry rules against database time, rejecting missing, non-finite, expired, or out-of-policy expiry. Preserve the bounded server session-lifetime policy.
- Insert only one new session record, with database-controlled creation time and the validated organization/user relationship.
- Return no token digest or password material; create no users and modify no existing sessions. Duplicate identity or digest must not become an upsert.

Its narrow justification is that ordinary runtime session INSERT would let the constrained role manufacture authentication authority. The function validates issuance inputs; it does not prove password verification. That proof rests on trusted Python login code and the independently protected authenticator credential.

## Decision 7 — Bootstrap user is admin/deployment only

The one-time bootstrap command no longer relies on `fleetops_app` INSERT on users. It uses an explicit deployment/admin privilege path, such as `fleetops_migrator` or another already-authorized deployment mechanism, separate from ordinary request engines.

Bootstrap remains outside migrations, reads credentials and organization from trusted configuration/environment, hashes the password with Argon2, persists no plaintext credential, refuses overwrite, and links the initial user to the migration-seeded organization and active HUMAN Actor. Existing retry/concurrency protection must remain effective.

Do not give the authenticator user-creation authority for bootstrap convenience. No fourth always-on runtime privilege role is introduced solely for bootstrap, and no user-management workflow is added.

## Decision 8 — Session digest is credential-equivalent material

Only after `fleetops_app` can no longer mint or enumerate valid session digests may possession of a valid digest serve as database-side proof corresponding to the presented bearer credential. Treat that digest as credential-equivalent material inside the server/database boundary.

A digest must never be returned by API responses, exposed by direct app-role table SELECT, intentionally logged, included in repr/debug output, or accepted as an alternate credential in request JSON, query parameters, or arbitrary headers. The client presents the raw bearer token through the existing bearer authentication path; Python derives the digest.

Credential handling must avoid disclosure through SQL text, bound-parameter logging, error details, and diagnostics accessible to other runtime requests. Parameter and exception handling must preserve confidentiality. The one-time login response is the required raw-token delivery; raw tokens must not appear in other API responses or logging. No raw token is stored in reusable plaintext form.

## Decision 9 — Transaction-local credential context

After the request successfully follows:

```text
presented bearer token -> SHA-256 digest -> resolve_session(digest)
```

the authenticated request transaction establishes both transaction-local organization context and transaction-local credential-digest context. A GUC such as `fleetops.session_digest_hex` is an acceptable representation; its exact name is an implementation detail.

Use transaction-local settings. Commit, rollback, exceptions, and connection reuse must end the request's authority; neither context may leak into the next pooled request. Persistent session-level settings are not the request mechanism.

The GUC is not trusted merely because it is a GUC. Database attribution must re-resolve its credential value against the session authority. Do not introduce `fleetops.actor_id` as an authority shortcut or trust an Actor UUID placed in any caller-settable context.

## Decision 10 — Current authenticated Actor resolver

This ADR explicitly approves a second narrow ADR-001 Category-2 helper:

```text
current_authenticated_actor()
```

It accepts no Actor ID or alternative identity input, requires existing organization and credential contexts, and:

1. Reads the digest from transaction-local credential context.
2. Validates exact encoding and length; a hex representation must encode precisely one 32-byte SHA-256 digest.
3. Resolves it through `resolve_session` or the same credential/session authority without weakening that resolver's checks.
4. Requires the resolved organization to equal the current organization context.
5. Requires the session, user, and linked HUMAN Actor still to be valid.
6. Returns only that Actor ID.

Missing, malformed, unknown, expired, revoked, or inactive credentials fail closed, as do missing or mismatched organization contexts. Failed resolution must not become nullable attribution or a fallback Actor. The helper does not cache an Actor UUID as authority independent of the credential.

It is narrowly justified as sharing credential validation across durable attribution boundaries while keeping credential tables hidden from `fleetops_app`. Use migrator ownership, fixed safe object resolution, revoked PUBLIC EXECUTE, and runtime EXECUTE only for `fleetops_app`; SECURITY DEFINER is permitted only if required for this boundary. It changes no tenant-owned data.

An arbitrary guessed digest gains nothing. Writing Actor B's UUID into a GUC cannot establish B. Possession of an actually valid credential remains bearer authority; protecting credential issuance and confidentiality is essential to this guarantee.

## Decision 11 — HUMAN session authority in v0.1

The current HTTP mechanism authenticates HUMAN Actors. SYSTEM, DEVICE, and INTEGRATION Actor rows remain valid domain identities and need not have user rows. Their mere existence does not grant runtime execution authority to callers supplying those IDs.

A HUMAN session may create a typed Actor record while attributing its creation to the authenticated HUMAN. Deliberate administrative fixtures can represent typed history without claiming a production machine-login mechanism. Future machine/integration credentials require an explicit authentication design; this ADR does not implement them or pull them into Slice 5.

The existing typed-Actor requirement remains. It must not be interpreted as permission for unauthenticated non-HUMAN attribution in ordinary runtime SQL.

## Decision 12 — Database-bound attribution

For runtime writes carrying `created_by_actor_id`, `updated_by_actor_id`, or performing `actor_id`, the database must derive or enforce attribution through `current_authenticated_actor()` or an equivalent mechanism backed by the same verified credential. Another active same-org Actor is not an acceptable substitute.

The corrective implementation must audit at least these existing and candidate surfaces:

| Surface | Attribution requiring enforcement | Current write boundary |
| --- | --- | --- |
| Actors | `actors.created_by_actor_id` | Ordinary runtime INSERT |
| Parties | `parties.created_by_actor_id` | Ordinary runtime INSERT; related role-set creation remains atomic |
| Items | `items.created_by_actor_id`, `items.updated_by_actor_id` | Ordinary runtime INSERT and permitted descriptive/default UPDATE |
| External references | `external_references.created_by_actor_id` | Ordinary runtime INSERT |
| Facilities | `facilities.created_by_actor_id` | Ordinary runtime INSERT |
| Locations | `locations.created_by_actor_id` | Ordinary runtime INSERT; reparenting remains deferred |
| Assets | `assets.created_by_actor_id`, `assets.updated_by_actor_id` | Candidate descriptive UPDATE; production creation remains deferred |
| Asset identifiers | `asset_identifiers.created_by_actor_id` | Candidate capture attribution; no new production INSERT grant or route |
| Asset transitions | `asset_transitions.actor_id` | Existing candidate atomic transition function |

Use narrowly scoped reusable trigger invariants for ordinary writes and the existing atomic function boundary where appropriate. This authorizes the attribution invariant mechanism, not a general-purpose dynamic SQL privilege helper or one stored procedure per ordinary table. Keep trigger helpers SECURITY INVOKER where the credential resolver and row assignment suffice; any necessary elevation is confined to the approved authentication/attribution boundary and its explicit target/tenant checks. PostgreSQL must not become a stored-procedure application.

This audit does not grant previously unavailable DML, add routes, or turn identity references such as a user's linked Actor into performing-Actor fields. Preserve tenant-safe relationships, permanent identity, original creator protection, immutable history, and projection restrictions.

## Decision 13 — INSERT attribution

On every ordinary runtime INSERT into an attribution-bearing table, the resulting creator/performing Actor must equal the Actor resolved from the current valid credential. The database may derive/overwrite creator attribution or reject a supplied mismatch. A different supplied Actor must never persist, including when it belongs to the same organization.

Python validation is insufficient by itself. Initial updater attribution, where present on the new row, must also be truthful. Privileged migrator/test setup remains a deliberate administrative bypass, not ordinary runtime authority. Runtime calls through SECURITY DEFINER functions must still enforce attribution; elevated effective ownership inside such a call must not accidentally turn runtime work into exempt administrative setup.

## Decision 14 — UPDATE attribution

For runtime UPDATE of mutable fields whose row carries updater attribution, every successful consequential/descriptive mutation atomically records:

```text
updated_by_actor_id = current authenticated Actor
updated_at = database/server time
```

The caller cannot retain a stale prior Actor or timestamp, choose another same-org Actor, or supply an authoritative update timestamp. This applies to Item updates and candidate Asset tag/description updates even when direct SQL omits all attribution columns. Attribution-only input must not provide a way to falsify the row.

Preserve permitted direct descriptive SQL and the handoff's distinction between descriptive and protected projection columns. HTTP PATCH remains limited to its permitted descriptive fields, and Asset descriptive edits leave global Asset version and lifecycle history unchanged. No descriptive-metadata history subsystem is introduced. Original creator attribution remains protected.

## Decision 15 — `transition_asset` no longer trusts `actor_id`

ADR-006 refines ADR-004 Decision 6's conceptual signature so the durable transition function derives its HUMAN Actor from authenticated credential context. The preferred final SQL interface removes caller-authoritative `actor_id`.

If temporarily retaining the parameter for compatibility, the database function must require equality with `current_authenticated_actor()` and reject mismatch before any history or projection write. An old executable overload that still trusts the argument must not remain available. Removing the unnecessary parameter is preferred.

ADR-004 already requires authenticated attribution; this ADR replaces the implementation assumption that passing a service-selected Actor into SQL sufficiently enforces it. All other ADR-004/005 transition semantics remain unchanged: explicit tenant checks, active identity, lock before expected-version comparison, history-verified admission, valid global-version gaps, atomic history/projection/version updates, lifecycle legality in Python, evidence seam, and fail-closed retirement.

## Decision 16 — Future versioned functions share the principal boundary

Future `move_asset`, `change_custody`, `change_ownership`, `assign_asset`, and `unassign_asset` must derive runtime Actor authority through this same authenticated-principal mechanism. Each slice must not invent its own authoritative Actor input.

This requirement is independent of ADR-005's shared Asset row lock and global-version protocol; both apply. It defines a future obligation, not permission to start those workflows or create their schemas now.

## Decision 17 — Logout without direct session UPDATE

This ADR approves the narrow ADR-001 Category-2 function:

```text
revoke_current_session()
```

It is invoked only by an already authenticated request, requires organization and credential context, resolves that credential with the same validity and organization checks, and deactivates only the exact matched session. It accepts no user ID, Actor ID, or arbitrary session ID, cannot select or revoke another session, and returns no credential material. It cannot reactivate a session, extend expiry, or alter identity links or digest material.

Use migrator ownership and a fixed safe `search_path`/qualified references, with SECURITY DEFINER only as required to mutate the otherwise inaccessible session row. Revoke PUBLIC EXECUTE and grant runtime EXECUTE only to `fleetops_app`. The authenticator does not receive this runtime authority.

The justification is current-session revocation without exposing session storage or granting direct session UPDATE. Resolving an Actor alone is insufficient to choose a session: revocation must identify the exact current digest, not all sessions for that Actor. Logout and revocation participate in the request transaction, and missing/invalid context fails closed.

## Decision 18 — New helpers are not context-free

| Operation | Required context | Intended runtime caller |
| --- | --- | --- |
| `resolve_session(token_digest)` | Exact presented digest; no pre-existing organization required | `fleetops_app` |
| `issue_session(...)` | Trusted configured login organization | `fleetops_authenticator` |
| `current_authenticated_actor()` | Organization and valid credential context | `fleetops_app`, including its invariant/function paths |
| `revoke_current_session()` | Organization and valid credential context | `fleetops_app` |

Ownership/admin execution is distinct from runtime EXECUTE grants. Only `resolve_session` retains the context-free authentication-resolution exception. None of the new helpers broadens it. Every elevated tenant operation still performs explicit organization and tenant-safe relationship checks rather than relying on owner RLS behavior.

## Decision 19 — Organization GUC still is not authentication

Preserve ADR-002: `fleetops.org_id` or equivalent context represents tenant scope, not authentication. An app transaction with only organization context and no valid credential context must not produce a runtime attribution-bearing consequential write claiming an authenticated Actor.

Tenant selection and Actor authentication are distinct facts. A valid credential for organization B paired with organization A context must fail at the attribution boundary. The trusted configured-org login path belongs to the separate authenticator domain and does not make app-role organization-only writes authenticated.

## Decision 20 — Session issuance is the trusted login seam

PostgreSQL does not independently verify Argon2 passwords. Python does. `issue_session` must not be described as proving that a password was checked: it validates the session inputs presented by the trusted issuer.

The separate authenticator credential is the deliberate trust boundary between password-verification/login code and ordinary `fleetops_app` runtime SQL. It must be independently protected, narrowly privileged, unavailable through app-role assumption, used only by login code, and denied domain mutation authority. A role with only app credentials cannot manufacture a session as an alternative to knowing a valid credential.

Issuer compromise remains authentication compromise because it can mint sessions. Separation prevents app-role SQL from inheriting issuer power and prevents authenticator SQL from directly performing domain operations; it does not claim to prevent misuse of legitimately issued bearer credentials after issuer compromise. Maintaining this distinction is necessary to describe the boundary truthfully.

## Decision 21 — Initial Asset INSERT remains a separate finding

The third Slice 5 blocker remains valid and needs no new authentication architecture. After this ADR's independent review and commit, the reopened corrective gate must add durable INSERT-specific enforcement requiring:

```text
new Asset.current_state = RECEIVED
new Asset.version = 1
```

The invariant must apply to ordinary owner/migrator INSERT while enabled, yet permit later legitimate transition updates of state/version. Defaults alone are insufficient; a static CHECK that prevents later transitions is inappropriate.

Initial history remains a separate coherent fixture/receiving concern: `result_version = 1`, `from_state IS NULL`, `to_state = RECEIVED`. No automatic history-creation trigger or production Asset creation route is introduced here. Slice 9 receiving retains production creation authority. This document does not implement the invariant.

## Bounded supersession

ADR-006 supersedes only these implementation assumptions and their repeated implications:

1. **ADR-002 login and its handoff application:** `fleetops_app` may perform successful-login session INSERT using ordinary table privileges. Login instead uses configured-org authenticator access and the approved issuance boundary; Python password verification remains.
2. **ADR-002 login/logout/bootstrap access:** the ordinary app role needs user/session SELECT/INSERT or direct active-column session UPDATE. Credential reads/issuance move to the narrow login boundary, logout moves to exact-current-session revocation, and bootstrap uses deployment/admin authority.
3. **Handoff v1.2 section 2.3:** two database privilege domains suffice. Three independently bounded execution domains replace that convention, without introducing user-facing authorization roles.
4. **ADR-004 Decision 6:** a passed `actor_id` can serve as the database's authoritative execution Actor. Prefer removing it; otherwise verify equality to the credential-derived Actor. ADR-004's authenticated-cause requirement is preserved, not retroactively characterized as permission to spoof.

ADR-001's Category-2 rule remains governing. This ADR supplies the explicit, narrow authorization required for issuance, current Actor resolution, revocation, and their reusable attribution invariants; it gives no blanket permission for additional privileged procedures.

Where earlier credential-table tests require direct app SELECT to return zero rows without scope, the stronger removal of SELECT means permission denial is the production behavior. Preserve fail-closed RLS tests through isolated test-only privileges where needed, and add production privilege-denial proofs. This changes only the superseded access expectation, not tenant isolation. Existing typed-Actor fixture proofs do not authorize caller-selected machine execution identities.

This ADR does not supersede bearer entropy/storage rules, SHA-256 digest convention, Argon2 convention/parameters, exact-digest `resolve_session` behavior, RLS tenant isolation, transaction-local organization context, tenant-safe references, ADR-003 catalog identity, ADR-005 global Asset version/locking, immutable history, projection restrictions, lifecycle graph, evidence seam, or receiving-owned creation. Prior ADRs and the handoff remain unchanged as source documents.

## Required future adversarial proofs

Implementation must prove at least the following against real PostgreSQL 16, with each asserted operation executed by the role whose boundary is under test. Owner connections may prepare and inspect fixtures but cannot stand in for runtime privilege proofs.

1. `fleetops_app` cannot INSERT sessions, including a chosen digest for another existing same-org user.
2. `fleetops_app` cannot INSERT users or create arbitrary password-bearing users.
3. `fleetops_app` cannot enumerate stored session digests, through direct table/column access or another exposed read path.
4. `fleetops_app` cannot assume authenticator authority; actual login credentials, memberships, inheritance, SET ROLE, and indirect escalation paths preserve domain separation.
5. Neither operational credential can assume migrator authority, and the authenticator cannot assume app privileges.
6. The authenticator cannot mutate FleetOps domain tables or history and cannot call `transition_asset`.
7. Valid login succeeds through the authenticator connection, returns the raw token once, and stores only its SHA-256 digest.
8. Bad password and unknown user each return 401 with no session write; inactive users/Actors cannot log in.
9. `issue_session` grants runtime EXECUTE only to the authenticator, rejects absent organization context, cross-org users, inactive/non-HUMAN relationships, malformed digests, invalid expiry, and duplicate identity/digest without modifying existing sessions or creating users.
10. `resolve_session` retains exact-digest lookup, minimal output, all independent validity checks, context-free bootstrap behavior, and no data mutation. No alternate context-free lookup exists.
11. Both contexts are transaction-local and pool-safe after commit, rollback, and request failure. A subsequent request cannot inherit prior credential authority.
12. Organization context alone cannot forge authenticated attribution. Missing/malformed/guessed digest context and a credential/organization mismatch fail closed.
13. Expired and revoked sessions cannot establish Actor authority, including when credential context was previously populated. Inactive users and Actors independently fail the same boundary.
14. Actor A cannot persist Actor B attribution within the same organization by SQL arguments, row fields, or an Actor GUC; cross-org attribution remains rejected.
15. A production transition authenticated as A records A. Direct `fleetops_app` invocation of the privileged boundary cannot bypass that binding, including any retained compatibility interface.
16. Direct Item and Asset descriptive UPDATE records authenticated A and database time even if the caller omits attribution fields or tries to retain B/old time or supply arbitrary values. Asset PATCH still works with unchanged global version/history.
17. Creator attribution cannot be forged on representative existing INSERT surfaces, with coverage of the audited Actor, Party, Item, external-reference, Facility, and Location surfaces. Creating a non-HUMAN Actor still attributes its creation to the authenticated HUMAN.
18. Runtime operations through SECURITY DEFINER paths do not acquire the administrative fixture exemption. Existing history/projection grant restrictions remain intact.
19. Logout revokes only the exact current session; another session for the same user and sessions of other users/tenants remain unchanged. No user/Actor/session selector can expand its target.
20. Direct sessions UPDATE is denied to `fleetops_app`, including active-flag changes, and logout cannot reactivate or extend a session.
21. Bootstrap works through deployment/admin authority, refuses overwrite, preserves the seeded organization/HUMAN relationship, and needs no runtime/authenticator user-creation grant.
22. No digest appears in API responses, logs, repr/debug output, errors, or exposed SQL diagnostics. Raw bearer tokens appear only in their intentional one-time login response, never other responses or logging. The bearer path never accepts a supplied digest as a replacement raw token.
23. New privileged helpers have migrator ownership, safe object resolution, revoked PUBLIC EXECUTE, only intended runtime grants, explicit tenant checks, and no unrelated side effects or privilege escalation.
24. All prior Slice 1–5 invariants remain proved, with only the explicitly superseded credential-table access assumptions updated. New tests cannot weaken unrelated invariants to obtain a pass.

The corrective gate must also prove valid version 1 / RECEIVED Asset insertion, rejection of the other initial state/version combinations even for ordinary owner INSERT, and continued legitimate transition updates. This is separate from authentication proof.

## Architecture consistency and scope

D10's authenticated cause is enforced at the durable runtime boundary while typed Actors remain intact. D18 and ADR-002 retain RLS, explicit tenant checks, tenant-safe references, and pooled-connection isolation. D1 permits descriptive fields to remain mutable; D11 keeps database update/record time distinct from event-time claims. D3/D6 preserve authoritative immutable history and protected projections; ADR-005's locking, global version, and valid history gaps remain unchanged. D8 orthogonality, D17 evidence requirements, and receiving-owned Asset creation remain governing.

The database execution domains implement authenticated identity; they are not the user role hierarchies excluded by frozen section 10. No frozen section is amended. An implementation collision with the frozen architecture still requires STOP and the architecture amendment process.

This gate creates only this document. It authorizes no production-code change, test change, migration change, or rewrite of prior ADRs/handoff/architecture; it does not fix or close Slice 5. No new user-management workflow, password reset, MFA, SSO/OAuth, external identity provider, machine credential implementation, application role hierarchy, or Slice 6 work is introduced.
