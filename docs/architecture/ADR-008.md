# ADR-008 — Immutable Assignment Events, Initial Assignment Authority, and Configuration Ordering

## Status

Accepted

## Context and authority

Slice 7 stopped before schema work at checkpoint `ac52c0ce1cdf722f6b770513e68ab08ae728da50`. Review of the governing documents and existing implementation confirmed three missing decisions:

1. [Build Handoff v1.3](FleetOps_v0.1_Build_Handoff_v1.3.docx), Slice 7, retains assignment intervals with `started_at` and nullable `ended_at`, including a second assignment closing the first. ## Decision 1 — Assignment is immutable event history

Store authoritative assignment changes as immutable version-producing events, conceptually `asset_assignment_events`. Each successful assignment, unassignment, or reassignment creates exactly one new event. No earlier authoritative event is updated or deleted to close an assignment.

Assignment functions are ADR-001 Category-1 atomic history/projection boundaries. Normal `fleetops_app` access cannot directly INSERT, UPDATE, DELETE, or TRUNCATE assignment events, or directly UPDATE `assets.current_assignment_id`. The controlled operations insert history and maintain the projection together. Future D6 corrections must preserve original events; no correction workflow is introduced here.

## Decision 2 — Events record both prior and resulting assignment

Each event conceptually contains:

| Field | Contract |
| --- | --- |
| `id` | Permanent FleetOps UUIDv7 event identity. |
| `org_id`, `asset_id` | Non-null organization and Asset scope. |
| `result_version` | Positive, non-null global Asset version produced by this event. |
| `from_assignee_type`, `from_assignee_id` | Prior assignee pair; both NULL means unassigned. |
| `to_assignee_type`, `to_assignee_id` | Resulting assignee pair; both NULL means unassigned. |
| `actor_id` | Credential-derived performing Actor. |
| `occurred_at` | Event-time claim. |
| `recorded_at` | Database/server-set recording time. |
| `reason` | Required stated reason. |
| `corrects_assignment_event_id` | Nullable, inert correction reference. |
| `client_op_id` | Nullable correlation seam, not an idempotency mechanism. |

Exact naming, keys, and constraints belong to Slice 7. Require per-Asset produced-version uniqueness equivalent to `UNIQUE (org_id, asset_id, result_version)`. The prior assignee is derived from authoritative history or the initial witness, never supplied as caller authority. Both timestamps remain distinct UTC values under D11; the client cannot choose authoritative record time or produced version.

Tenant-owned event, witness, and configuration records require non-null organization scope, ADR-002 RLS with USING/WITH CHECK, fail-closed missing context, and tenant-safe Asset/Actor relationships. A correction reference, when structurally present, cannot point to another Asset or organization. Normal assignment operations leave it NULL. No corrections, offline queue, or client-operation deduplication are implemented by this decision.

## Decision 3 — Assignment, unassignment, and reassignment have distinct meanings

| Operation | Authoritative prior pair | Resulting pair |
| --- | --- | --- |
| ASSIGN | Unassigned | Assignee |
| UNASSIGN | Assignee | Unassigned |
| REASSIGN | Prior assignee | New assignee |

Nullability plus durable validation may express these cases without an `event_type` column. If such a column materially improves constraints or readability, its exact vocabulary is `ASSIGN`, `UNASSIGN`, `REASSIGN`, and it must agree with the pairs. Like every event field, it is immutable.

Unassigned to unassigned is not an assignment change and must reject without writes. `assign_asset` establishes an assignment when unassigned and records a direct reassignment when already assigned; `unassign_asset` requires an authoritative current assignee. Neither operation may use a caller-selected prior assignment to choose its meaning.

## Decision 4 — Preserve assignee vocabulary and tenancy

The only assignee types in Slice 7 are `ACTOR`, `LOCATION`, and `PARTY`. For each non-null pair, type and ID are both present, the ID resolves to the table named by that type, and the target belongs to the Asset's organization. Half-null pairs are invalid. Two NULL fields explicitly mean unassigned, not unknown.

The controlled assignment boundary must durably validate polymorphic targets, including type/table agreement, existence, and tenant membership. Ordinary composite tenant-safe foreign keys remain required where structurally applicable. A definer function must perform explicit tenant checks rather than rely on owner RLS. An Actor used as assignee is a domain target; it does not select the Actor performing the operation or confer execution authority.

## Decision 5 — Reassignment produces one event and one global version

A requested reassignment from A to B appends one immutable event containing A as prior assignee and B as resulting assignee. It produces exactly `N + 1` from expected global version N. It does not execute an unassignment and assignment as two version-producing operations, and it does not mutate the event that established A.

One requested reassignment therefore has one atomic history/projection result and one produced Asset version.

## Decision 6 — Historical assignment intervals are derived

For an ASSIGN or REASSIGN event E that establishes an assignment:

| Interval value | Derivation |
| --- | --- |
| Assignee | E's `to_assignee_type` and `to_assignee_id`. |
| `started_at` | E's `occurred_at`. |
| `ended_at` | `occurred_at` of the next UNASSIGN or REASSIGN event ending that assignment; NULL if no such event exists. |

Find the successor in authoritative assignment `result_version` order. A reassignment both ends the preceding interval and begins the next. An unassignment ends the interval and leaves the Asset unassigned. Events remain intact in both cases.

These intervals preserve the handoff's open/closed and `ended_at` read semantics. They are derived views of immutable events, not authoritative rows later updated to close them. No separately mutable current-assignment domain record is needed.

Occurrence clocks do not determine succession. A later-produced event may claim an earlier occurrence time; retain those claims without sorting events by clock, clamping interval endpoints, or rewriting history. Derived endpoints describe the recorded claims and do not certify chronological clock accuracy.

## Decision 7 — Produced global version orders assignment history

Within one tenant-scoped Asset, authoritative assignment order is `result_version ASC`. The latest event is the row with `MAX(result_version)`. Occurrence time, record time, UUID, and insertion order cannot replace this order.

Per-class gaps are valid because other operation classes consume intervening global versions. Assignment history may end below `assets.version`; history ahead of the Asset is inconsistent.

## Decision 8 — Every assignment change shares the Asset lock and global version

Every successful ASSIGN, UNASSIGN, or REASSIGN follows ADR-005/006:

1. Resolve trusted organization scope and the credential-derived Actor through `current_authenticated_actor()`.
2. Identify that organization's Asset and acquire the same `fleetops.assets` row lock used by transition, movement, custody, and ownership operations, with `SELECT ... FOR UPDATE` semantics.
3. Only after acquiring the lock, compare locked `assets.version` with `expected_version = N`.
4. Validate authoritative assignment history or creation authority, projection agreement, target references, and other operation preconditions.
5. Append one immutable assignment event with `result_version = N + 1`.
6. Maintain `current_assignment_id` and set `assets.version = N + 1` exactly once in the same transaction, retaining the lock until transaction completion.

A stale version, missing required authority, inconsistent projection/history, invalid target, or invalid credential rejects without history, projection, or version writes. No Actor parameter, arbitrary Actor GUC, or organization context alone supplies performing authority. Runtime calls through a definer function do not acquire an administrative fixture exemption. Preserve migrator ownership, safe object resolution, revoked PUBLIC EXECUTE, runtime execution restricted to `fleetops_app`, and denial of authenticator domain-operation authority.

Assignment operations leave lifecycle state, location, owner, and custodian unchanged. Conversely, lifecycle transitions, including entry to ON_HOLD, do not change assignment. No assignment-specific concurrency version or shared Asset version register is introduced.

## Decision 9 — The assignment projection references its establishing event

When assigned, `assets.current_assignment_id` references the immutable ASSIGN or REASSIGN event establishing the current assignment. When unassigned, it is NULL, including after an UNASSIGN event.

The relationship must identify an event for the same organization and the same Asset. Controlled admission and reconciliation also verify that it is the latest current-establishing event with a non-null resulting assignee. An arbitrary historical event for that Asset is not sufficient.

The projection is a maintained convenience, never independent admission authority. It cannot validate itself or replace event history. No mutable assignment record is added merely to give this column a target.

## Decision 10 — A newly created v0.1 Asset begins unassigned

Make the creation rule explicit: every newly created v0.1 Asset enters FleetOps UNASSIGNED. Receiving establishes the Asset before later assignment. This is consistent with the current deferred NULL-only projection, but that mutable projection alone does not supply D3 evidence once assignments become available.

Slice 7 therefore introduces an independent immutable witness of the unassigned creation fact. RECEIVED lifecycle state is not used as proof of assignment status; state and assignment remain orthogonal under D8.

## Decision 11 — One immutable initial-assignment witness per Asset

Use a separate tenant-owned record, conceptually `asset_initial_assignment_facts`, that positively attests: this Asset entered FleetOps unassigned.

| Field | Meaning |
| --- | --- |
| `asset_id`, `org_id` | Asset identity and non-null tenant scope. |
| `initially_unassigned` | TRUE; may be omitted only if the row's existence/type unambiguously makes the same positive assertion. |
| `actor_id` | Authenticated cause of creation. |
| `occurred_at` | Creation operation's occurrence-time claim. |
| `recorded_at` | Database/server-set recording time. |

Exactly one witness belongs to each coherently created Asset. Enforce one-record-per-Asset uniqueness and tenant-safe references; a separate UUID is optional because Asset identity can identify the witness. If the boolean exists, it is non-null and constrained TRUE. Do not use a nullable assignee that could mean either unknown or unassigned.

The completeness requirement does not authorize fabricating witnesses for pre-existing incomplete Assets. Their explicit missing-witness treatment is defined below. Ordinary `fleetops_app` has no production witness INSERT surface in Slice 7 and no UPDATE, DELETE, or TRUNCATE privilege. The record remains immutable after later assignments. Production attribution must follow ADR-006 at the durable boundary; controlled fixtures use the existing independent administrative setup convention.

## Decision 12 — Keep assignment authority separate from ADR-007

ADR-007's `asset_initial_facts` records initial ownership, custody, and location. This ADR adds `asset_initial_assignment_facts` solely for the initially unassigned fact now required by Slice 7.

The physical baseline is neither expanded nor reinterpreted. Its schema, authority, and immutability remain governed by ADR-007. Adding a distinct witness under this later decision does not rewrite ADR-007's deliberate exclusion or make physical facts evidence of assignment.

## Decision 13 — The witness produces no global version

The initial-assignment witness is creation history, not an operational assignment change. It has no `result_version` and does not increment `assets.version`.

ADR-004/005 initialization remains Asset version 1 / RECEIVED plus initial lifecycle transition version 1 / NULL to RECEIVED. That lifecycle event represents global version 1 exactly once. Do not create an assignment event at version 1 or another initialization version counter.

## Decision 14 — Receiving retains production creation authority

When Slice 9 introduces production creation, its one coherent receiving transaction must create:

- The Asset at version 1 / RECEIVED with `current_assignment_id = NULL`.
- The initial immutable lifecycle transition at version 1 / NULL to RECEIVED.
- The ADR-007 initial physical-fact baseline.
- The ADR-008 initial-unassigned witness.
- Required identifiers, receipt linkage, and receiving provenance.

The witness records the validated creation operation's Actor and times, not values inferred at the first later assignment. Failure rolls the creation transaction back as a unit. Serialized-Item eligibility and the receipt-based establishment boundary remain unchanged.

Slice 7 may create coherent records only through controlled fixtures. It introduces no `POST /assets`, `POST /initial-assignment-facts`, manual onboarding, or equivalent production witness-creation shortcut.

## Decision 15 — No projection-derived backfill or lazy witness

Do not migration-backfill witnesses from `assets.current_assignment_id IS NULL`, infer them from lifecycle state, or populate them on the first assignment request. The pre-Slice-7 NULL-only constraint does not authorize converting current projections into creation history.

Existing Assets without a witness remain explicitly incomplete. Controlled Slice 7 fixtures create the witness from declared creation inputs alongside the other creation records; they do not read a potentially corrupted projection to manufacture prior truth. Missing witnesses fail first-assignment admission closed and remain visible to reconciliation. No migration-time synthetic assignment events or invented creation timestamps may hide that incompleteness.

## Decision 16 — First assignment requires the witness

After resolving organization/Actor, acquiring the shared Asset lock, and validating expected version N, determine that no assignment events exist for this Asset. Load its same-tenant immutable initial-assignment witness. If missing, reject without writes.

Require `assets.current_assignment_id IS NULL`. The NULL projection agrees with independent creation authority only because the witness positively attests initially unassigned. A non-null projection rejects without repair.

Validate the requested non-null assignee and append an ASSIGN event from unassigned to that assignee. The event produces `N + 1`; set `current_assignment_id` to its ID and `assets.version` to `N + 1` atomically under the retained lock. Do not copy a caller-selected prior assignee, synthesize a witness, or perform an unassigned-to-unassigned operation.

## Decision 17 — Later admission uses the latest event

Once assignment events exist, select the latest by `MAX(result_version)` after the shared lock and expected-version check. Require its result version to be no greater than the locked Asset version. Its resulting assignee is authoritative for the next operation's prior pair.

- If the latest event leaves the Asset assigned, `current_assignment_id` must equal that ASSIGN/REASSIGN event's ID.
- If the latest event leaves it unassigned, `current_assignment_id` must be NULL.

A mismatch or history ahead of the Asset rejects without writes or repair. A later assignment after UNASSIGN derives unassigned from that event, not from the creation witness. Reassignment derives its prior assignee from the latest assigned event. Unassignment requires such an assigned event.

Do not fall back to the creation witness as current authority after event history exists. Witness completeness remains a separate reconciliation concern; later events do not recreate missing creation truth.

## Decision 18 — Reconcile initial and current assignment separately

With no assignment events, a coherent Asset requires a present initial-unassigned witness and NULL `current_assignment_id`. Report a missing witness and a non-null projection as discrepancies rather than inferring or repairing history.

With assignment events, compare the projection against the latest event under Decision 17, not against the initial unassigned value. Continue reporting a missing creation witness independently, including after later events; current-value agreement cannot establish a complete creation timeline.

## Decision 19 — Configurations remain append-only and non-version-producing

`asset_configurations` is immutable append-only history with no maintained current-configuration projection. A configuration append does not increment `assets.version`, carry `result_version`, or enter global Asset-version reconciliation.

This explicitly preserves the handoff's configuration capability without treating it as an ADR-005 version-producing operation. Configuration appends do not implicitly change lifecycle, location, custody, ownership, or assignment.

## Decision 20 — A database-assigned sequence orders configurations

Add an explicit ordering field, conceptually `configuration_seq`, used only for deterministic configuration append order. Prefer a database-generated increasing BIGINT/identity sequence, with durable non-null and uniqueness enforcement. A sequence shared across configuration records is permitted; per-Asset histories may contain gaps.

For a tenant-scoped Asset, configuration history is ordered by `configuration_seq ASC` and current configuration is the visible row with greatest `configuration_seq`. With no configuration rows there is no current configuration; do not invent one.

The database assigns the ordering value during append. Clients and ordinary runtime SQL must not choose, override, reset, or reuse its authoritative values. Exact sequence/default and privilege enforcement belongs to Slice 7. Keep FleetOps UUID identity separate from this ordering field.

Sequence order is database allocation order, not a guarantee of transaction commit order or physical application time. Concurrent transactions can commit in a different order from their allocated values, and aborted appends can leave gaps. Reads use the greatest sequence among visible committed rows in their snapshot. Do not renumber history, require contiguity, or serialize all Asset operations to disguise those semantics.

## Decision 21 — Timestamps and UUIDs are not configuration authority

`applied_at` is an event-time claim. `recorded_at` is database/server recording time and may coincide across rows or differ from commit order. UUIDv7 supplies identity, not business ordering. None determines authoritative configuration order.

Preserve both timestamps as distinct UTC facts under D11. Out-of-order or equal time claims do not change which sequence is latest, and selecting the latest sequence does not rewrite either timestamp.

## Decision 22 — Configuration sequence is not Asset authority

`configuration_seq` is not an optimistic-concurrency token, authorization version, or global Asset event number. It must never validate an expected Asset version, authorize another Asset operation, enter combined global-version reconciliation, or determine lifecycle/location/custody/ownership/assignment authority.

The database sequence orders one history class only. It is not a shared Asset event register, a separate Asset concurrency system, or a requirement for a sequence-register table.

## Decision 23 — Configuration appends do not contend on Asset versions

Concurrent valid configuration appends may both succeed with distinct sequence values. They do not need an expected Asset version and must not reject merely because another operation advanced `assets.version`.

Each append still validates same-tenant Asset existence, authenticated Actor, and request/schema constraints. Ordinary database referential and transaction behavior still applies; this decision does not promise an absence of all database locks. Do not add the ADR-005 Asset lock/version protocol merely to assign configuration order. Configuration and assignment may proceed concurrently without corrupting either configuration history or global Asset-version semantics.

## Decision 24 — Configuration attribution follows ADR-006

Preserve the v1.3 configuration fields: `asset_id`, `image_name`, `image_version`, `config_profile`, `notes`, `applied_by` Actor, `applied_at`, `recorded_at`, and `evidence_ref`, with the normal FleetOps identity/tenant conventions and the added `configuration_seq`. Use v1.3 field names during implementation; exact constraint details remain Slice 7 work.

The performing/applied Actor derives from the valid credential through `current_authenticated_actor()` or the same accepted database-bound attribution mechanism. Request fields, SQL Actor selectors, arbitrary GUCs, and organization context alone cannot choose another performer. Recording time is database/server-set.

Because configuration has no maintained projection, prefer ordinary RLS-protected INSERT with durable attribution and ordering constraints under ADR-001's smallest-boundary rule. This ADR supplies no blanket Category-2 stored-procedure authorization. Protect sequence and record-time assignment even on permitted direct SQL paths; a request-model restriction alone is insufficient.

## Decision 25 — Configuration evidence remains inert

At the current checkpoint no verifiable evidence subsystem exists. Slice 7 normal configuration writes require `evidence_ref = NULL`, enforced durably at the database boundary. Unverifiable non-null identifiers reject rather than being accepted as evidence.

Slice 11 retains evidence implementation and the eventual tenant-safe, provenance-checked relationship. This NULL-only seam does not weaken D17 or authorize fake evidence, attachment storage, or an early evidence workflow.

## Decision 26 — Configuration rows remain immutable

`fleetops_app` cannot UPDATE, DELETE, or TRUNCATE configuration rows, including their sequence, Actor, or timestamps. Later appends leave all prior rows intact.

Future corrections follow D6 through explicit correction history while preserving originals. This ADR does not design or implement that workflow.

## Decision 27 — Extend combined reconciliation only with assignment events

After Slice 7, global Asset-version reconciliation includes the version-producing classes:

- `asset_transitions`.
- `asset_movements`.
- `asset_custody_changes`.
- `asset_ownership_changes`.
- `asset_assignment_events`.

It excludes `asset_initial_facts`, `asset_initial_assignment_facts`, and `asset_configurations`. For each tenant-scoped Asset, every version from 1 through `assets.version` must appear exactly once across the producing classes. Detect missing, cross-class duplicate, and ahead-of-Asset versions without a version register or silent repair. Per-class gaps and lower latest class versions remain valid.

Extend the existing combined reconciliation rather than adding a competing version system. Preserve lifecycle and physical-fact checks, including baseline completeness, as separate invariants.

## Decision 28 — Assignment corruption must remain detectable

The authenticated tenant-scoped reconciliation surface must report at minimum:

- Missing initial-assignment witness, even when later assignment events exist.
- Non-null `current_assignment_id` before assignment event history exists.
- Latest event assigned but projection NULL or pointing to the wrong event.
- Latest event unassigned but projection non-null.
- A projection target belonging to another Asset/tenant or otherwise unable to establish the current assignment, if privileged corruption bypasses normal constraints.
- Assignment history `result_version > assets.version`.
- Missing global versions, duplicate versions across producing classes, and global history ahead of the Asset.

Report without repair. A discrepancy cannot be hidden by copying the projection into history, recreating the witness, updating an earlier event, or treating a separate completeness check as a substitute for current-value agreement.

## Decision 29 — Reconstruct assignment from creation and events

A complete assignment timeline starts with the positive initially unassigned witness, followed by events in ascending `result_version`. Each event's prior/resulting pairs explain the change; the current projection is unnecessary as historical evidence.

Derived assignee intervals expose `started_at` and `ended_at` under Decision 6. Both records establishing successive assignments persist, with closure represented by the later event. Missing creation truth remains visible as an incomplete timeline rather than an inferred unassigned start.

## Decision 30 — Reconstruct configuration by sequence

Read all configurations for the tenant-scoped Asset in ascending `configuration_seq`. Current configuration means the visible row with `MAX(configuration_seq)`, not greatest `applied_at` or `recorded_at`.

Preserve each row's original Actor, application-time claim, record time, and payload. An occurrence-order presentation in a later combined history API does not replace this configuration order or assignment produced-version order.

## Decision 31 — This gate authorizes no implementation or deferred workflow

This ADR records only the minimum assignment representation, initial-assignment authority, configuration ordering, and related Slice 7 invariants. A separately opened Slice 7 implements its schema, migration, bounded authenticated APIs, reconciliation, and proofs after this design gate closes.

No procurement, receiving implementation, evidence storage, correction workflow, offline capture, labels, software licensing, RMA/shipping, materials, or governed operations enter this gate or Slice 7 through this decision. The receiving creation consequence is a future Slice 9 obligation, not an early production creation path.

## Bounded handoff refinement

This ADR explicitly refines only these previously unresolved details in v1.3 Slice 7:

1. Open/closed assignment intervals and historical `ended_at` are derived from immutable assignment events. The earlier interval remains reconstructable after reassignment without UPDATE to authoritative history.
2. First assignment uses a separate immutable initially unassigned witness. The NULL assignment projection alone is insufficient, and existing projections cannot be migration-backfilled into authority.
3. Configuration latest/history order uses greatest/ascending database-assigned `configuration_seq`.
4. Configurations remain non-version-producing and outside global Asset-version reconciliation.

All other v1.3 Slice 7 requirements remain governing: assignee vocabulary, authenticated Actor, shared Asset lock, post-lock version validation, orthogonality, immutable history, tenancy, reconstruction, and acceptance proofs. The interval acceptance is satisfied by derived closure with both establishing events preserved. Its wording is not permission to update an old authoritative row.

ADR-007's separate physical baseline and all unaffected ADR-001 through ADR-007 decisions remain unchanged. No v1.4 is required solely to begin a separately opened Slice 7 after ADR-008 is accepted. The source handoff and frozen architecture remain unchanged.

13. Assigned `current_assignment_id` points to the latest establishing ASSIGN/REASSIGN event for the same Asset and organization.
14. The projection is NULL when the latest event is UNASSIGN.

18. Assignment versus lifecycle transition contends on the same Asset lock with one winner and one post-lock stale rejection.
19. Assignment versus movement contends on the same Asset lock with one winner and one post-lock stale rejection.
20. Assign versus unassign expecting the same version has one winner, one stale rejection, and no losing writes.
21. Combined reconciliation includes assignment-produced versions and accepts a complete interleaved five-class global sequence with per-class gaps.
22. Cross-class duplicate assignment-produced versions are detected.
23. Missing assignment-produced global versions are detected.
24. Assignment history ahead of the Asset version is rejected by admission and reported by reconciliation.
25. Cross-tenant ACTOR assignees reject.
26. Cross-tenant LOCATION assignees reject.
27. Cross-tenant PARTY assignees reject.
28. Wrong type/table pairs, missing targets, unsupported types, and half-null assignee pairs reject durably.
29. Derived assignment intervals expose the required `started_at`/`ended_at`, including reassignment and unassignment, without modifying stored events. Successor selection follows result version even when occurrence times disagree.
30. Configuration appends change no Asset projection or global version and carry no `result_version`.
31. Configuration ordering values are database-assigned; request fields and direct runtime SQL cannot select, override, reset, or reuse authoritative sequence values.
32. Concurrent configuration appends obtain distinct sequence values and persist independently. Reversed commit order and rollback gaps do not change the defined sequence ordering rule.
33. Latest configuration uses the greatest visible `configuration_seq`; an Asset with no records has no current configuration.

35. Configuration Actor is credential-derived and cannot be spoofed; record time is database/server-set at the durable boundary.
36. Configuration UPDATE, DELETE, and TRUNCATE are denied; appending later rows preserves earlier payloads and metadata.
37. Configuration `evidence_ref` is durably NULL-only in Slice 7; unverifiable evidence IDs reject.
38. Configuration rows and both creation witnesses are excluded from combined global Asset-version reconciliation.

Also preserve all unaffected v1.3 and separately opened Slice 7 acceptance requirements, including same-class assignment contention, unassignment versus ownership contention, an independent lock-before-version proof, configuration/assignment concurrency, tenant isolation, strict bounded APIs, migration round trip, and prior Slice 1–6 regressions. Missing-witness reconciliation must be exercised both before and after later assignment history. Witness attribution requires a real runtime-boundary proof under isolated test privileges or an equivalent controlled probe, without granting a production creation surface. Tenant-isolation and privilege assertions execute as the actual runtime role; administrative connections may prepare and inspect fixtures but cannot stand in for that role.

Database, concurrency, and migration proofs use real PostgreSQL 16. The accepted pre-gate baseline is 862 passing tests on PostgreSQL 16.15; this document-only gate introduces no test execution result and requires no full-suite rerun. No existing test may be weakened to accommodate implementation.

## Architecture compatibility and implementation gate

| Governing contract | Compatibility |
| --- | --- |
| D3 | Independent creation witness or latest immutable event supplies assignment authority; projections are checked against it and maintained atomically. Reconciliation never validates a projection against itself. |
