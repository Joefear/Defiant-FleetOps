# Defiant FleetOps — Claude Code Repository Instructions

## Mandatory Git authorship and attribution rule

Git identity and attribution rules are mandatory.

- Never modify `git user.name`.
- Never modify `git user.email`.
- Never modify repository or global Git identity/configuration unless Sam explicitly directs it.
- Preserve the existing configured human Git identity.
- Never add AI/model/tool attribution to commits or repository content.
- Prohibited examples include `Co-Authored-By: Claude`, `Co-Authored-By: Codex`, and `Co-Authored-By` for any AI, model, agent, or tool.
- Never add `Generated-By`, `Assisted-By`, `Generated by Claude`, `Generated by Codex`, `AI-assisted`, `AI-generated`, model attribution, agent attribution, bot attribution, tool attribution, or similar signatures or trailers.
- Do not add AI attribution to source comments, docs, changelogs, PR text, release notes, or headers unless Sam explicitly requests it.
- Do not add `Signed-off-by` or other trailers unless the active task explicitly requires them.
- Codex does not commit or push unless explicitly authorized.
- Claude Code commits and pushes only when the active review workflow explicitly authorizes it after PASS.
- Lack of AI attribution is intentional repository policy and must not be "corrected."

## Required reading and authority

Before relevant implementation or review work, including any production-code change, read:

1. [Frozen architecture Markdown](docs/architecture/FleetOps_Architecture_Boundary_v0.1.md).
2. [Shared coding standards](docs/development/CODING_STANDARDS.md).
3. [Build handoff v1.1](docs/architecture/FleetOps_v0.1_Build_Handoff_v1.1.docx) when working from the build handoff or an active slice, including that slice's acceptance requirements.

The frozen FleetOps Architecture & Boundary document remains the governing implementation contract. Its [frozen DOCX](docs/architecture/FleetOps_Architecture_Boundary_v0.1.docx) is the governing source artifact; the Markdown is a working transcription. If they disagree, STOP and defer to the DOCX.

These repository instructions and the shared coding standards must not reinterpret, summarize into weaker language, replace, or amend the frozen architecture. Never silently reinterpret a controlled architectural decision. If implementation conflicts with a controlled architectural section, STOP and report a possible Architecture Amendment Request rather than working around the conflict.

## Review responsibilities

- Review the ACTUAL diff, not only the implementer's report.
- Verify the active slice against every cited governing decision.
- Verify its acceptance tests exist and prove what they claim; run the relevant tests/checks independently.
- Confirm prior invariant tests remain green. Never weaken a test to make implementation pass.
- Use real PostgreSQL 16 wherever the handoff requires it. No SQLite substitution.
- Work only on the explicitly opened slice/task. Treat scope expansion and pulling deferred work forward as defects.
- Treat architecture reinterpretation as a STOP. Do not silently fix architectural conflicts during review; report them.
- Follow the mandatory commenting and documentation rules in [CODING_STANDARDS.md](docs/development/CODING_STANDARDS.md). Treat missing or inadequate comments on non-obvious logic as a review defect.
- Do not claim PASS merely from test count.
- Follow the mandatory Git authorship and attribution rule above.

- Commit and push only when the active workflow explicitly says Claude should do so after PASS.
